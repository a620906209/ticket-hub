## Requirements

### Requirement: 未登入使用者存取需登入頁面或執行需登入操作時導向登入頁
系統 SHALL 在使用者嘗試存取需要登入的買家頁面（我的訂單、下單結果頁）或在公開頁面上執行需要登入的操作（活動詳情頁選位）但尚未登入時，導向登入頁；登入成功後 SHALL 導回原本嘗試存取的頁面。活動列表頁與活動詳情頁本身（含座位圖瀏覽）不需要登入即可瀏覽——只有「選位」這個動作本身才觸發導向登入頁，不是進入活動詳情頁就要求登入。

#### Scenario: 未登入直接進入我的訂單頁
- **WHEN** 未登入的使用者直接開啟「我的訂單」頁面網址
- **THEN** 系統導向登入頁

#### Scenario: 未登入在活動詳情頁點選座位
- **WHEN** 未登入的使用者在活動詳情頁點選任一座位（不論該座位是否為 Available 狀態）
- **THEN** 系統導向登入頁，不進行任何選位動作

#### Scenario: 登入成功後導回原頁面
- **WHEN** 使用者因未登入被導向登入頁，登入成功
- **THEN** 系統導回使用者原本嘗試存取的頁面（例如導回原本瀏覽的活動詳情頁，可繼續選位）

### Requirement: 買家可透過介面註冊與登入
系統 SHALL 提供註冊頁與登入頁，呼叫既有 `member-management`／`authentication` API 完成會員註冊與登入；登入成功後 SHALL 將角色為一般會員者導向買家端首頁。

#### Scenario: 註冊成功
- **WHEN** 使用者在註冊頁填寫有效的 Email／密碼並送出
- **THEN** 系統呼叫註冊 API 成功後導向登入頁

#### Scenario: 登入成功導向買家端首頁
- **WHEN** 一般會員在登入頁輸入正確帳密送出
- **THEN** 系統登入成功並導向買家端活動列表首頁

#### Scenario: 登入失敗顯示錯誤訊息
- **WHEN** 使用者輸入錯誤密碼送出登入
- **THEN** 系統顯示登入失敗的錯誤訊息，停留在登入頁

### Requirement: 買家可瀏覽活動列表與座位可售狀態
系統 SHALL 提供活動列表頁與活動詳情頁，呼叫既有 `event-catalog`／`ticket-purchase` API 顯示活動基本資訊與座位可售狀態（Available／Held／Sold），不需要登入即可瀏覽。活動詳情頁 SHALL 並排顯示活動資訊（含海報圖片與說明文字，若 Admin 建立活動時有填寫）與座位選擇區；座位依分區分組顯示。此狀態為頁面載入或手動重新整理當下查詢 API 取得的結果，非伺服器推播的即時更新（本輪不引入 WebSocket／SignalR）。

#### Scenario: 瀏覽活動列表
- **WHEN** 使用者開啟活動列表頁
- **THEN** 系統以卡片格線顯示目前所有活動的基本資訊

#### Scenario: 查看活動座位狀態
- **WHEN** 使用者點選某活動進入詳情頁
- **THEN** 系統顯示該活動的資訊（含海報／說明，如有設定）與座位圖，座位依分區分組、每個座位標示目前的可售狀態

#### Scenario: 活動未設定海報或說明
- **WHEN** Admin 建立活動時沒有填寫海報網址或說明
- **THEN** 系統不顯示海報圖片區塊或說明文字區塊，不顯示空白佔位或錯誤訊息

### Requirement: 買家可選位並送出訂單
系統 SHALL 在活動詳情頁提供座位選擇與下單操作，呼叫既有 `ticket-purchase` 下單 API；下單成功後 SHALL 導向訂單結果頁，顯示訂單 Id 與持有到期時間。活動可由 Admin 設定「每筆訂單限購張數」（選填，未設定代表不限制）；當已選座位數加上已輸入的純計數票種購買數量總和達到上限時，系統 SHALL 阻止再選新座位或增加計數購買數量，直到取消已選座位或降低計數數量釋出額度。座位選購與計數購買輸入的阻止方式不同：點選座位被阻止時 SHALL 顯示提示訊息（比照既有座位選購的既定行為，見「已選座位數達到每筆訂單限購張數」Scenario）；計數購買數量輸入則採限制型互動，由輸入元件本身限制數值上限、不接受超過限購的輸入，不另外顯示提示訊息或呈現為錯誤狀態（見「純計數購買數量達到每筆訂單限購張數」Scenario，與可售總量的限制型互動一致）。此限制前端會提前檢查並提示，但**後端 `PlaceOrder` API 才是最終把關**——前端檢查被繞過或跟後端資料不同步時，後端仍會拒絕超過上限的下單請求。

活動詳情頁 SHALL 對 `RequiresSeat = false` 的純計數票種，於獨立的「計數購票」區塊顯示票種名稱、票價、當下可售總量，並提供購買數量輸入（非負整數，0 代表不購買）；此區塊與既有座位選購區塊（僅列出 `RequiresSeat = true` 的票種）並列顯示，互不影響彼此的選購狀態。計數購買操作比照既有座位選位規則，視為需登入才能執行的操作：未登入時嘗試調整任一計數票種的購買數量（含直接輸入、增減按鈕等任何互動方式），系統 SHALL 立即導向登入頁，不套用該次數量變更；登入成功後 SHALL 導回原頁面，比照既有座位選位「登入後可繼續選位」的既定行為，不特別還原導向登入前嘗試輸入的數值——因為攔截發生在數值套用之前，本來就沒有暫存值需要還原。

單一計數票種的購買數量輸入元件 SHALL 將可輸入上限設為「該票種當下可售總量」與「限購剩餘額度（`maxTicketsPerOrder` 扣除已選座位數、扣除其他計數票種已輸入數量、加回自己目前輸入值後的結果）」兩者中較小值，並由元件本身限制輸入不得超過此上限——超過上限的輸入 SHALL 被限制、不接受，不呈現為錯誤狀態（限制型輸入控制，元件不允許出現暫時性的超額顯示值，與下方「計數輸入元件限制數量不得超過可售總量」Scenario 一致）；此限制與既有「區域隨選」的雙重限制計算方式一致，兩者共用同一份剩餘額度，任一方消耗額度後 SHALL 立即反映到另一方可輸入/可抽選的上限。數量為 0 的計數票種 SHALL 視為未選購，送出訂單時 MUST NOT 包含在下單請求的選購項目中。

送出訂單時，座位選購項目與計數購買項目（數量大於 0 者）SHALL 合併於同一次下單請求送出，呼叫既有支援混合項目的下單 API；座位項目送出時不帶購買數量（後端預設視為 1，維持既有行為），計數項目送出對應的 `TicketTypeId` 與購買數量、不帶座位 Id。送出前系統 MUST 重新加總座位數與計數購買總量，超過限購張數時 MUST 擋下、顯示提示訊息、不呼叫下單 API——不得僅依賴各輸入元件的上限屬性作為唯一防線（例如買家在其中一個輸入框調整上限生效前，已在另一個輸入框填入超額數值的情況）。

下單 API 呼叫失敗時，若為 401（換發失敗），系統 SHALL 直接導向登入頁（比照既有座位選位的登入要求），不顯示下單失敗訊息、不套用下方的清空/刷新處理——活動詳情頁為公開頁，既有全域換發/登入導頁機制僅在需要登入的路由才會生效，不會處理公開頁上的登入失效，此元件 MUST 自行攔截 401 並導頁。除 401 以外的其他下單失敗（座位已被搶先鎖定、計數票種可售總量於送出當下已被其他買家買光、或後端其他驗證失敗），系統 SHALL 一律顯示錯誤訊息、清空目前已選座位與已輸入的計數購買數量、並重新呼叫查詢 API 刷新座位與票種資料——比照既有座位選購失敗時的既定處理，不依失敗原因做差異化處理（維持既有行為單純、一致，不新增依錯誤類型分流的重試或保留輸入邏輯）。

活動是否處於熱門搶購模式，前端 SHALL 直接讀取活動列表查詢 API（`GET /api/events`，`ticket-purchase`「瀏覽活動與座位可售狀態」能力）回應中的 `IsQueueModeEnabled` 欄位判斷，不需另外呼叫其他端點確認。若活動處於熱門搶購模式（`IsQueueModeEnabled = true`），買家進入活動詳情頁的選位/計數購票操作前，系統 SHALL 先呼叫排隊狀態查詢 API：尚未加入排隊時 SHALL 提供加入排隊的操作；已加入且狀態為 `Waiting` 時 SHALL 顯示排隊等待畫面（含前方等待人數），停用座位選擇、計數購買輸入與區域隨選快速下單的操作入口，並以固定間隔定期輪詢排隊狀態查詢 API（輪詢間隔為可設定值，與後端 `PurchaseQueueOptions.PollingInterval` 同數量級，避免輪詢過於頻繁造成負擔或過於稀疏造成畫面更新明顯延遲）；每次輪詢回應除排隊紀錄狀態外，SHALL 一併包含該活動當下的 `queueModeEnabled`（見 `purchase-queue`「買家可查詢自己的排隊狀態」能力），不需另外呼叫活動列表 API 確認——若某次輪詢回應的 `queueModeEnabled` 為 `false`（Admin 已於買家等待期間關閉熱門搶購模式），系統 SHALL 停止輪詢、關閉排隊等待畫面，開放選位/計數購買、區域隨選與送出訂單操作，比照該活動從未開啟熱門搶購模式的一般行為。狀態轉為 `Admitted` 時 SHALL 停止輪詢、關閉排隊等待畫面，開放選位/計數購買、區域隨選與送出訂單操作。下單 API 回傳 `403 Forbidden` 且 `ProblemDetails.title === "QueueAdmissionRequired"`（排隊資格不足：未入場或已逾時）而失敗時，系統 SHALL 顯示提示訊息並導回排隊等待畫面重新查詢狀態，不套用「其他下單失敗」一般情形的清空/刷新處理（此情形不代表座位或庫存資料有變動）；前端 MUST 同時檢查 `status` 與 `title` 兩者才視為排隊資格不足，不得只依 HTTP 403 狀態碼判斷——其他業務語意的 403（例如既有「非本人操作」情境）SHALL 沿用一般授權錯誤處理，不導向排隊等待畫面。下單 API 因超過請求頻率限制（429）而失敗時，系統 SHALL 顯示「請稍後再試」的提示訊息，不清空已選座位與已輸入的計數購買數量、不重新整理座位與票種資料——此情形代表發送速度過快，而非資料已變動，維持買家目前已選內容供其等待後直接重試。

#### Scenario: BW-ORDER-001 選擇可售座位並成功下單
- **WHEN** 已登入買家在活動詳情頁選擇一個或多個 Available 狀態的座位並送出下單
- **THEN** 系統呼叫下單 API 成功，導向該筆訂單的訂單結果頁

#### Scenario: BW-ORDER-002 下單時座位已被搶先鎖定
- **WHEN** 買家送出下單時，其中一個座位已被其他訂單鎖定或售出（API 回傳失敗）
- **THEN** 系統顯示下單失敗的錯誤訊息，清空目前已選座位與已輸入的計數購買數量，重新呼叫查詢 API 刷新座位與票種資料，不導向訂單結果頁

#### Scenario: BW-ORDER-003 送出訂單時登入狀態已失效（401）
- **WHEN** 買家送出下單時，Access Token 已過期且換發也失敗，下單 API 回傳 401
- **THEN** 系統直接導向登入頁，不顯示下單失敗訊息，不套用清空已選座位/計數輸入與重新整理資料的處理

#### Scenario: BW-ORDER-004 已選座位數達到每筆訂單限購張數
- **WHEN** 買家在已選座位數（含已輸入的計數購買數量總和）等於活動設定的限購張數時，再點選一個新的 Available 座位
- **THEN** 系統顯示「已達每筆訂單限購張數」的提示訊息，不將新座位加入已選清單

#### Scenario: BW-ORDER-005 活動未設定限購張數
- **WHEN** 活動的每筆訂單限購張數為未設定（不限制）
- **THEN** 買家可以選擇任意數量的 Available 座位，不受張數限制

#### Scenario: BW-ORDER-006 未登入嘗試調整計數購買數量
- **WHEN** 未登入的使用者嘗試調整任一純計數票種的購買數量（直接輸入或使用增減按鈕）
- **THEN** 系統立即導向登入頁，不套用該次數量變更；登入成功後導回原頁面，該票種購買數量維持 0

#### Scenario: BW-ORDER-007 純計數票種輸入購買數量並成功下單
- **WHEN** 已登入買家在活動詳情頁的計數購票區塊，對一個 `RequiresSeat = false` 的票種輸入購買數量（不超過當下可售總量與限購剩餘額度）並送出訂單
- **THEN** 系統呼叫下單 API 成功（該筆選購項目不含座位 Id），導向該筆訂單的訂單結果頁

#### Scenario: BW-ORDER-008 混合座位選購與純計數購買並成功下單
- **WHEN** 已登入買家同時選擇一個或多個座位，並對一個純計數票種輸入購買數量，送出下單
- **THEN** 系統將座位項目與計數項目合併於同一次下單請求送出，成功後導向該筆訂單的訂單結果頁

#### Scenario: BW-ORDER-009 純計數購買數量達到每筆訂單限購張數
- **WHEN** 買家輸入的計數購買數量（加上已選座位數）達到活動設定的限購張數，嘗試再增加計數購買數量
- **THEN** 計數輸入元件限制數值不得超過剩餘額度，不接受超過限購的輸入，不呈現為錯誤狀態（限制型，與「計數輸入元件限制數量不得超過可售總量」Scenario 一致的互動模式；已選座位數達到限購張數後再嘗試選新座位，仍依「已選座位數達到每筆訂單限購張數」Scenario 顯示提示訊息——座位選購走點選互動，不是連續數量輸入，兩種介面元件的既定回饋方式不同）

#### Scenario: BW-ORDER-010 計數輸入元件限制數量不得超過可售總量
- **WHEN** 買家嘗試在計數輸入框以直接輸入或增減按鈕，調整超過該票種當下可售總量的數值
- **THEN** 輸入元件限制數值不得超過可售總量上限，不接受超額輸入，不呈現為錯誤狀態

#### Scenario: BW-ORDER-011 送出時因庫存已變動被後端拒絕
- **WHEN** 買家在前端檢查通過的情況下送出訂單，但送出當下某計數票種的可售總量已因其他買家搶購而變動，後端拒絕本次購買
- **THEN** 系統顯示下單失敗訊息，清空目前已選座位與已輸入的計數購買數量，並重新整理票種與座位資料（比照「下單時座位已被搶先鎖定」的統一失敗處理）

#### Scenario: BW-ORDER-012 純計數票種可售總量為 0
- **WHEN** 某純計數票種當下的可售總量為 0
- **THEN** 該票種的購買數量輸入框上限為 0、無法輸入大於 0 的數量，介面顯示「已售完」提示，不視為錯誤狀態、不顯示錯誤訊息樣式

#### Scenario: BW-ORDER-013 活動未設定限購張數時的純計數購買
- **WHEN** 活動的每筆訂單限購張數為未設定（不限制），買家對某純計數票種輸入購買數量
- **THEN** 該票種的購買數量輸入僅受當下可售總量限制，不受限購張數限制

#### Scenario: BW-ORDER-014 計數購買數量為 0 時不送出對應項目
- **WHEN** 買家在計數購票區塊對某票種維持購買數量為 0（未輸入或清空），對其他票種正常選購並送出訂單
- **THEN** 下單請求的選購項目 MUST NOT 包含該數量為 0 的票種

#### Scenario: BW-ORDER-015 送出訂單前偵測到合併總數超過限購張數
- **WHEN** 買家透過分別在座位網格與計數輸入框操作，使已選座位數與計數購買總量的加總超過活動設定的限購張數（例如個別輸入當下未觸發即時提示，但送出當下加總已超過）
- **THEN** 系統在呼叫下單 API 之前偵測到總數超過限購張數，擋下送出、顯示提示訊息，不呼叫下單 API

#### Scenario: BW-ORDER-016 已手動選取座位佔用額度後，計數購買輸入上限隨之減少
- **WHEN** 買家已在座位網格手動選取座位、佔用部分限購額度（尚未送出訂單），接著要在計數購票區塊輸入購買數量
- **THEN** 該計數票種輸入框當下可輸入的上限 SHALL 扣除已選座位數後重新計算，不允許輸入超過剩餘額度的數量

#### Scenario: BW-QUEUE-001 進入熱門搶購模式活動且尚未加入排隊
- **WHEN** 已登入買家進入 `IsQueueModeEnabled = true` 的活動詳情頁，且尚未加入該活動的排隊
- **THEN** 系統顯示加入排隊的操作，不開放選位/計數購買輸入

#### Scenario: BW-QUEUE-002 排隊中顯示等待畫面並輪詢狀態
- **WHEN** 已登入買家已加入排隊，狀態為 `Waiting`
- **THEN** 系統顯示排隊等待畫面與目前前方等待人數，停用座位選擇、計數購買輸入與區域隨選快速下單的操作入口，並定期輪詢排隊狀態

#### Scenario: BW-QUEUE-003 排隊入場後開放選位與下單
- **WHEN** 買家的排隊狀態由 `Waiting` 轉為 `Admitted`
- **THEN** 系統停止輪詢、關閉排隊等待畫面，開放座位選擇、計數購買輸入、區域隨選快速下單與送出訂單操作

#### Scenario: BW-QUEUE-004 下單時排隊資格已逾時
- **WHEN** 買家送出下單時，其排隊資格已逾時或不存在，下單 API 回傳 `403 Forbidden` 且 `title === "QueueAdmissionRequired"`
- **THEN** 系統顯示提示訊息並導回排隊等待畫面重新查詢狀態，不清空座位/計數輸入、不比照一般失敗重新整理座位與票種資料

#### Scenario: BW-QUEUE-006 其他語意的 403 不視為排隊資格不足
- **WHEN** 買家送出下單時，下單 API 回傳 `403 Forbidden`，但 `title` 不是 `"QueueAdmissionRequired"`（例如既有其他業務語意的 403）
- **THEN** 系統 SHALL 沿用一般授權錯誤處理，不導向排隊等待畫面、不誤判為排隊資格不足

#### Scenario: BW-QUEUE-005 下單因請求頻率限制被拒絕
- **WHEN** 買家送出下單時，下單 API 回傳 429（請求頻率限制）
- **THEN** 系統顯示「請稍後再試」提示訊息，不清空已選座位與已輸入的計數購買數量，不重新整理座位與票種資料

#### Scenario: BW-TOGGLE-001 排隊等待期間 Queue Mode 被關閉
- **WHEN** 買家在排隊等待畫面（`Waiting`）停留期間，Admin 將該活動的熱門搶購模式關閉，前端下一次輪詢排隊狀態查詢 API 回應中的 `queueModeEnabled` 已為 `false`
- **THEN** 系統停止輪詢、關閉排隊等待畫面，開放座位選擇、計數購買輸入、區域隨選與送出訂單操作，比照該活動從未開啟熱門搶購模式的一般行為，不要求買家等到原本的 `Admitted`、不誤導買家以為仍需排隊

### Requirement: 買家可用區域隨選快速下單，不必逐一手動點選座位或另外按送出
系統 SHALL 在活動詳情頁的選位區提供「區域隨選」功能：買家選擇一個分區（或「全部區域」）與想購買的張數，點選「自動選位並送出訂單」後，系統 SHALL 從符合條件、目前 Available 且尚未被選取的座位中**隨機**抽出對應數量，加入已選清單後**直接呼叫下單 API 送出訂單**——買家不需要再另外滾動頁面、點擊底部的「送出訂單」按鈕確認一次。此功能的隨機抽選對象僅限座位選購：分區下拉選單的選項來源 SHALL 僅列出目前有 `RequiresSeat = true` 票種對應座位的分區代碼，純計數票種沒有對應座位、不會出現在此下拉選單中，抽選候選座位集合 MUST NOT 包含任何純計數票種。但送出訂單這一步驟與「計數購票」區塊共用同一次下單請求——若買家在使用區域隨選之前已在計數購票區塊輸入購買數量（尚未送出），區域隨選送出時 SHALL 將這些已輸入的計數購買數量一併合併送出，不需要買家分開送出兩次訂單，行為與「買家可選位並送出訂單」需求中座位與計數項目合併送出的規則一致。分區下拉選單 SHALL 預設為「全部區域」；選擇「全部區域」時，抽選池 SHALL 涵蓋所有座位制分區的可售座位，不限定單一分區、也不含計數制票種。買家指定的自動選位張數 MUST NOT 超過「符合條件的可售座位數」與「每筆訂單限購張數的剩餘額度」兩者中較小值；超過時系統 MUST 顯示錯誤訊息、不加入任何座位、不呼叫下單 API（不得將張數靜默縮減為實際可抽取的數量後直接送出——買家要求的張數與實際送出訂單的張數必須一致）。此剩餘額度計算 SHALL 扣除已選座位數與已輸入的純計數票種購買數量總和；未登入時點選此按鈕的行為 SHALL 與點選單一座位一致，導向登入頁、不進行任何選位或下單動作。

#### Scenario: 全部區域隨機選位並直接送出訂單
- **WHEN** 已登入買家維持預設的「全部區域」、輸入張數（不超過可售座位數與限購剩餘額度），點選「自動選位並送出訂單」
- **THEN** 系統從所有分區的可售座位中隨機抽出對應數量、呼叫下單 API，成功後直接導向該筆訂單的訂單結果頁，不需要買家再手動點其他按鈕

#### Scenario: 指定單一分區隨機選位並直接送出訂單
- **WHEN** 已登入買家改選特定分區與張數，點選「自動選位並送出訂單」
- **THEN** 系統只從該分區的可售座位中隨機抽出對應數量並直接送出訂單

#### Scenario: 區域隨選張數超過可售座位或限購剩餘額度
- **WHEN** 買家指定的張數超過符合條件的可售座位數，或超過每筆訂單限購張數的剩餘額度
- **THEN** 系統顯示對應的錯誤訊息，不加入任何座位、不呼叫下單 API

#### Scenario: 未登入使用區域隨選
- **WHEN** 未登入的使用者選擇分區（或維持全部區域）與張數並點選「自動選位並送出訂單」
- **THEN** 系統導向登入頁，不進行任何選位或下單動作

#### Scenario: 已輸入純計數購買數量時，區域隨選的剩餘額度隨之減少
- **WHEN** 買家已在計數購票區塊輸入購買數量（尚未送出訂單），接著使用區域隨選輸入張數
- **THEN** 區域隨選的剩餘額度計算 SHALL 扣除已輸入的計數購買數量，超過扣除後的剩餘額度時顯示錯誤訊息、不加入任何座位

#### Scenario: 純計數票種不會出現在區域隨選的分區選單與抽選池中
- **WHEN** 活動同時存在座位制與純計數票種，買家開啟區域隨選的分區下拉選單
- **THEN** 選單只列出座位制票種對應的分區代碼，不包含任何純計數票種；點選「自動選位並送出訂單」時，抽選候選座位集合 MUST NOT 包含任何純計數票種

#### Scenario: 使用區域隨選時一併送出已輸入的計數購買
- **WHEN** 買家已在計數購票區塊輸入購買數量（尚未送出），接著使用區域隨選選擇分區與張數並點選「自動選位並送出訂單」
- **THEN** 系統將區域隨選抽出的座位與已輸入的計數購買數量合併於同一次下單請求送出，成功後導向該筆訂單的訂單結果頁

### Requirement: 買家可在下單結果頁確認或取消剛下的訂單
系統 SHALL 在下單成功導向的訂單結果頁，直接使用下單當下取得的訂單 Id 提供確認、取消操作入口，呼叫既有確認／取消訂單 API。此頁面顯示的內容僅來自下單當下的回應與前端本地暫存狀態，不透過任何查詢 API 取得訂單目前狀態——買家專屬的訂單查詢 API 尚未存在（見下一個 Requirement 與 design.md Non-Goals）。持有到期時間 SHALL 以下單當下時間加上固定 10 分鐘推算顯示（查證後確認下單 API 的成功回應只有訂單 Id，沒有持有到期時間欄位，10 分鐘對照後端 `CreateOrderHandler.HoldDuration` 常數，見 design.md）。

#### Scenario: 在訂單結果頁確認訂單
- **WHEN** 買家在下單成功後導向的訂單結果頁點選「確認訂單」
- **THEN** 系統呼叫確認訂單 API，成功後畫面顯示「已確認」

#### Scenario: 在訂單結果頁取消訂單
- **WHEN** 買家在下單成功後導向的訂單結果頁點選「取消訂單」
- **THEN** 系統呼叫取消訂單 API，成功後畫面顯示「已取消」

### Requirement: 「我的訂單」列表與明細頁串接查詢 API，顯示訂單、票券狀態與 QR Code
系統 SHALL 提供「我的訂單」列表頁與訂單明細頁，呼叫新增的 `buyer-order-query` 能力查詢自己的訂單列表與明細。列表頁與明細頁 SHALL 顯示每筆訂單的狀態；持有到期時間（`HeldUntilUtc`）僅在訂單狀態為 Pending 時 SHALL 顯示為「保留至 {時間}」提示，訂單狀態為 Paid、Cancelled 或 Expired（終態或已逾時）時 MUST NOT 顯示此欄位——`HeldUntilUtc` 是建立訂單當下設定的原始值，不因訂單轉為終態而清空或重新賦值（比照既有 `buyer-order-query` 能力對此欄位的定義），對終態訂單顯示原值會誤導買家以為訂單仍在保留中。明細頁 SHALL 顯示訂單狀態、每筆項目對應的票券清單與各自狀態（`Issued`／`Redeemed`）。狀態為 `Issued` 或 `Redeemed` 的票券，明細頁 SHALL 提供「查看 QR Code」操作，點選後顯示該票券的 QR Code 圖檔；圖檔 MUST 透過既有 API 攔截器（帶 Authorization Header）取得後以 Blob／Object URL 顯示，MUST NOT 直接將 `<img src>` 指向需要驗證的端點網址。訂單內項目尚未出票（例如訂單仍為 Pending）時，該項目 SHALL 顯示「尚未出票」，不顯示 QR Code 操作。`Ticket.Voided` 狀態依既有 `ticket-issuance` 能力規格現況無任何觸發路徑，本次前端 MUST NOT 為 `Voided` 實作任何顯示邏輯（不在本次 UI 行為範圍內）；待未來新增 `Voided` 觸發路徑的提案時，須一併規劃對應的前端顯示行為。

#### Scenario: 開啟我的訂單列表頁
- **WHEN** 已登入買家開啟「我的訂單」頁面
- **THEN** 系統呼叫訂單列表 API，顯示自己所有訂單的狀態；狀態為 Pending 的訂單額外顯示「保留至 {時間}」，其他狀態不顯示持有到期時間；尚無任何訂單時顯示空清單提示，不視為錯誤

#### Scenario: 開啟訂單明細頁查看已出票訂單
- **WHEN** 已登入買家從列表點入一筆已確認付款、已出票的訂單明細
- **THEN** 系統呼叫訂單明細 API，顯示訂單狀態（不顯示持有到期時間，因訂單已為 Paid 終態）與每筆項目對應的票券清單，狀態為 `Issued` 的票券顯示「查看 QR Code」操作

#### Scenario: 點選查看 QR Code
- **WHEN** 買家在訂單明細頁對一張 `Issued` 或 `Redeemed` 狀態的票券點選「查看 QR Code」
- **THEN** 系統透過帶 Authorization Header 的請求取得 QR Code 圖檔，以 Blob／Object URL 顯示在畫面上

#### Scenario: 開啟尚未出票訂單的明細頁
- **WHEN** 已登入買家開啟一筆狀態為 Pending、尚未出票的訂單明細頁
- **THEN** 系統顯示訂單狀態與「保留至 {時間}」，訂單內每筆項目顯示「尚未出票」，不提供「查看 QR Code」操作

#### Scenario: 直接以網址開啟不存在的訂單明細頁
- **WHEN** 使用者直接開啟一個不存在的訂單 Id 的明細頁網址
- **THEN** 訂單明細 API 回應 404，系統顯示「找不到這筆訂單」提示與返回「我的訂單」列表的操作，不顯示任何訂單資料

#### Scenario: 直接以網址開啟非本人的訂單明細頁
- **WHEN** 已登入買家直接開啟非自己所屬訂單的明細頁網址
- **THEN** 訂單明細 API 回應 403，系統顯示「你沒有權限查看這筆訂單」提示與返回「我的訂單」列表的操作，不顯示任何訂單資料

### Requirement: Access Token 過期時前端自動換發，換發失敗導回登入頁
系統 SHALL 在呼叫 API 收到權杖過期（401）回應時，自動使用 Refresh Token 換發一次新的 Access Token 並重試原請求；若換發本身也失敗，系統 SHALL 清除登入狀態並導向登入頁。

#### Scenario: Access Token 過期但可成功換發
- **WHEN** 買家操作觸發的 API 呼叫因 Access Token 過期回傳 401，且 Refresh Token 仍有效
- **THEN** 系統自動換發新 Access Token 並重試原請求，使用者無感知中斷

#### Scenario: Refresh Token 也已失效
- **WHEN** 系統嘗試以 Refresh Token 換發時，換發本身也失敗
- **THEN** 系統清除登入狀態並導向登入頁
