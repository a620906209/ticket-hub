## Requirements
### Requirement: 未登入使用者存取需登入頁面或執行需登入操作時導向登入頁
系統 SHALL 在使用者嘗試存取需要登入的買家頁面（我的訂單、下單結果頁）或在公開頁面上執行需要登入的操作（活動詳情頁選位）但尚未登入時，導向登入頁；登入成功後 SHALL 導回原本嘗試存取的頁面。活動列表頁與活動詳情頁本身（含座位圖瀏覽）不需要登入即可瀏覽——只有「選位」這個動作本身才觸發導向登入頁，不是進入活動詳情頁就要求登入。

#### Scenario: 未登入直接進入我的訂單頁
- **WHEN** 未登入的使用者直接開啟「我的訂單」頁面網址
- **THEN** 系統導向登入頁

#### Scenario: 未登入在活動詳情頁點選座位
- **WHEN** 未登入的使用者在活動詳情頁點選任一座位（不論該座位是否為 Available 狀態）
- **THEN** 系統導向登入頁，不進行任何選位動作

#### Scenario: 登入成功後導回原頁面
- **WHEN** 使用者因未登入被導向登入頁，登入成功
- **THEN** 系統導回使用者原本嘗試存取的頁面（例如導回原本瀏覽的活動詳情頁，可繼續選位）

### Requirement: 買家可透過介面註冊與登入
系統 SHALL 提供註冊頁與登入頁，呼叫既有 `member-management`／`authentication` API 完成會員註冊與登入；登入成功後 SHALL 將角色為一般會員者導向買家端首頁。登入 API 因請求頻率限制拒絕（`429 Too Many Requests`）而失敗時，系統 SHALL 顯示友善提示訊息（例如「登入嘗試過於頻繁，請稍後再試」），不得直接顯示後端回應的原始 `ProblemDetails.title` 字串（例如 `"TooManyRequests"`），不套用「登入失敗顯示錯誤訊息」情境的一般錯誤處理。**註冊頁與登入頁 SHALL 各自顯示驗證碼圖片與輸入欄位（呼叫 `GET /api/captcha` 取得），送出註冊或登入請求時 MUST 一併附帶取得的 token 與使用者填寫的驗證碼文字。驗證碼相關的圖片載入、刷新與輸入欄位管理 SHALL 透過共用元件（`useCaptcha` composable）實作，不在註冊頁與登入頁各自重複實作。任一頁面因驗證碼錯誤而被後端拒絕時，系統 SHALL 顯示驗證碼錯誤的提示訊息、自動呼叫 `GET /api/captcha` 換取新圖片並清空舊有輸入，不沿用已失效的舊 token 再次嘗試送出。無論是頁面初次載入、使用者手動刷新，或前述答錯後自動換發，只要該次 `GET /api/captcha` 呼叫本身失敗（`429` 或 `5xx`），系統 SHALL 顯示「系統暫時無法取得驗證碼，請稍後再試」提示、停用送出按鈕直到成功取得有效驗證碼為止，並提供可再次觸發取得驗證碼的操作，不得讓使用者在沒有有效 token 的情況下送出請求。**

#### Scenario: 註冊成功
- **WHEN** 使用者在註冊頁填寫有效的 Email／密碼，並填寫正確的驗證碼後送出
- **THEN** 系統呼叫註冊 API 成功後導向登入頁

#### Scenario: 登入成功導向買家端首頁
- **WHEN** 一般會員在登入頁輸入正確帳密與正確的驗證碼送出
- **THEN** 系統登入成功並導向買家端活動列表首頁

#### Scenario: 登入失敗顯示錯誤訊息
- **WHEN** 使用者輸入錯誤密碼（驗證碼正確）送出登入
- **THEN** 系統顯示登入失敗的錯誤訊息，停留在登入頁

#### Scenario: LRL-009 登入因請求頻率限制被拒絕
- **WHEN** 使用者送出登入請求，後端因該來源 IP 已超過請求頻率限制而回傳 `429 Too Many Requests`
- **THEN** 系統顯示「登入嘗試過於頻繁，請稍後再試」的友善提示訊息，不顯示原始 `title` 字串，停留在登入頁

#### Scenario: CAPTCHA-BW-001 註冊頁載入時顯示驗證碼圖片
- **WHEN** 使用者開啟註冊頁
- **THEN** 系統呼叫 `GET /api/captcha` 並顯示驗證碼圖片與輸入欄位

#### Scenario: CAPTCHA-BW-002 驗證碼錯誤被拒絕後自動換發新驗證碼
- **WHEN** 使用者在註冊頁或登入頁填寫錯誤的驗證碼並送出，後端回傳驗證碼錯誤
- **THEN** 系統顯示驗證碼錯誤的提示訊息，自動呼叫 `GET /api/captcha` 顯示新的驗證碼圖片，清空舊有的驗證碼輸入欄位，不得沿用已失效的舊 token 再次送出

#### Scenario: CAPTCHA-BW-003 使用者可手動刷新驗證碼圖片
- **WHEN** 使用者在註冊頁或登入頁點選驗證碼圖片旁的刷新操作
- **THEN** 系統重新呼叫 `GET /api/captcha` 取得新的 token 與圖片，取代畫面上原有的驗證碼

#### Scenario: CAPTCHA-BW-004 登入頁載入時顯示驗證碼圖片
- **WHEN** 使用者開啟登入頁
- **THEN** 系統呼叫 `GET /api/captcha` 並顯示驗證碼圖片與輸入欄位

#### Scenario: CAPTCHA-BW-005 初次載入驗證碼失敗
- **WHEN** 使用者開啟註冊頁或登入頁，`GET /api/captcha` 呼叫失敗（`429` 或 `5xx`）
- **THEN** 系統顯示「系統暫時無法取得驗證碼，請稍後再試」提示，停用送出按鈕，提供可再次觸發取得驗證碼的操作

#### Scenario: CAPTCHA-BW-006 手動或自動刷新驗證碼失敗
- **WHEN** 使用者在註冊頁或登入頁點選刷新，或系統於驗證碼錯誤後自動呼叫 `GET /api/captcha` 換新，該次呼叫失敗（`429` 或 `5xx`）
- **THEN** 系統顯示「系統暫時無法取得驗證碼，請稍後再試」提示，停用送出按鈕直到下一次成功取得新驗證碼，不清空表單其他已填欄位

### Requirement: 買家可瀏覽活動列表與座位可售狀態
系統 SHALL 提供活動列表頁與活動詳情頁，呼叫既有 `event-catalog`／`ticket-purchase` API 顯示活動基本資訊與座位可售狀態（Available／Held／Sold），不需要登入即可瀏覽。活動詳情頁 SHALL 並排顯示活動資訊（含海報圖片與說明文字，若 Admin 建立活動時有填寫）與座位選擇區；座位依分區分組顯示。座位可售狀態（Available／Held／Sold）為頁面載入或手動重新整理當下查詢 API 取得的結果，非伺服器推播的即時更新（本輪不引入 WebSocket／SignalR），此部分不受本節下述快取異動影響（`ticket-purchase`「瀏覽活動與座位可售狀態」能力的座位查詢端點不在 `query-caching` 能力的快取範圍內）。**活動基本資訊（包含 `IsQueueModeEnabled`）呼叫的 `GET /api/events` 端點，自 `query-caching` 能力起可能回傳快取內容，落後資料庫實際值的時間不超過該能力定義的 TTL 上限（`EventListTtlSeconds`，預設 30 秒）；這不改變本頁「頁面載入或手動重新整理當下取得結果」的既有行為模式（前端仍是每次載入即發起一次查詢，只是該次查詢在後端可能命中快取），只是該次查詢結果本身可能不是資料庫當下的絕對最新值。**

#### Scenario: 瀏覽活動列表
- **WHEN** 使用者開啟活動列表頁
- **THEN** 系統以卡片格線顯示目前所有活動的基本資訊；此資訊可能是 `query-caching` 能力的快取內容，落後時間不超過該能力定義的 TTL 上限

#### Scenario: 查看活動座位狀態
- **WHEN** 使用者點選某活動進入詳情頁
- **THEN** 系統顯示該活動的資訊（含海報／說明，如有設定）與座位圖，座位依分區分組、每個座位標示目前的可售狀態

#### Scenario: 活動未設定海報或說明
- **WHEN** Admin 建立活動時沒有填寫海報網址或說明
- **THEN** 系統不顯示海報圖片區塊或說明文字區塊，不顯示空白佔位或錯誤訊息

### Requirement: 買家可選位並送出訂單
系統 SHALL 在活動詳情頁提供座位選擇與下單操作，呼叫既有 `ticket-purchase` 下單 API；下單成功後 SHALL 導向訂單結果頁，顯示訂單 Id 與持有到期時間。活動可由 Admin 設定「每筆訂單限購張數」（選填，未設定代表不限制）；當已選座位數加上已輸入的純計數票種購買數量總和達到上限時，系統 SHALL 阻止再選新座位或增加計數購買數量，直到取消已選座位或降低計數數量釋出額度。座位選購與計數購買輸入的阻止方式不同：點選座位被阻止時 SHALL 顯示提示訊息（比照既有座位選購的既定行為，見「已選座位數達到每筆訂單限購張數」Scenario）；計數購買數量輸入則採限制型互動，由輸入元件本身限制數值上限、不接受超過限購的輸入，不另外顯示提示訊息或呈現為錯誤狀態（見「純計數購買數量達到每筆訂單限購張數」Scenario，與可售總量的限制型互動一致）。此限制前端會提前檢查並提示，但**後端 `PlaceOrder` API 才是最終把關**——前端檢查被繞過或跟後端資料不同步時，後端仍會拒絕超過上限的下單請求。

活動詳情頁 SHALL 對 `RequiresSeat = false` 的純計數票種，於獨立的「計數購票」區塊顯示票種名稱、票價、當下可售總量，並提供購買數量輸入（非負整數，0 代表不購買）；此區塊與既有座位選購區塊（僅列出 `RequiresSeat = true` 的票種）並列顯示，互不影響彼此的選購狀態。計數購買操作比照既有座位選位規則，視為需登入才能執行的操作：未登入時嘗試調整任一計數票種的購買數量（含直接輸入、增減按鈕等任何互動方式），系統 SHALL 立即導向登入頁，不套用該次數量變更；登入成功後 SHALL 導回原頁面，比照既有座位選位「登入後可繼續選位」的既定行為，不特別還原導向登入前嘗試輸入的數值——因為攔截發生在數值套用之前，本來就沒有暫存值需要還原。

單一計數票種的購買數量輸入元件 SHALL 將可輸入上限設為「該票種當下可售總量」與「限購剩餘額度（`maxTicketsPerOrder` 扣除已選座位數、扣除其他計數票種已輸入數量、加回自己目前輸入值後的結果）」兩者中較小值，並由元件本身限制輸入不得超過此上限——超過上限的輸入 SHALL 被限制、不接受，不呈現為錯誤狀態（限制型輸入控制，元件不允許出現暫時性的超額顯示值，與下方「計數輸入元件限制數量不得超過可售總量」Scenario 一致）；此限制與既有「區域隨選」的雙重限制計算方式一致，兩者共用同一份剩餘額度，任一方消耗額度後 SHALL 立即反映到另一方可輸入/可抽選的上限。數量為 0 的計數票種 SHALL 視為未選購，送出訂單時 MUST NOT 包含在下單請求的選購項目中。

送出訂單時，座位選購項目與計數購買項目（數量大於 0 者）SHALL 合併於同一次下單請求送出，呼叫既有支援混合項目的下單 API；座位項目送出時不帶購買數量（後端預設視為 1，維持既有行為），計數項目送出對應的 `TicketTypeId` 與購買數量、不帶座位 Id。送出前系統 MUST 重新加總座位數與計數購買總量，超過限購張數時 MUST 擋下、顯示提示訊息、不呼叫下單 API——不得僅依賴各輸入元件的上限屬性作為唯一防線（例如買家在其中一個輸入框調整上限生效前，已在另一個輸入框填入超額數值的情況）。

下單 API 呼叫失敗時，若為 401（換發失敗），系統 SHALL 直接導向登入頁（比照既有座位選位的登入要求），不顯示下單失敗訊息、不套用下方的清空/刷新處理——活動詳情頁為公開頁，既有全域換發/登入導頁機制僅在需要登入的路由才會生效，不會處理公開頁上的登入失效，此元件 MUST 自行攔截 401 並導頁。除 401 與本 Requirement 另行列出的例外（`403 QueueAdmissionRequired`、`429`、`409 SalesNotOpen`／`SalesClosed`）以外的其他下單失敗（座位已被搶先鎖定、計數票種可售總量於送出當下已被其他買家買光、或後端其他驗證失敗），系統 SHALL 一律顯示錯誤訊息、清空目前已選座位與已輸入的計數購買數量、並重新呼叫查詢 API 刷新座位與票種資料——比照既有座位選購失敗時的既定處理，除上述明列例外外，不依失敗原因做差異化處理（維持既有行為單純、一致，明列例外以外不新增依錯誤類型分流的重試或保留輸入邏輯）。

活動是否處於熱門搶購模式，前端 SHALL 直接讀取活動列表查詢 API（`GET /api/events`，`ticket-purchase`「瀏覽活動與座位可售狀態」能力）回應中的 `IsQueueModeEnabled` 欄位判斷，不需另外呼叫其他端點確認。若活動處於熱門搶購模式（`IsQueueModeEnabled = true`），買家進入活動詳情頁的選位/計數購票操作前，系統 SHALL 先呼叫排隊狀態查詢 API：**尚未加入排隊時 SHALL 顯示驗證碼圖片與輸入欄位（呼叫 `GET /api/captcha` 取得），提供加入排隊的操作，加入排隊時 MUST 一併附帶取得的 token 與使用者填寫的驗證碼文字；驗證碼相關元件沿用「買家可透過介面註冊與登入」能力所述的共用 `useCaptcha` composable，不重複實作；加入排隊因驗證碼錯誤被拒絕時，系統 SHALL 顯示驗證碼錯誤提示、自動換發新驗證碼、清空舊輸入，停留在尚未加入排隊的畫面，不清空/重新整理座位與票種資料（與此操作無關）；此處驗證碼圖片載入、刷新失敗時的處理沿用「買家可透過介面註冊與登入」能力所述的共用行為（顯示「系統暫時無法取得驗證碼，請稍後再試」、停用加入排隊按鈕、提供重試操作），不重複定義**；已加入且狀態為 `Waiting` 時 SHALL 顯示排隊等待畫面（含前方等待人數），停用座位選擇、計數購買輸入與區域隨選快速下單的操作入口，並以固定間隔定期輪詢排隊狀態查詢 API（輪詢間隔為可設定值，與後端 `PurchaseQueueOptions.PollingInterval` 同數量級，避免輪詢過於頻繁造成負擔或過於稀疏造成畫面更新明顯延遲）；每次輪詢回應除排隊紀錄狀態外，SHALL 一併包含該活動當下的 `queueModeEnabled`（見 `purchase-queue`「買家可查詢自己的排隊狀態」能力），不需另外呼叫活動列表 API 確認——若某次輪詢回應的 `queueModeEnabled` 為 `false`（Admin 已於買家等待期間關閉熱門搶購模式），系統 SHALL 停止輪詢、關閉排隊等待畫面，開放選位/計數購買、區域隨選與送出訂單操作，比照該活動從未開啟熱門搶購模式的一般行為。狀態轉為 `Admitted` 時 SHALL 停止輪詢、關閉排隊等待畫面，開放選位/計數購買、區域隨選與送出訂單操作。下單 API 回傳 `403 Forbidden` 且 `ProblemDetails.title === "QueueAdmissionRequired"`（排隊資格不足：未入場或已逾時）而失敗時，系統 SHALL 顯示提示訊息並導回排隊等待畫面重新查詢狀態，不套用「其他下單失敗」一般情形的清空/刷新處理（此情形不代表座位或庫存資料有變動）；前端 MUST 同時檢查 `status` 與 `title` 兩者才視為排隊資格不足，不得只依 HTTP 403 狀態碼判斷——其他業務語意的 403（例如既有「非本人操作」情境）SHALL 沿用一般授權錯誤處理，不導向排隊等待畫面。下單 API 因超過請求頻率限制（429）而失敗時，系統 SHALL 顯示「請稍後再試」的提示訊息，不清空已選座位與已輸入的計數購買數量、不重新整理座位與票種資料——此情形代表發送速度過快，而非資料已變動，維持買家目前已選內容供其等待後直接重試。下單 API 回傳 `409 Conflict` 且 `ProblemDetails.title` 為 `SalesNotOpen` 或 `SalesClosed`（販售期間外）而失敗時，系統 SHALL 依「活動頁依販售期間顯示狀態並限制購票操作」能力處理：顯示對應中文訊息，不清空已選座位與已輸入的計數購買數量、不重新整理座位與票種資料——後端在檢查販售期間時尚未鎖定任何座位或庫存，選擇仍然有效；前端 MUST 同時檢查 `status` 與 `title`，其他 409 沿用一般失敗處理。

#### Scenario: BW-ORDER-001 選擇可售座位並成功下單
- **WHEN** 已登入買家在活動詳情頁選擇一個或多個 Available 狀態的座位並送出下單
- **THEN** 系統呼叫下單 API 成功，導向該筆訂單的訂單結果頁

#### Scenario: BW-ORDER-002 下單時座位已被搶先鎖定
- **WHEN** 買家送出下單時，其中一個座位已被其他訂單鎖定或售出（API 回傳失敗）
- **THEN** 系統顯示下單失敗的錯誤訊息，清空目前已選座位與已輸入的計數購買數量，重新呼叫查詢 API 刷新座位與票種資料，不導向訂單結果頁

#### Scenario: BW-ORDER-003 送出訂單時登入狀態已失效（401）
- **WHEN** 買家送出下單時，Access Token 已過期且換發也失敗，下單 API 回傳 401
- **THEN** 系統直接導向登入頁，不顯示下單失敗訊息，不套用清空已選座位/計數輸入與重新整理資料的處理

#### Scenario: BW-ORDER-004 已選座位數達到每筆訂單限購張數
- **WHEN** 買家在已選座位數（含已輸入的計數購買數量總和）等於活動設定的限購張數時，再點選一個新的 Available 座位
- **THEN** 系統顯示「已達每筆訂單限購張數」的提示訊息，不將新座位加入已選清單

#### Scenario: BW-ORDER-005 活動未設定限購張數
- **WHEN** 活動的每筆訂單限購張數為未設定（不限制）
- **THEN** 買家可以選擇任意數量的 Available 座位，不受張數限制

#### Scenario: BW-ORDER-006 未登入嘗試調整計數購買數量
- **WHEN** 未登入的使用者嘗試調整任一純計數票種的購買數量（直接輸入或使用增減按鈕）
- **THEN** 系統立即導向登入頁，不套用該次數量變更；登入成功後導回原頁面，該票種購買數量維持 0

#### Scenario: BW-ORDER-007 純計數票種輸入購買數量並成功下單
- **WHEN** 已登入買家在活動詳情頁的計數購票區塊，對一個 `RequiresSeat = false` 的票種輸入購買數量（不超過當下可售總量與限購剩餘額度）並送出訂單
- **THEN** 系統呼叫下單 API 成功（該筆選購項目不含座位 Id），導向該筆訂單的訂單結果頁

#### Scenario: BW-ORDER-008 混合座位選購與純計數購買並成功下單
- **WHEN** 已登入買家同時選擇一個或多個座位，並對一個純計數票種輸入購買數量，送出下單
- **THEN** 系統將座位項目與計數項目合併於同一次下單請求送出，成功後導向該筆訂單的訂單結果頁

#### Scenario: BW-ORDER-009 純計數購買數量達到每筆訂單限購張數
- **WHEN** 買家輸入的計數購買數量（加上已選座位數）達到活動設定的限購張數，嘗試再增加計數購買數量
- **THEN** 計數輸入元件限制數值不得超過剩餘額度，不接受超過限購的輸入，不呈現為錯誤狀態（限制型，與「計數輸入元件限制數量不得超過可售總量」Scenario 一致的互動模式；已選座位數達到限購張數後再嘗試選新座位，仍依「已選座位數達到每筆訂單限購張數」Scenario 顯示提示訊息——座位選購走點選互動，不是連續數量輸入，兩種介面元件的既定回饋方式不同）

#### Scenario: BW-ORDER-010 計數輸入元件限制數量不得超過可售總量
- **WHEN** 買家嘗試在計數輸入框以直接輸入或增減按鈕，調整超過該票種當下可售總量的數值
- **THEN** 輸入元件限制數值不得超過可售總量上限，不接受超額輸入，不呈現為錯誤狀態

#### Scenario: BW-ORDER-011 送出時因庫存已變動被後端拒絕
- **WHEN** 買家在前端檢查通過的情況下送出訂單，但送出當下某計數票種的可售總量已因其他買家搶購而變動，後端拒絕本次購買
- **THEN** 系統顯示下單失敗訊息，清空目前已選座位與已輸入的計數購買數量，並重新整理票種與座位資料（比照「下單時座位已被搶先鎖定」的統一失敗處理）

#### Scenario: BW-ORDER-012 純計數票種可售總量為 0
- **WHEN** 某純計數票種當下的可售總量為 0
- **THEN** 該票種的購買數量輸入框上限為 0、無法輸入大於 0 的數量，介面顯示「已售完」提示，不視為錯誤狀態、不顯示錯誤訊息樣式

#### Scenario: BW-ORDER-013 活動未設定限購張數時的純計數購買
- **WHEN** 活動的每筆訂單限購張數為未設定（不限制），買家對某純計數票種輸入購買數量
- **THEN** 該票種的購買數量輸入僅受當下可售總量限制，不受限購張數限制

#### Scenario: BW-ORDER-014 計數購買數量為 0 時不送出對應項目
- **WHEN** 買家在計數購票區塊對某票種維持購買數量為 0（未輸入或清空），對其他票種正常選購並送出訂單
- **THEN** 下單請求的選購項目 MUST NOT 包含該數量為 0 的票種

#### Scenario: BW-ORDER-015 送出訂單前偵測到合併總數超過限購張數
- **WHEN** 買家透過分別在座位網格與計數輸入框操作，使已選座位數與計數購買總量的加總超過活動設定的限購張數（例如個別輸入當下未觸發即時提示，但送出當下加總已超過）
- **THEN** 系統在呼叫下單 API 之前偵測到總數超過限購張數，擋下送出、顯示提示訊息，不呼叫下單 API

#### Scenario: BW-ORDER-016 已手動選取座位佔用額度後，計數購買輸入上限隨之減少
- **WHEN** 買家已在座位網格手動選取座位、佔用部分限購額度（尚未送出訂單），接著要在計數購票區塊輸入購買數量
- **THEN** 該計數票種輸入框當下可輸入的上限 SHALL 扣除已選座位數後重新計算，不允許輸入超過剩餘額度的數量

#### Scenario: BW-QUEUE-001 進入熱門搶購模式活動且尚未加入排隊
- **WHEN** 已登入買家進入 `IsQueueModeEnabled = true` 的活動詳情頁，且尚未加入該活動的排隊
- **THEN** 系統顯示驗證碼圖片、輸入欄位與加入排隊的操作，不開放選位/計數購買輸入

#### Scenario: BW-QUEUE-002 排隊中顯示等待畫面並輪詢狀態
- **WHEN** 已登入買家已加入排隊，狀態為 `Waiting`
- **THEN** 系統顯示排隊等待畫面與目前前方等待人數，停用座位選擇、計數購買輸入與區域隨選快速下單的操作入口，並定期輪詢排隊狀態

#### Scenario: BW-QUEUE-003 排隊入場後開放選位與下單
- **WHEN** 買家的排隊狀態由 `Waiting` 轉為 `Admitted`
- **THEN** 系統停止輪詢、關閉排隊等待畫面，開放座位選擇、計數購買輸入、區域隨選快速下單與送出訂單操作

#### Scenario: BW-QUEUE-004 下單時排隊資格已逾時
- **WHEN** 買家送出下單時，其排隊資格已逾時或不存在，下單 API 回傳 `403 Forbidden` 且 `title === "QueueAdmissionRequired"`
- **THEN** 系統顯示提示訊息並導回排隊等待畫面重新查詢狀態，不清空座位/計數輸入、不比照一般失敗重新整理座位與票種資料

#### Scenario: BW-QUEUE-006 其他語意的 403 不視為排隊資格不足
- **WHEN** 買家送出下單時，下單 API 回傳 `403 Forbidden`，但 `title` 不是 `"QueueAdmissionRequired"`（例如既有其他業務語意的 403）
- **THEN** 系統 SHALL 沿用一般授權錯誤處理，不導向排隊等待畫面、不誤判為排隊資格不足

#### Scenario: BW-QUEUE-005 下單因請求頻率限制被拒絕
- **WHEN** 買家送出下單時，下單 API 回傳 429（請求頻率限制）
- **THEN** 系統顯示「請稍後再試」提示訊息，不清空已選座位與已輸入的計數購買數量，不重新整理座位與票種資料

#### Scenario: BW-TOGGLE-001 排隊等待期間 Queue Mode 被關閉
- **WHEN** 買家在排隊等待畫面（`Waiting`）停留期間，Admin 將該活動的熱門搶購模式關閉，前端下一次輪詢排隊狀態查詢 API 回應中的 `queueModeEnabled` 已為 `false`
- **THEN** 系統停止輪詢、關閉排隊等待畫面，開放座位選擇、計數購買輸入、區域隨選與送出訂單操作，比照該活動從未開啟熱門搶購模式的一般行為，不要求買家等到原本的 `Admitted`、不誤導買家以為仍需排隊

#### Scenario: CAPTCHA-BW-QUEUE-001 加入排隊時顯示驗證碼圖片
- **WHEN** 已登入買家進入 `IsQueueModeEnabled = true` 的活動詳情頁，且尚未加入該活動的排隊
- **THEN** 系統呼叫 `GET /api/captcha` 並顯示驗證碼圖片與輸入欄位，加入排隊操作 MUST 隨請求附帶取得的 token 與使用者填寫的文字

#### Scenario: CAPTCHA-BW-QUEUE-002 加入排隊時驗證碼錯誤
- **WHEN** 買家在尚未加入排隊的畫面填寫錯誤的驗證碼並送出加入排隊
- **THEN** 系統顯示驗證碼錯誤提示，自動呼叫 `GET /api/captcha` 換取新驗證碼、清空舊輸入，停留在尚未加入排隊的畫面，不開放選位/計數購買輸入

### Requirement: 買家可用區域隨選快速下單，不必逐一手動點選座位或另外按送出
系統 SHALL 在活動詳情頁的選位區提供「區域隨選」功能：買家選擇一個分區（或「全部區域」）與想購買的張數，點選「自動選位並送出訂單」後，系統 SHALL 從符合條件、目前 Available 且尚未被選取的座位中**隨機**抽出對應數量，加入已選清單後**直接呼叫下單 API 送出訂單**——買家不需要再另外滾動頁面、點擊底部的「送出訂單」按鈕確認一次。此功能的隨機抽選對象僅限座位選購：分區下拉選單的選項來源 SHALL 僅列出目前有 `RequiresSeat = true` 票種對應座位的分區代碼，純計數票種沒有對應座位、不會出現在此下拉選單中，抽選候選座位集合 MUST NOT 包含任何純計數票種。但送出訂單這一步驟與「計數購票」區塊共用同一次下單請求——若買家在使用區域隨選之前已在計數購票區塊輸入購買數量（尚未送出），區域隨選送出時 SHALL 將這些已輸入的計數購買數量一併合併送出，不需要買家分開送出兩次訂單，行為與「買家可選位並送出訂單」需求中座位與計數項目合併送出的規則一致。分區下拉選單 SHALL 預設為「全部區域」；選擇「全部區域」時，抽選池 SHALL 涵蓋所有座位制分區的可售座位，不限定單一分區、也不含計數制票種。買家指定的自動選位張數 MUST NOT 超過「符合條件的可售座位數」與「每筆訂單限購張數的剩餘額度」兩者中較小值；超過時系統 MUST 顯示錯誤訊息、不加入任何座位、不呼叫下單 API（不得將張數靜默縮減為實際可抽取的數量後直接送出——買家要求的張數與實際送出訂單的張數必須一致）。此剩餘額度計算 SHALL 扣除已選座位數與已輸入的純計數票種購買數量總和；未登入時點選此按鈕的行為 SHALL 與點選單一座位一致，導向登入頁、不進行任何選位或下單動作。

#### Scenario: 全部區域隨機選位並直接送出訂單
- **WHEN** 已登入買家維持預設的「全部區域」、輸入張數（不超過可售座位數與限購剩餘額度），點選「自動選位並送出訂單」
- **THEN** 系統從所有分區的可售座位中隨機抽出對應數量、呼叫下單 API，成功後直接導向該筆訂單的訂單結果頁，不需要買家再手動點其他按鈕

#### Scenario: 指定單一分區隨機選位並直接送出訂單
- **WHEN** 已登入買家改選特定分區與張數，點選「自動選位並送出訂單」
- **THEN** 系統只從該分區的可售座位中隨機抽出對應數量並直接送出訂單

#### Scenario: 區域隨選張數超過可售座位或限購剩餘額度
- **WHEN** 買家指定的張數超過符合條件的可售座位數，或超過每筆訂單限購張數的剩餘額度
- **THEN** 系統顯示對應的錯誤訊息，不加入任何座位、不呼叫下單 API

#### Scenario: 未登入使用區域隨選
- **WHEN** 未登入的使用者選擇分區（或維持全部區域）與張數並點選「自動選位並送出訂單」
- **THEN** 系統導向登入頁，不進行任何選位或下單動作

#### Scenario: 已輸入純計數購買數量時，區域隨選的剩餘額度隨之減少
- **WHEN** 買家已在計數購票區塊輸入購買數量（尚未送出訂單），接著使用區域隨選輸入張數
- **THEN** 區域隨選的剩餘額度計算 SHALL 扣除已輸入的計數購買數量，超過扣除後的剩餘額度時顯示錯誤訊息、不加入任何座位

#### Scenario: 純計數票種不會出現在區域隨選的分區選單與抽選池中
- **WHEN** 活動同時存在座位制與純計數票種，買家開啟區域隨選的分區下拉選單
- **THEN** 選單只列出座位制票種對應的分區代碼，不包含任何純計數票種；點選「自動選位並送出訂單」時，抽選候選座位集合 MUST NOT 包含任何純計數票種

#### Scenario: 使用區域隨選時一併送出已輸入的計數購買
- **WHEN** 買家已在計數購票區塊輸入購買數量（尚未送出），接著使用區域隨選選擇分區與張數並點選「自動選位並送出訂單」
- **THEN** 系統將區域隨選抽出的座位與已輸入的計數購買數量合併於同一次下單請求送出，成功後導向該筆訂單的訂單結果頁

### Requirement: 買家可在下單結果頁確認或取消剛下的訂單
系統 SHALL 在下單成功導向的訂單結果頁，以下單當下取得的訂單 Id 呼叫 `buyer-order-query` 能力的訂單明細 API，取得訂單目前狀態與伺服器端持有到期時間（`HeldUntilUtc`）後，顯示訂單 Id、活動名稱與訂單狀態的中文標籤；MUST NOT 以前端本地狀態或前端自行推算的時間代替伺服器值（原「不透過查詢 API」與「以下單當下時間加 10 分鐘推算」的規定，是在買家訂單查詢 API 尚不存在時的權宜做法，本次廢止）。訂單目前狀態為 Pending 時，頁面 SHALL 提供「確認付款」「取消訂單」操作入口，呼叫既有確認／取消訂單 API，並顯示「保留至 {時間}」；狀態非 Pending 時 MUST NOT 顯示這兩個操作與持有到期時間。按鈕文字由既有「確認訂單」改為「確認付款」、成功後狀態文字由「已確認」改為「已付款」，與統一的訂單狀態中文標籤（Paid「已付款」）一致。「取消訂單」操作 SHALL 先顯示確認對話框（按鈕文字為「取消訂單」與「保留訂單」，MUST NOT 使用「確定」／「取消」），使用者選「保留訂單」或關閉對話框時 MUST NOT 呼叫取消訂單 API；「確認付款」不需確認對話框。操作成功時 SHALL 顯示簡短成功提示（「付款成功，票券已出票」／「訂單已取消」）。重新查詢期間 SHALL 保留目前畫面內容，不得先清空再重新顯示。確認或取消操作不論成功或失敗，系統 SHALL 重新查詢訂單明細並依伺服器回傳的狀態更新畫面；操作失敗時 SHALL 在重新查詢完成後顯示失敗訊息，不得被重新查詢流程清除。操作後的重新查詢本身失敗（網路錯誤、5xx、404、403）時，系統 SHALL 顯示錯誤訊息並提供「重新整理」操作，且 MUST NOT 再顯示「確認付款」「取消訂單」按鈕與「保留至 {時間}」——此時畫面內容可能已過時，不得讓使用者依過時狀態再次操作。確認或取消操作失敗、重新查詢後伺服器狀態仍為 Pending 時（例如付款被拒，確認訂單 API 回應 409，訂單不會因此轉為終態），SHALL 同時顯示失敗訊息、「保留至 {時間}」與「確認付款」「取消訂單」操作，允許買家再次嘗試。明細 API 回應 404 或 403 時，比照訂單明細頁顯示對應提示與返回「我的訂單」列表的操作，不顯示任何訂單資料、不提供確認付款或取消操作；網址中的訂單 Id 非 GUID 格式時，前端不另做格式檢查，由後端路由約束 `{id:guid}` 回應 404，依 404 處理。同一頁面切換至另一筆訂單時（例如瀏覽器上一頁／下一頁），系統 SHALL 以新訂單重新查詢，且較早送出的明細請求晚於較新請求回應時 MUST NOT 覆蓋畫面。

### Requirement: 「我的訂單」列表與明細頁串接查詢 API，顯示訂單、票券狀態與 QR Code

### Requirement: 買家可透過「實名資料」頁查看與登記實名
系統 SHALL 提供需登入的「實名資料」頁（未登入時依既有規則導向登入頁），並在買家端會員選單提供「實名資料」入口。頁面載入時 SHALL 呼叫查詢個人資料 API。

- **未登記**：顯示姓名與身分證末四碼輸入欄位，以及「登記後無法自行修改」的提示。
- **送出前確認**：按下送出時，系統 SHALL 先顯示確認對話框，內容重新列出使用者輸入的姓名與末四碼，按鈕文字為「確認登記」與「返回修改」。對話框開啟時預設焦點 MUST 在「返回修改」。選「返回修改」或關閉對話框時 MUST NOT 呼叫登記 API，已輸入的內容保留。
- **登記成功**：顯示成功提示，頁面改為唯讀的已登記狀態。
- **已登記**：唯讀顯示姓名與遮蔽後末四碼（API 回傳的 `nationalIdLast4Masked`），不提供任何輸入欄位或修改操作。
- **登記 API 回應 409**（例如另一個分頁已先登記）：系統 SHALL 重新查詢個人資料並顯示已登記狀態，同時提示「已登記過實名」。
- **登記 API 回應 400**：顯示格式錯誤提示，保留輸入內容。
- **前端格式提示**：前端 SHALL 對末四碼做格式提示（必須為 4 位數字），並在開啟確認對話框前以與後端相同的規則檢查姓名（去除前後空白後非空、長度、不可見字元、至少一個字母，見 real-name-verification spec 的 RealName 規則），不符時顯示提示且不開啟對話框；最終以後端驗證為準。
- **去除前後空白**：確認對話框顯示與送出登記 API 的姓名 SHALL 為去除前後空白後的值，與後端儲存值一致。
- **確認值固定**：確認對話框顯示與「確認登記」送出的值 SHALL 是開啟對話框當下通過檢查的值；對話框開著時改動輸入欄位不影響送出值，再次送出表單則先關閉對話框並重新檢查。
- **返回原頁**：頁面網址帶 `redirect` 參數，且其值以 `/` 開頭、不以 `//` 開頭時，登記成功後 SHALL 導回該路徑；其他情況留在本頁。
- **渲染方式**：姓名 MUST 以文字插值渲染，不得使用 `v-html`。

- **個人資料查詢失敗**：不顯示未登記提示，不影響購票操作。
- **未登入者**：只顯示「本活動需實名」標示。

### Requirement: 活動頁依販售期間顯示狀態並限制購票操作
前端 SHALL 依公開活動列表回傳的 `salesStartAtUtc`、`salesEndAtUtc`、`startAtUtc` 推導販售狀態，規則與後端一致（見 `event-management` 能力「建立活動時可指定販售期間，建立後不可變更」）：

- 實際販售期間為左閉右開區間 `[salesStartAtUtc, salesEndAtUtc ?? startAtUtc)`
- `salesStartAtUtc` 為 null 時沒有下界
- `salesStartAtUtc`、`salesEndAtUtc` 為 null 或欄位缺漏（`undefined`）時，皆視同未設定
- 當下時間早於開賣時間：「尚未開賣」
- 當下時間在期間內：「販售中」
- 當下時間等於或晚於實際停售時間：「已停售」

推導使用瀏覽器本機時鐘。後端下單與加入排隊的 409 判斷是最終把關，前端推導只用來提前提示與停用操作。

- **詳情頁顯示**：活動詳情頁 SHALL 顯示販售期間（開賣時間為 null 時顯示「即日起」，停售時間顯示實際停售時間）與販售狀態文字，不得只用顏色或圖示表示狀態。
- **期間外停用操作**：販售狀態不是「販售中」時，詳情頁 SHALL：
  - 不接受選位、計數數量輸入與快速選位；已登入者的快速選位控制項與計數輸入 SHALL 呈現停用狀態
  - 停用送出訂單按鈕
  - 不顯示加入排隊畫面，也不載入排隊驗證碼
  - 在購票區塊顯示狀態提示（呈現條件見下方「購票區塊販售提示」）
  - 座位圖仍顯示，供瀏覽
  - **未登入者**沿用既有行為：點選座位、調整計數數量或快速選位時導向登入頁（登入後回到本頁，再依販售狀態停用），不在前端額外攔截；未登入者的計數輸入與快速選位控制項 MUST NOT 呈現停用，否則無法觸發導向登入
  - **排隊等待中（Waiting）**的買家跨越停售時間時，沿用既有排隊等待畫面與輪詢，不顯示停售提示；放行後若已停售，購票操作依上述規則停用
- **購票區塊販售提示**：位於購票區塊最上方、既有「請先登入」提示之前，依下表呈現（「已停售」含伺服器判定）。排隊等待中（Waiting）一律不顯示。未登入者與已登入者規則相同。

  | 販售狀態 | 排隊等待中 | 其他情況 |
  | --- | --- | --- |
  | 尚未開賣 | （不會發生：未開賣不顯示加入排隊） | 「尚未開賣，將於 {開賣時間} 開放購票」 |
  | 販售中（載入時即為販售中） | 不顯示 | 不顯示 |
  | 販售中（停留期間由尚未開賣轉來） | 不顯示 | 「現在開放購票」（含熱門搶購活動的加入排隊畫面、放行後的購票畫面） |
  | 已停售 | 不顯示 | 「本活動已停售」 |

- **與既有 Scenario 的關係**：本能力既有的選位、下單、快速選位、加入排隊（含 `BW-QUEUE-*`、`CAPTCHA-BW-QUEUE-*`）Scenario，皆以活動處於「販售中」為前提
- **自動解鎖**：
  - 買家停留在詳情頁期間，販售狀態 SHALL 隨時間自動更新，不需重新整理頁面：開賣時間一到即恢復可購票操作，停售時間一到即停用。
  - 熱門搶購模式活動開賣時，SHALL 在此時才顯示加入排隊畫面並載入驗證碼。
  - 停留期間由「尚未開賣」轉為「販售中」時，原本的尚未開賣提示 SHALL 在同一位置改為「現在開放購票」，不得整塊移除造成下方內容位移；此提示持續顯示，直到離開本頁或狀態轉為「已停售」（此時改為「本活動已停售」），排隊等待中暫不顯示。熱門搶購活動同樣適用，提示位於加入排隊畫面上方，所有活動規則一致。
  - 分頁從背景切回前景時，SHALL 立即依當下時間重算狀態。
- **下單收到 409**：下單 API 回應 409 且 `Title` 為 `SalesNotOpen` 或 `SalesClosed` 時，系統 SHALL：
  - 顯示中文訊息（`SalesNotOpen`：「尚未開賣，請於開賣時間後再試」；`SalesClosed`：「本活動已停售」）
  - `SalesClosed` 的訊息由購票區的販售提示（轉為「本活動已停售」）顯示，MUST NOT 另以錯誤訊息重複顯示同一句；`SalesNotOpen` 不改變販售提示，以錯誤訊息顯示
  - MUST NOT 顯示後端回傳的英文 `detail`
  - MUST 保留已選座位（含快速選位抽出並加入已選清單的座位）與計數數量，不重新載入座位資料，不清空選擇
- **加入排隊收到 409**：加入排隊 API 回應 409 且 `Title` 為 `SalesNotOpen` 或 `SalesClosed` 時，系統 SHALL：
  - 顯示同樣的中文訊息，清空驗證碼輸入，不進入排隊等待畫面
  - `SalesNotOpen`：換發新的驗證碼（後端先核對驗證碼才檢查販售期間，驗證碼已被消耗；加入畫面仍顯示，供開賣後重試）
  - `SalesClosed`：頁面轉為已停售、加入畫面隱藏，MUST NOT 再呼叫驗證碼 API
- **伺服器判定優先**：
  - 收到 `SalesClosed` 後，該頁 SHALL 視為已停售，不論本機時鐘推導結果為何；此判定在離開本頁前持續有效。
  - 收到 `SalesNotOpen` 不覆寫推導結果，以便開賣後可重試：本機推導仍為「販售中」時，送出訂單按鈕 SHALL 維持可用。
- **活動列表**：活動列表頁每張卡片 SHALL 以文字標籤顯示販售狀態（尚未開賣／販售中／已停售），於頁面載入時計算，不隨時間自動更新。

#### Scenario: BW-SALES-001 販售狀態推導與後端邊界一致
- **WHEN** 依活動的 `salesStartAtUtc`、`salesEndAtUtc`、`startAtUtc` 與當下時間推導販售狀態
- **THEN** 當下時間早於開賣時間為「尚未開賣」；等於開賣時間為「販售中」；`salesEndAtUtc` 為 null 時，等於或晚於 `startAtUtc` 為「已停售」；`salesEndAtUtc` 有值時，等於或晚於 `salesEndAtUtc` 為「已停售」；`salesStartAtUtc` 為 null 且未到停售時間為「販售中」；`salesStartAtUtc` 或 `salesEndAtUtc` 為 `undefined` 時，推導的販售狀態與實際停售時間皆與該欄位為 null 時相同

- **THEN** 頁面顯示「本活動已停售」，座位圖仍顯示但點選座位不會選取，計數輸入與快速選位的區域下拉、數量輸入、按鈕呈現停用，快速選位不會送出訂單，送出訂單按鈕停用

- **THEN** 排隊等待中不顯示「現在開放購票」；放行後「現在開放購票」重新顯示於購票區塊最上方，買家可選位並送出訂單

### Requirement: 活動詳情頁在窄螢幕不產生頁面橫向捲動
活動詳情頁在視窗寬度 320px 至 720px 之間時，頁面文件寬度（`document.documentElement.scrollWidth`）MUST NOT 大於視窗寬度，也就是不得出現頁面層級的橫向捲動。資訊欄（活動標題、時間、販售期間、票價表）與購票欄（區域隨選列、座位區塊、計數購票列、送出訂單區塊）SHALL 完整顯示在視窗寬度內。區域隨選列（分區選單、張數輸入、「自動選位並送出訂單」按鈕）與計數購票列（區域、價格、可售數量、張數輸入）在一行放不下時 SHALL 換行顯示，不得把所在欄位或頁面撐寬。視窗寬度大於 720px 時，SHALL 維持既有的雙欄版面（資訊欄固定 320px、購票欄佔剩餘寬度），且同樣不得出現頁面層級的橫向捲動。

本需求不涵蓋排隊中的驗證碼畫面、資料載入失敗與找不到活動的空狀態（見 design.md Non-Goals）。

#### Scenario: 390px 寬未登入瀏覽活動詳情頁
- **WHEN** 未登入的使用者以 390px 寬的視窗開啟一個含座位制票種的活動詳情頁，並等待資料載入完成
- **THEN** 頁面 `scrollWidth` 不大於 390，活動標題與票價表的右緣不超過 390

#### Scenario: 320px 寬未登入瀏覽活動詳情頁
- **WHEN** 未登入的使用者以 320px 寬的視窗開啟同一個活動詳情頁，並等待資料載入完成
- **THEN** 頁面 `scrollWidth` 不大於 320，區域隨選列的按鈕換到下一行顯示，而不是超出視窗

#### Scenario: 已登入買家在窄螢幕瀏覽含計數票種的活動詳情頁
- **WHEN** 已登入的買家分別以 390px 與 320px 寬的視窗開啟一個同時有座位制與計數票種、且販售中的活動詳情頁
- **THEN** 兩種寬度下頁面 `scrollWidth` 都不大於視窗寬度，計數購票列與送出訂單區塊的右緣都不超過視窗寬度

#### Scenario: 桌面與平板寬度維持雙欄版面
- **WHEN** 使用者分別以 721px、800px 與 1280px 寬的視窗開啟活動詳情頁
- **THEN** grid 第一欄寬度為 320px，資訊欄寬度為 320px，購票欄的左緣位於資訊欄右緣的右側，且頁面 `scrollWidth` 不大於視窗寬度

#### Scenario: 斷點上限寬度維持單欄且不橫向捲動
- **WHEN** 未登入的使用者以 720px 寬的視窗（單欄版面的最大寬度）開啟活動詳情頁
- **THEN** grid 只有一欄，購票欄位於資訊欄下方，且頁面 `scrollWidth` 不大於 720

### Requirement: 前端文件語言宣告為繁體中文
前端應用程式的 HTML 文件 SHALL 將根元素的 `lang` 屬性宣告為 `zh-Hant-TW`，讓輔助科技與瀏覽器以正確語言處理頁面內容。

#### Scenario: 根元素語言宣告
- **WHEN** 讀取前端建置輸入的 `web/index.html`（本 SPA 唯一的 HTML 文件）
- **THEN** `<html>` 元素的 `lang` 屬性值為 `zh-Hant-TW`
