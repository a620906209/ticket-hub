## ADDED Requirements

### Requirement: 買家在建立訂單前於確認步驟檢查已選內容並同意注意事項
活動詳情頁的購票流程 SHALL 分為選位步驟與確認步驟。結帳列的「下一步」按鈕啟用條件與原「送出訂單」按鈕相同；按下後，有已選內容（座位或數量大於 0 的計數票種）且通過限購重新加總檢查時，SHALL 切換到確認步驟：網址加上 `step=confirm` query，並新增一筆瀏覽紀錄。此時 MUST NOT 呼叫下單 API。限購檢查未通過時，SHALL 在結帳列顯示提示訊息，不切換步驟，也不清除既有錯誤訊息。

確認步驟 SHALL 取代購票欄內的選位內容（區域隨選、座位網格、計數購票區塊、結帳列），並顯示：

- 已選座位：依加入順序每個座位一列，顯示「分區-座位號碼」與票價
- 計數票種：只列數量大於 0 者，顯示票種名稱、數量與小計（票價 × 數量）
- 總金額：與選位步驟結帳列摘要的總金額相同
- 注意事項（固定文字，不渲染使用者輸入）：
  - 確認訂單後保留 10 分鐘，期限內未付款，訂單自動取消並釋出座位與票券
  - 付款完成後才出票，可在「我的訂單」查看
  - 活動需實名時另加一行實名入場說明；不需實名的活動不顯示此行
- 「我已閱讀並同意注意事項」勾選框：每次進入確認步驟時為未勾選
- 錯誤訊息區（有錯誤時才顯示，`role="alert"`）、「返回改選」與「確認訂單」按鈕。確認步驟錯誤區與結帳列錯誤區顯示同一則操作錯誤訊息，依當下所在步驟顯示在其中一處；在兩步驟間以「返回改選」或瀏覽器上一頁／下一頁切換時，訊息保留，只在「下一步」「確認訂單」「自動選位」通過前置檢查時清除

購票欄上方的販售提示、實名引導與頁面頂端錯誤訊息，維持原本的顯示規則。

「確認訂單」與「返回改選」：

- 勾選注意事項前，「確認訂單」SHALL 停用。
- 按下「確認訂單」才呼叫下單 API，送出內容與規則依「買家可選位並送出訂單」Requirement。送出前的限購重新加總保留為防禦性檢查（確認步驟無法修改已選內容，正常操作不會觸發，不另設 Scenario），未通過時訊息顯示在確認步驟的錯誤區。
- 通過前置檢查後，SHALL 清除確認步驟錯誤區與頁面頂端的錯誤訊息。
- 送出中「確認訂單」SHALL 顯示載入中且不可再次觸發，「返回改選」SHALL 停用；同一次確認只呼叫一次下單 API。
- 「返回改選」與瀏覽器上一頁 SHALL 回到選位步驟，保留已選座位與計數數量，焦點移到「下一步」按鈕。
- 進入確認步驟時，焦點 SHALL 移到確認步驟標題。

確認步驟只在以下條件同時成立時存在：

- 已登入
- 可購買：非熱門搶購活動或排隊已放行，且販售狀態為「販售中」
- 有已選內容

網址帶 `step=confirm` 但條件不成立時，系統 SHALL 以取代目前紀錄的方式移除 `step`，顯示選位步驟。例如：直接開啟或重新整理該網址、停留期間跨過停售時間。排隊放行後前端不再輪詢，入場資格逾時只能由下單回應 `403 QueueAdmissionRequired` 得知，依下方失敗處理退回。

下單 API 失敗時：

- 401：依「買家可選位並送出訂單」導向登入頁，`redirect` 為不含 `step` 的活動頁網址。
- 其他錯誤：訊息、清空與重新整理行為依原 Requirement，停留的步驟如下。
  - 429、`409 SalesNotOpen`：停在確認步驟，訊息顯示在確認步驟的錯誤區，保留勾選狀態與已選內容，可直接再按「確認訂單」。
  - `403 QueueAdmissionRequired`、`403 RealNameRequired`、`409 SalesClosed`、其他下單失敗：以取代目前紀錄的方式退回選位步驟，訊息顯示在原 Requirement 規定的位置。
- 送出中買家已用瀏覽器上一頁回到選位步驟時，回應依同一規則處理：「退回選位步驟」不再改變步驟；429、`409 SalesNotOpen` 的訊息依上述共用錯誤訊息規則顯示在結帳列。

下單成功時：

- SHALL 依「活動列表在建立訂單後顯示一次性付款提示」Requirement 回到活動列表。
- 導頁以取代目前紀錄的方式進行，按上一頁回到活動詳情頁，不回到已送出的確認步驟。
- 成功回應前買家仍在活動詳情頁但已回到選位步驟時，同樣導向活動列表。
- 成功回應前買家已離開活動詳情頁時，MUST NOT 導頁，也不記錄活動列表的付款提示（避免延後顯示時「保留 10 分鐘」已不正確、或換帳號後看到前一人的訂單），改以短暫成功訊息「訂單已建立，請到「我的訂單」完成付款」告知。

用語對應：本 capability 其他 Requirement 所稱「送出訂單」，指在確認步驟按下「確認訂單」。所稱「送出訂單按鈕」，在選位步驟指結帳列的「下一步」，在確認步驟指「確認訂單」。例如販售期間外「停用送出訂單按鈕」即停用「下一步」，且確認步驟依上述條件不存在。

#### Scenario: BW-CONFIRM-001 按下一步進入確認步驟，不呼叫下單 API
- **WHEN** 已登入買家選了 2 個座位，並對一個計數票種輸入數量 2，按「下一步」
- **THEN** 網址帶 `step=confirm`，畫面列出 2 個座位的「分區-座位號碼」與票價、該計數票種的名稱、數量 2 與小計、總金額，注意事項勾選框為未勾選；座位網格與結帳列不顯示；系統不呼叫下單 API

#### Scenario: BW-CONFIRM-002 勾選注意事項後才能確認訂單
- **WHEN** 買家在確認步驟尚未勾選「我已閱讀並同意注意事項」
- **THEN** 「確認訂單」為停用；勾選後變為可用，按下時以目前已選內容呼叫一次下單 API

#### Scenario: BW-CONFIRM-003 返回改選保留已選內容，重新進入時需重新勾選
- **WHEN** 買家在確認步驟勾選注意事項後，按「返回改選」（或瀏覽器上一頁）
- **THEN** 回到選位步驟，網址不帶 `step`，已選座位與計數數量不變，焦點在「下一步」按鈕，下單 API 呼叫次數為 0；再次按「下一步」，或以瀏覽器下一頁回到確認步驟時，勾選框皆為未勾選

#### Scenario: BW-CONFIRM-004 直接開啟確認步驟網址
- **WHEN** 使用者直接開啟或重新整理 `/events/{id}?step=confirm`，此時沒有已選內容
- **THEN** 系統以取代目前紀錄的方式移除 `step`，顯示選位步驟

#### Scenario: BW-CONFIRM-005 送出中不重複送出
- **WHEN** 買家按下「確認訂單」，下單 API 尚未回應時再次按「確認訂單」
- **THEN** 下單 API 只被呼叫一次，「返回改選」在回應前為停用

#### Scenario: BW-CONFIRM-006 可重試的錯誤停在確認步驟
- **WHEN** 買家在確認步驟按「確認訂單」，下單 API 回應 429，或回應 409 且 `Title = "SalesNotOpen"`
- **THEN** 畫面停在確認步驟，確認步驟錯誤區顯示對應訊息（429：「請求過於頻繁，請稍後再試」；SalesNotOpen：「尚未開賣，請於開賣時間後再試」），勾選狀態與已選內容保留，「確認訂單」可再次按下

#### Scenario: BW-CONFIRM-007 一般下單失敗退回選位步驟並清空
- **WHEN** 買家在確認步驟按「確認訂單」，下單 API 回應一般失敗（例如座位已被搶先鎖定）
- **THEN** 系統以取代目前紀錄的方式退回選位步驟，結帳列顯示下單失敗訊息，已選座位與計數數量清空，並重新查詢座位與票種資料

#### Scenario: BW-CONFIRM-008 排隊資格、實名或停售錯誤退回選位步驟並保留已選內容
- **WHEN** 買家在確認步驟按「確認訂單」，下單 API 回應 `403 QueueAdmissionRequired`、`403 RealNameRequired` 或 `409 SalesClosed`
- **THEN** 系統以取代目前紀錄的方式退回選位步驟，不清空已選內容；三者分別在頁面頂端顯示排隊資格訊息並重新查詢排隊狀態、顯示「購票前需先登記實名」引導、顯示「本活動已停售」並停用「下一步」

#### Scenario: BW-CONFIRM-009 確認時登入已失效
- **WHEN** 買家在確認步驟按「確認訂單」，下單 API 回應 401
- **THEN** 系統導向登入頁，`redirect` 為 `/events/{id}`（不含 `step`）

#### Scenario: BW-CONFIRM-010 停留確認步驟期間跨過停售時間
- **WHEN** 買家停在確認步驟，時間經過實際停售時間
- **THEN** 系統以取代目前紀錄的方式退回選位步驟，購票區塊顯示「本活動已停售」，「下一步」停用

#### Scenario: BW-CONFIRM-011 進入確認步驟時焦點移到標題
- **WHEN** 買家按「下一步」進入確認步驟
- **THEN** 焦點位於確認步驟標題

#### Scenario: BW-CONFIRM-012 按下一步時超過限購
- **WHEN** 活動限購 2 張，買家已選 1 個座位且計數數量為 2（在輸入上限生效前填入），按「下一步」
- **THEN** 結帳列顯示限購提示，不進入確認步驟，不呼叫下單 API

#### Scenario: BW-CONFIRM-013 需實名活動的注意事項
- **WHEN** 買家在 `IsRealNameRequired = true` 的活動進入確認步驟
- **THEN** 注意事項包含實名入場說明；`IsRealNameRequired = false` 的活動不顯示此行

#### Scenario: BW-CONFIRM-014 下單回應前已離開活動詳情頁
- **WHEN** 買家按「確認訂單」後、下單 API 回應成功前，已離開活動詳情頁（例如前往「我的訂單」）
- **THEN** 系統不導向活動列表、不記錄付款提示，顯示成功訊息「訂單已建立，請到「我的訂單」完成付款」

#### Scenario: BW-CONFIRM-015 確認成功後回到活動列表
- **WHEN** 買家在確認步驟勾選注意事項後按「確認訂單」，下單 API 回應成功
- **THEN** 系統以取代目前紀錄的方式導向活動列表，不新增瀏覽紀錄；活動列表的付款提示所指的訂單，即本次下單 API 回應的訂單 Id

#### Scenario: BW-CONFIRM-016 送出中按瀏覽器上一頁回到選位步驟
- **WHEN** 買家按下「確認訂單」後、下單 API 回應前，以瀏覽器上一頁回到選位步驟
- **THEN** 回應成功時導向活動列表並顯示付款提示；回應 429 時結帳列顯示「請求過於頻繁，請稍後再試」，已選內容保留，停在選位步驟

#### Scenario: BW-CONFIRM-017 錯誤訊息隨步驟切換保留
- **WHEN** 買家在確認步驟收到 429 訊息後按「返回改選」，再以瀏覽器下一頁回到確認步驟
- **THEN** 返回後結帳列顯示同一則訊息；回到確認步驟後確認步驟錯誤區仍顯示該訊息；之後按「確認訂單」通過前置檢查時訊息清除

### Requirement: 活動列表在建立訂單後顯示一次性付款提示
確認步驟建立訂單成功、回到活動列表頁時，系統 SHALL 在列表頂端顯示可關閉的成功橫幅（`role="status"`）：

- 文字為「訂單已建立，已為你保留 10 分鐘，請在期限內完成付款」
- 附「前往付款」連結，指向該筆訂單的訂單明細頁 `/orders/{訂單 Id}`

提示只顯示一次：

- 買家關閉橫幅後，橫幅消失。
- 顯示過後，再次進入活動列表或重新整理頁面，MUST NOT 再顯示。
- 訂單 Id MUST NOT 放在網址中。
- 不是由建立訂單成功而進入活動列表時，不顯示橫幅。

橫幅與活動列表資料載入互不影響：列表載入失敗時，橫幅仍顯示。

#### Scenario: BW-LOBBY-NOTICE-001 建立訂單後回到活動列表顯示付款提示
- **WHEN** 買家確認訂單成功，系統回到活動列表
- **THEN** 列表頂端顯示「訂單已建立，已為你保留 10 分鐘，請在期限內完成付款」與「前往付款」連結，連結目標為 `/orders/{訂單 Id}`，訂單 Id 與本次下單 API 回應的 Id 相同；網址為 `/events`，不帶訂單 Id

#### Scenario: BW-LOBBY-NOTICE-002 關閉付款提示
- **WHEN** 買家在活動列表關閉付款提示橫幅
- **THEN** 橫幅消失

#### Scenario: BW-LOBBY-NOTICE-003 付款提示只顯示一次
- **WHEN** 付款提示顯示過後，買家離開再回到活動列表，或重新整理活動列表
- **THEN** 不再顯示付款提示

#### Scenario: BW-LOBBY-NOTICE-004 未建立訂單進入活動列表
- **WHEN** 使用者未經確認訂單成功，直接開啟活動列表
- **THEN** 不顯示付款提示

#### Scenario: BW-LOBBY-NOTICE-005 活動列表載入失敗仍顯示付款提示
- **WHEN** 買家確認訂單成功回到活動列表，活動列表查詢 API 失敗
- **THEN** 頁面同時顯示載入失敗訊息與付款提示

### Requirement: 舊的下單結果頁網址導向訂單明細頁
前端 SHALL 將 `/order-result/{id}` 導向 `/orders/{id}`，`{id}` 原值保留（不檢查格式、不在導向時查詢訂單）。導向後的登入要求、權限與找不到訂單的處理，依訂單明細頁既有規則（BW-MYORDER-NOTFOUND-001、BW-MYORDER-FORBIDDEN-001、BW-MYORDER-INVALID-ID-001）：不存在或非 GUID 的 Id 顯示找不到提示，非本人的訂單顯示無權限提示且不顯示訂單內容。

#### Scenario: BW-RESULT-REDIRECT-001 已登入開啟舊結果頁網址
- **WHEN** 已登入買家開啟 `/order-result/{訂單 Id}`
- **THEN** 前端導向 `/orders/{訂單 Id}`，顯示該筆訂單明細

#### Scenario: BW-RESULT-REDIRECT-002 未登入開啟舊結果頁網址
- **WHEN** 未登入使用者開啟 `/order-result/{訂單 Id}`
- **THEN** 前端導向登入頁，登入成功後導回 `/orders/{訂單 Id}`

#### Scenario: BW-RESULT-REDIRECT-003 舊網址帶不存在、非 GUID 或他人的訂單 Id
- **WHEN** 已登入買家開啟 `/order-result/{Id}`，Id 為不存在的 GUID、非 GUID 字串（例如 `not-a-guid`），或他人訂單的 Id
- **THEN** 前端導向 `/orders/{同一個 Id 原值}`；不存在與非 GUID 時顯示「找不到這筆訂單」，他人訂單時顯示「你沒有權限查看這筆訂單」，兩者都不顯示任何訂單內容

## MODIFIED Requirements

### Requirement: 未登入使用者存取需登入頁面或執行需登入操作時導向登入頁
系統 SHALL 在使用者嘗試存取需要登入的買家頁面（我的訂單、訂單明細頁）或在公開頁面上執行需要登入的操作（活動詳情頁選位）但尚未登入時，導向登入頁；登入成功後 SHALL 導回原本嘗試存取的頁面。活動列表頁與活動詳情頁本身（含座位圖瀏覽）不需要登入即可瀏覽——只有「選位」這個動作本身才觸發導向登入頁，不是進入活動詳情頁就要求登入。

#### Scenario: 未登入直接進入我的訂單頁
- **WHEN** 未登入的使用者直接開啟「我的訂單」頁面網址
- **THEN** 系統導向登入頁

#### Scenario: 未登入在活動詳情頁點選座位
- **WHEN** 未登入的使用者在活動詳情頁點選任一座位（不論該座位是否為 Available 狀態）
- **THEN** 系統導向登入頁，不進行任何選位動作

#### Scenario: 登入成功後導回原頁面
- **WHEN** 使用者因未登入被導向登入頁，登入成功
- **THEN** 系統導回使用者原本嘗試存取的頁面（例如導回原本瀏覽的活動詳情頁，可繼續選位）

### Requirement: 買家可選位並送出訂單
系統 SHALL 在活動詳情頁提供座位選擇與下單操作，呼叫既有 `ticket-purchase` 下單 API；送出訂單分為選位與確認兩個步驟（見「買家在建立訂單前於確認步驟檢查已選內容並同意注意事項」Requirement），本 Requirement 所稱「送出訂單」指在確認步驟按下「確認訂單」；下單成功後 SHALL 回到活動列表並顯示付款提示（見「活動列表在建立訂單後顯示一次性付款提示」Requirement）。活動可由 Admin 設定「每筆訂單限購張數」（選填，未設定代表不限制）；當已選座位數加上已輸入的純計數票種購買數量總和達到上限時，系統 SHALL 阻止再選新座位或增加計數購買數量，直到取消已選座位或降低計數數量釋出額度。座位選購與計數購買輸入的阻止方式不同：點選座位被阻止時 SHALL 顯示提示訊息（比照既有座位選購的既定行為，見「已選座位數達到每筆訂單限購張數」Scenario）；計數購買數量輸入則採限制型互動，由輸入元件本身限制數值上限、不接受超過限購的輸入，不另外顯示提示訊息或呈現為錯誤狀態（見「純計數購買數量達到每筆訂單限購張數」Scenario，與可售總量的限制型互動一致）。此限制前端會提前檢查並提示，但**後端 `PlaceOrder` API 才是最終把關**——前端檢查被繞過或跟後端資料不同步時，後端仍會拒絕超過上限的下單請求。

活動詳情頁 SHALL 對 `RequiresSeat = false` 的純計數票種，於獨立的「計數購票」區塊顯示票種名稱、票價、當下可售總量，並提供購買數量輸入（非負整數，0 代表不購買）；此區塊與既有座位選購區塊（僅列出 `RequiresSeat = true` 的票種）並列顯示，互不影響彼此的選購狀態。計數購買操作比照既有座位選位規則，視為需登入才能執行的操作：未登入時嘗試調整任一計數票種的購買數量（含直接輸入、增減按鈕等任何互動方式），系統 SHALL 立即導向登入頁，不套用該次數量變更；登入成功後 SHALL 導回原頁面，比照既有座位選位「登入後可繼續選位」的既定行為，不特別還原導向登入前嘗試輸入的數值——因為攔截發生在數值套用之前，本來就沒有暫存值需要還原。

單一計數票種的購買數量輸入元件 SHALL 將可輸入上限設為「該票種當下可售總量」與「限購剩餘額度（`maxTicketsPerOrder` 扣除已選座位數、扣除其他計數票種已輸入數量、加回自己目前輸入值後的結果）」兩者中較小值，並由元件本身限制輸入不得超過此上限——超過上限的輸入 SHALL 被限制、不接受，不呈現為錯誤狀態（限制型輸入控制，元件不允許出現暫時性的超額顯示值，與下方「計數輸入元件限制數量不得超過可售總量」Scenario 一致）；此限制與既有「區域隨選」的雙重限制計算方式一致，兩者共用同一份剩餘額度，任一方消耗額度後 SHALL 立即反映到另一方可輸入/可抽選的上限。數量為 0 的計數票種 SHALL 視為未選購，送出訂單時 MUST NOT 包含在下單請求的選購項目中。

送出訂單時，座位選購項目與計數購買項目（數量大於 0 者）SHALL 合併於同一次下單請求送出，呼叫既有支援混合項目的下單 API；座位項目 SHALL 送出 `eventSeatId`（該座位 Id）與 `ticketTypeId`，不含 `quantity` 欄位（欄位省略，後端預設視為 1，維持既有行為）；計數項目的 `eventSeatId` SHALL 為 `null`（欄位存在、值為 `null`，非省略），並包含 `ticketTypeId` 與正整數 `quantity`。按「下一步」時系統 MUST 重新加總座位數與計數購買總量，超過限購張數時 MUST 擋下、在結帳列顯示提示訊息、不進入確認步驟、不呼叫下單 API（「確認訂單」送出前的再次加總為防禦性檢查，見確認步驟 Requirement）——不得僅依賴各輸入元件的上限屬性作為唯一防線（例如買家在其中一個輸入框調整上限生效前，已在另一個輸入框填入超額數值的情況）。

下單 API 呼叫失敗時，若為 401（換發失敗），系統 SHALL 直接導向登入頁（比照既有座位選位的登入要求），不顯示下單失敗訊息、不套用下方的清空/刷新處理——活動詳情頁為公開頁，既有全域換發/登入導頁機制僅在需要登入的路由才會生效，不會處理公開頁上的登入失效，此元件 MUST 自行攔截 401 並導頁。除 401 與本 Requirement 另行列出的例外（`403 QueueAdmissionRequired`、`429`、`409 SalesNotOpen`／`SalesClosed`）以外的其他下單失敗（座位已被搶先鎖定、計數票種可售總量於送出當下已被其他買家買光、或後端其他驗證失敗），系統 SHALL 一律顯示錯誤訊息、清空目前已選座位與已輸入的計數購買數量、並重新呼叫查詢 API 刷新座位與票種資料——比照既有座位選購失敗時的既定處理，除上述明列例外外，不依失敗原因做差異化處理（維持既有行為單純、一致，明列例外以外不新增依錯誤類型分流的重試或保留輸入邏輯）。

活動是否處於熱門搶購模式，前端 SHALL 直接讀取活動列表查詢 API（`GET /api/events`，`ticket-purchase`「瀏覽活動與座位可售狀態」能力）回應中的 `IsQueueModeEnabled` 欄位判斷，不需另外呼叫其他端點確認。若活動處於熱門搶購模式（`IsQueueModeEnabled = true`），買家進入活動詳情頁的選位/計數購票操作前，系統 SHALL 先呼叫排隊狀態查詢 API：**尚未加入排隊時 SHALL 顯示驗證碼圖片與輸入欄位（呼叫 `GET /api/captcha` 取得），提供加入排隊的操作，加入排隊時 MUST 一併附帶取得的 token 與使用者填寫的驗證碼文字；驗證碼相關元件沿用「買家可透過介面註冊與登入」能力所述的共用 `useCaptcha` composable，不重複實作；加入排隊因驗證碼錯誤被拒絕時，系統 SHALL 顯示驗證碼錯誤提示、自動換發新驗證碼、清空舊輸入，停留在尚未加入排隊的畫面，不清空/重新整理座位與票種資料（與此操作無關）；此處驗證碼圖片載入、刷新失敗時的處理沿用「買家可透過介面註冊與登入」能力所述的共用行為（顯示「系統暫時無法取得驗證碼，請稍後再試」、停用加入排隊按鈕、提供重試操作），不重複定義**；已加入且狀態為 `Waiting` 時 SHALL 顯示排隊等待畫面（含前方等待人數），停用座位選擇、計數購買輸入與區域隨選快速下單的操作入口，並以固定間隔定期輪詢排隊狀態查詢 API（輪詢間隔為可設定值，與後端 `PurchaseQueueOptions.PollingInterval` 同數量級，避免輪詢過於頻繁造成負擔或過於稀疏造成畫面更新明顯延遲）；每次輪詢回應除排隊紀錄狀態外，SHALL 一併包含該活動當下的 `queueModeEnabled`（見 `purchase-queue`「買家可查詢自己的排隊狀態」能力），不需另外呼叫活動列表 API 確認——若某次輪詢回應的 `queueModeEnabled` 為 `false`（Admin 已於買家等待期間關閉熱門搶購模式），系統 SHALL 停止輪詢、關閉排隊等待畫面，開放選位/計數購買、區域隨選與送出訂單操作，比照該活動從未開啟熱門搶購模式的一般行為。狀態轉為 `Admitted` 時 SHALL 停止輪詢、關閉排隊等待畫面，開放選位/計數購買、區域隨選與送出訂單操作。下單 API 回傳 `403 Forbidden` 且 `ProblemDetails.title === "QueueAdmissionRequired"`（排隊資格不足：未入場或已逾時）而失敗時，系統 SHALL 顯示提示訊息並導回排隊等待畫面重新查詢狀態，不套用「其他下單失敗」一般情形的清空/刷新處理（此情形不代表座位或庫存資料有變動）；前端 MUST 同時檢查 `status` 與 `title` 兩者才視為排隊資格不足，不得只依 HTTP 403 狀態碼判斷——其他業務語意的 403（例如既有「非本人操作」情境）SHALL 沿用一般授權錯誤處理，不導向排隊等待畫面。下單 API 因超過請求頻率限制（429）而失敗時，系統 SHALL 顯示「請稍後再試」的提示訊息，不清空已選座位與已輸入的計數購買數量、不重新整理座位與票種資料——此情形代表發送速度過快，而非資料已變動，維持買家目前已選內容供其等待後直接重試。下單 API 回傳 `409 Conflict` 且 `ProblemDetails.title` 為 `SalesNotOpen` 或 `SalesClosed`（販售期間外）而失敗時，系統 SHALL 依「活動頁依販售期間顯示狀態並限制購票操作」能力處理：顯示對應中文訊息，不清空已選座位與已輸入的計數購買數量、不重新整理座位與票種資料——後端在檢查販售期間時尚未鎖定任何座位或庫存，選擇仍然有效；前端 MUST 同時檢查 `status` 與 `title`，其他 409 沿用一般失敗處理。

#### Scenario: BW-ORDER-001 選擇可售座位並成功下單
- **WHEN** 已登入買家在活動詳情頁選擇一個或多個 Available 狀態的座位，按「下一步」、勾選注意事項後按「確認訂單」
- **THEN** 系統呼叫下單 API 成功，回到活動列表並顯示該筆訂單的付款提示

#### Scenario: BW-ORDER-002 下單時座位已被搶先鎖定
- **WHEN** 買家送出下單時，其中一個座位已被其他訂單鎖定或售出（API 回傳失敗）
- **THEN** 系統顯示下單失敗的錯誤訊息，清空目前已選座位與已輸入的計數購買數量，重新呼叫查詢 API 刷新座位與票種資料，退回選位步驟，不回到活動列表

#### Scenario: BW-ORDER-003 送出訂單時登入狀態已失效（401）
- **WHEN** 買家送出下單時，Access Token 已過期且換發也失敗，下單 API 回傳 401
- **THEN** 系統直接導向登入頁，不顯示下單失敗訊息，不套用清空已選座位/計數輸入與重新整理資料的處理

#### Scenario: BW-ORDER-004 已選座位數達到每筆訂單限購張數
- **WHEN** 買家在已選座位數（含已輸入的計數購買數量總和）等於活動設定的限購張數時，再點選一個新的 Available 座位
- **THEN** 系統顯示「已達每筆訂單限購張數」的提示訊息，不將新座位加入已選清單

#### Scenario: BW-ORDER-005 活動未設定限購張數
- **WHEN** 活動的每筆訂單限購張數為未設定（不限制）
- **THEN** 買家可以選擇任意數量的 Available 座位，不受張數限制

#### Scenario: BW-ORDER-006 未登入嘗試調整計數購買數量
- **WHEN** 未登入的使用者嘗試調整任一純計數票種的購買數量（直接輸入或使用增減按鈕）
- **THEN** 系統立即導向登入頁，不套用該次數量變更；登入成功後導回原頁面，該票種購買數量維持 0

#### Scenario: BW-ORDER-007 純計數票種輸入購買數量並成功下單
- **WHEN** 已登入買家在活動詳情頁的計數購票區塊，對一個 `RequiresSeat = false` 的票種輸入購買數量（不超過當下可售總量與限購剩餘額度）並送出訂單
- **THEN** 系統呼叫下單 API 成功，該筆選購項目為 `eventSeatId: null`（欄位存在、值為 `null`）、`ticketTypeId` 為該票種、`quantity` 為輸入的正整數數量，回到活動列表並顯示該筆訂單的付款提示

#### Scenario: BW-ORDER-008 混合座位選購與純計數購買並成功下單
- **WHEN** 已登入買家同時選擇一個或多個座位，並對一個純計數票種輸入購買數量，送出下單
- **THEN** 系統將座位項目（`eventSeatId` 為座位 Id、不含 `quantity`）與計數項目（`eventSeatId: null`、含 `ticketTypeId` 與正整數 `quantity`）合併於同一次下單請求送出，成功後回到活動列表並顯示該筆訂單的付款提示

#### Scenario: BW-ORDER-009 純計數購買數量達到每筆訂單限購張數
- **WHEN** 買家輸入的計數購買數量（加上已選座位數）達到活動設定的限購張數，嘗試再增加計數購買數量
- **THEN** 計數輸入元件限制數值不得超過剩餘額度，不接受超過限購的輸入，不呈現為錯誤狀態（限制型，與「計數輸入元件限制數量不得超過可售總量」Scenario 一致的互動模式；已選座位數達到限購張數後再嘗試選新座位，仍依「已選座位數達到每筆訂單限購張數」Scenario 顯示提示訊息——座位選購走點選互動，不是連續數量輸入，兩種介面元件的既定回饋方式不同）

#### Scenario: BW-ORDER-010 計數輸入元件限制數量不得超過可售總量
- **WHEN** 買家嘗試在計數輸入框以直接輸入或增減按鈕，調整超過該票種當下可售總量的數值
- **THEN** 輸入元件限制數值不得超過可售總量上限，不接受超額輸入，不呈現為錯誤狀態

#### Scenario: BW-ORDER-011 送出時因庫存已變動被後端拒絕
- **WHEN** 買家在前端檢查通過的情況下送出訂單，但送出當下某計數票種的可售總量已因其他買家搶購而變動，後端拒絕本次購買
- **THEN** 系統顯示下單失敗訊息，清空目前已選座位與已輸入的計數購買數量，並重新整理票種與座位資料（比照「下單時座位已被搶先鎖定」的統一失敗處理）

#### Scenario: BW-ORDER-012 純計數票種可售總量為 0
- **WHEN** 某純計數票種當下的可售總量為 0
- **THEN** 該票種的購買數量輸入框上限為 0、無法輸入大於 0 的數量，介面顯示「已售完」提示，不視為錯誤狀態、不顯示錯誤訊息樣式

#### Scenario: BW-ORDER-013 活動未設定限購張數時的純計數購買
- **WHEN** 活動的每筆訂單限購張數為未設定（不限制），買家對某純計數票種輸入購買數量
- **THEN** 該票種的購買數量輸入僅受當下可售總量限制，不受限購張數限制

#### Scenario: BW-ORDER-014 計數購買數量為 0 時不送出對應項目
- **WHEN** 買家在計數購票區塊對某票種維持購買數量為 0（未輸入或清空），對其他票種正常選購並送出訂單
- **THEN** 下單請求的選購項目 MUST NOT 包含該數量為 0 的票種

#### Scenario: BW-ORDER-015 按下一步時偵測到合併總數超過限購張數
- **WHEN** 買家透過分別在座位網格與計數輸入框操作，使已選座位數與計數購買總量的加總超過活動設定的限購張數（例如個別輸入當下未觸發即時提示，但按「下一步」當下加總已超過），按「下一步」
- **THEN** 系統偵測到總數超過限購張數，停留在選位步驟（網址不帶 `step`）、在結帳列顯示限購提示訊息，不呼叫下單 API

#### Scenario: BW-ORDER-016 已手動選取座位佔用額度後，計數購買輸入上限隨之減少
- **WHEN** 買家已在座位網格手動選取座位、佔用部分限購額度（尚未送出訂單），接著要在計數購票區塊輸入購買數量
- **THEN** 該計數票種輸入框當下可輸入的上限 SHALL 扣除已選座位數後重新計算，不允許輸入超過剩餘額度的數量

#### Scenario: BW-QUEUE-001 進入熱門搶購模式活動且尚未加入排隊
- **WHEN** 已登入買家進入 `IsQueueModeEnabled = true` 的活動詳情頁，且尚未加入該活動的排隊
- **THEN** 系統顯示驗證碼圖片、輸入欄位與加入排隊的操作，不開放選位/計數購買輸入

#### Scenario: BW-QUEUE-002 排隊中顯示等待畫面並輪詢狀態
- **WHEN** 已登入買家已加入排隊，狀態為 `Waiting`
- **THEN** 系統顯示排隊等待畫面與目前前方等待人數，停用座位選擇、計數購買輸入與區域隨選快速下單的操作入口，並定期輪詢排隊狀態

#### Scenario: BW-QUEUE-003 排隊入場後開放選位與下單
- **WHEN** 買家的排隊狀態由 `Waiting` 轉為 `Admitted`
- **THEN** 系統停止輪詢、關閉排隊等待畫面，開放座位選擇、計數購買輸入、區域隨選快速下單與送出訂單操作

#### Scenario: BW-QUEUE-004 下單時排隊資格已逾時
- **WHEN** 買家送出下單時，其排隊資格已逾時或不存在，下單 API 回傳 `403 Forbidden` 且 `title === "QueueAdmissionRequired"`
- **THEN** 系統顯示提示訊息並導回排隊等待畫面重新查詢狀態，不清空座位/計數輸入、不比照一般失敗重新整理座位與票種資料

#### Scenario: BW-QUEUE-006 其他語意的 403 不視為排隊資格不足
- **WHEN** 買家送出下單時，下單 API 回傳 `403 Forbidden`，但 `title` 不是 `"QueueAdmissionRequired"`（例如既有其他業務語意的 403）
- **THEN** 系統 SHALL 沿用一般授權錯誤處理，不導向排隊等待畫面、不誤判為排隊資格不足

#### Scenario: BW-QUEUE-005 下單因請求頻率限制被拒絕
- **WHEN** 買家送出下單時，下單 API 回傳 429（請求頻率限制）
- **THEN** 系統顯示「請稍後再試」提示訊息，不清空已選座位與已輸入的計數購買數量，不重新整理座位與票種資料

#### Scenario: BW-TOGGLE-001 排隊等待期間 Queue Mode 被關閉
- **WHEN** 買家在排隊等待畫面（`Waiting`）停留期間，Admin 將該活動的熱門搶購模式關閉，前端下一次輪詢排隊狀態查詢 API 回應中的 `queueModeEnabled` 已為 `false`
- **THEN** 系統停止輪詢、關閉排隊等待畫面，開放座位選擇、計數購買輸入、區域隨選與送出訂單操作，比照該活動從未開啟熱門搶購模式的一般行為，不要求買家等到原本的 `Admitted`、不誤導買家以為仍需排隊

#### Scenario: CAPTCHA-BW-QUEUE-001 加入排隊時顯示驗證碼圖片
- **WHEN** 已登入買家進入 `IsQueueModeEnabled = true` 的活動詳情頁，且尚未加入該活動的排隊
- **THEN** 系統呼叫 `GET /api/captcha` 並顯示驗證碼圖片與輸入欄位，加入排隊操作 MUST 隨請求附帶取得的 token 與使用者填寫的文字

#### Scenario: CAPTCHA-BW-QUEUE-002 加入排隊時驗證碼錯誤
- **WHEN** 買家在尚未加入排隊的畫面填寫錯誤的驗證碼並送出加入排隊
- **THEN** 系統顯示驗證碼錯誤提示，自動呼叫 `GET /api/captcha` 換取新驗證碼、清空舊輸入，停留在尚未加入排隊的畫面，不開放選位/計數購買輸入

### Requirement: 買家可用區域隨選自動填入座位，確認後再送出訂單
系統 SHALL 在活動詳情頁的選位區提供「區域隨選」功能：買家選擇一個分區（或「全部區域」）與想購買的張數，點選「自動選位」後，系統 SHALL 從符合條件、目前 Available 且尚未被選取的座位中**隨機**抽出對應數量，加入已選清單，並在結帳列顯示（見「活動詳情頁以固定在購票欄底部的結帳列呈現已選內容並就近顯示操作錯誤」需求）。點選「自動選位」MUST NOT 呼叫下單 API；買家確認抽中的座位後，SHALL 由買家點選「下一步」並在確認步驟按下「確認訂單」才送出，送出規則與「買家可選位並送出訂單」需求相同。抽出的座位與手動點選的座位沒有差別，買家可以個別點選取消。

此功能的隨機抽選對象僅限座位選購：分區下拉選單 SHALL 只列出目前有 `RequiresSeat = true` 票種對應的座位分區代碼；純計數票種沒有對應座位，不會出現在下拉選單中，抽選候選座位集合 MUST NOT 包含任何純計數票種。分區下拉選單 SHALL 預設為「全部區域」；選擇「全部區域」時，抽選池 SHALL 涵蓋所有座位制分區的可售座位。

買家指定的自動選位張數 MUST NOT 超過「符合條件的可售座位數」與「每筆訂單限購張數的剩餘額度」兩者中較小值；超過時系統 MUST 顯示錯誤訊息、不加入任何座位（不得將張數靜默縮減為實際可抽取的數量——買家要求的張數與實際加入的張數必須一致）。剩餘額度計算 SHALL 扣除已選座位數與已輸入的純計數票種購買數量總和。未登入時點選此按鈕的行為 SHALL 與點選單一座位一致：導向登入頁，不進行任何選位動作。

#### Scenario: BW-QUICK-001 全部區域隨機選位並填入已選清單
- **WHEN** 已登入買家維持預設的「全部區域」，輸入不超過可售座位數與限購剩餘額度的張數，點選「自動選位」
- **THEN** 系統從所有座位制分區的可售座位中隨機抽出對應數量，加入已選清單，結帳列顯示這些座位與更新後的張數與總金額；系統不呼叫下單 API，停留在活動詳情頁

#### Scenario: BW-QUICK-002 指定單一分區隨機選位
- **WHEN** 已登入買家改選特定分區與張數，點選「自動選位」
- **THEN** 系統只從該分區的可售座位中抽出對應數量並加入已選清單，不會選到其他分區，也不呼叫下單 API

#### Scenario: BW-QUICK-003 自動選位後由買家送出訂單
- **WHEN** 買家使用「自動選位」填入座位後，點選「下一步」，在確認步驟勾選注意事項後按「確認訂單」
- **THEN** 系統以已選清單（含自動選位抽出的座位）呼叫一次下單 API，成功後回到活動列表並顯示付款提示

#### Scenario: BW-QUICK-004 區域隨選張數超過可售座位或限購剩餘額度
- **WHEN** 買家指定的張數超過符合條件的可售座位數，或超過每筆訂單限購張數的剩餘額度，點選「自動選位」
- **THEN** 系統在結帳列上方顯示對應的錯誤訊息，不加入任何座位，不呼叫下單 API

#### Scenario: BW-QUICK-005 未登入使用區域隨選
- **WHEN** 未登入的使用者選擇分區（或維持全部區域）與張數，點選「自動選位」
- **THEN** 系統導向登入頁，不進行任何選位動作

#### Scenario: BW-QUICK-006 已輸入純計數購買數量時，區域隨選的剩餘額度隨之減少
- **WHEN** 買家已在計數購票區塊輸入購買數量（尚未送出訂單），接著使用區域隨選輸入張數
- **THEN** 區域隨選的剩餘額度計算 SHALL 扣除已輸入的計數購買數量；超過扣除後的剩餘額度時，顯示錯誤訊息、不加入任何座位

#### Scenario: BW-QUICK-007 純計數票種不會出現在區域隨選的分區選單與抽選池中
- **WHEN** 活動同時存在座位制與純計數票種，買家開啟區域隨選的分區下拉選單
- **THEN** 選單只列出座位制票種對應的分區代碼，不包含任何純計數票種；點選「自動選位」時，抽選候選座位集合 MUST NOT 包含任何純計數票種

#### Scenario: BW-QUICK-008 自動選位後與已輸入的計數購買合併送出
- **WHEN** 買家已在計數購票區塊輸入購買數量，接著使用「自動選位」填入座位，再點選「下一步」並在確認步驟按下「確認訂單」
- **THEN** 系統將抽出的座位與已輸入的計數購買數量合併於同一次下單請求送出，成功後回到活動列表並顯示付款提示

### Requirement: 活動詳情頁以固定在購票欄底部的結帳列呈現已選內容並就近顯示操作錯誤
活動詳情頁的購票欄 SHALL 在最下方提供結帳列，內容依序為：操作錯誤訊息（有錯誤時才顯示）、已選座位清單、已選張數與總金額摘要、「下一步」按鈕（見「買家在建立訂單前於確認步驟檢查已選內容並同意注意事項」Requirement）。在所有視窗寬度下，購票欄捲動到可視範圍內時，結帳列 SHALL 以 sticky 方式固定在視窗底部，買家不需要捲到座位網格最後面才能看到總金額或按「下一步」。結帳列只在可以選位購票的畫面顯示；排隊等待畫面、加入排隊畫面與確認步驟 MUST NOT 顯示結帳列。

已選座位清單 SHALL 以「分區-座位號碼」格式依加入順序列出（例如 `A-12、A-13`）。已選座位超過 6 個時，SHALL 只列出前 6 個，並接著顯示「等 N 個座位」，N 為已選座位總數。沒有已選座位時不顯示清單。摘要文字 SHALL 維持「已選 X 個座位、Y 張計數票券，總金額 Z」的格式，並以 `aria-live="polite"` 標示，讓螢幕閱讀器在已選內容改變時念出新的摘要。

由選位、區域隨選、「下一步」觸發的錯誤，以及送出訂單後退回選位步驟的其他下單失敗（超過每筆訂單限購張數、分區尚未設定票種、區域隨選可售座位不足、「下一步」的限購檢查未通過、其他下單失敗）SHALL 顯示在結帳列內的錯誤訊息區，MUST NOT 顯示在頁面頂端。送出時 429、送出時 `409 SalesNotOpen` 與「確認訂單」的限購檢查未通過時停在確認步驟，顯示在確認步驟的錯誤區；送出中買家已回到選位步驟時改顯示在結帳列（兩處共用同一則訊息，完整規則見確認步驟 Requirement）。與選位操作無關、或發生後結帳列不會顯示的錯誤（活動資料載入失敗、排隊狀態查詢失敗、加入排隊失敗、送出時 `403 QueueAdmissionRequired`）SHALL 維持顯示在頁面頂端。兩處的錯誤訊息都 SHALL 以 `role="alert"` 呈現。買家按下「自動選位」或「下一步」、而且通過前置檢查（自動選位：已登入、販售中、張數大於 0；下一步：有已選內容、未超過限購檢查）後，SHALL 同時清除兩處既有的錯誤訊息，再依該次操作的結果顯示新訊息，與修改前的清除時機一致；「確認訂單」通過前置檢查時同樣清除（見確認步驟 Requirement）。未通過前置檢查時不清除既有訊息。

#### Scenario: BW-FLOW-001 座位很多時結帳列固定在視窗底部
- **WHEN** 已登入的買家分別以 320、390、720、721、1280px 寬、700px 高的視窗開啟一個第一個分區至少有 400 個座位的活動詳情頁，並捲動到第一個分區的頂端
- **THEN** 「下一步」按鈕完全位於視窗內，且最後一個座位的頂端位於視窗下緣之下

#### Scenario: BW-FLOW-002 結帳列列出已選座位，超過 6 個時截斷
- **WHEN** 已登入買家依序選取 7 個座位
- **THEN** 結帳列依選取順序列出前 6 個座位的「分區-座位號碼」，並顯示「等 7 個座位」；取消其中 1 個後，清單改為列出剩下的 6 個，且不顯示「等 N 個座位」

#### Scenario: BW-FLOW-003 選位、區域隨選與送出的錯誤顯示在結帳列
- **WHEN** 已登入買家觸發以下任一錯誤：已達限購張數後再點選新座位、區域隨選張數超過可售座位數、送出訂單時後端回傳一般下單失敗（退回選位步驟後）
- **THEN** 對應的錯誤訊息出現在結帳列內的錯誤訊息區，且頁面頂端不顯示錯誤訊息

#### Scenario: BW-FLOW-004 頁面層級錯誤維持顯示在頁面頂端
- **WHEN** 活動資料載入失敗，或已登入買家送出訂單時後端回傳 `403 QueueAdmissionRequired`
- **THEN** 錯誤訊息顯示在頁面頂端，結帳列內不顯示該錯誤訊息

#### Scenario: BW-FLOW-005 已選內容改變時摘要以 polite live region 公告
- **WHEN** 已登入買家點選一個可選座位
- **THEN** 摘要文字更新為「已選 1 個座位…」，且摘要元素帶有 `aria-live="polite"`

#### Scenario: BW-FLOW-006 排隊畫面不顯示結帳列
- **WHEN** 已登入買家進入熱門搶購模式的活動，狀態為尚未加入排隊或 `Waiting`
- **THEN** 頁面不顯示結帳列與「下一步」按鈕

#### Scenario: BW-FLOW-007 重新操作時清除兩處的舊錯誤
- **WHEN** 一般下單失敗、且重新載入資料也失敗，頁面頂端與結帳列各顯示一則錯誤（已選內容因失敗而清空）後，買家重新點選一個可選座位，再按「下一步」
- **THEN** 頁面頂端的載入失敗訊息與結帳列的下單失敗訊息都消失，畫面進入確認步驟

### Requirement: 前端導覽處理未知網址並在換頁時回到頁首
前端路由 SHALL 將沒有對應路由的網址導回活動列表頁，不顯示空白頁面。一般換頁 SHALL 捲動到頁首；只改變 `step` query 的導覽（同一路徑、其他 query 與 hash 相同，例如活動詳情頁進入或離開確認步驟）MUST NOT 由路由捲動，焦點與捲動交由頁面處理，此規則優先於下一句，瀏覽器上一頁／下一頁只改變 `step` 時也不還原記錄的捲動位置；瀏覽器上一頁／下一頁（只改 `step` 的導覽除外）SHALL 交回瀏覽器記錄的捲動位置（資料非同步載入的頁面在還原當下高度可能不足，實際位置可能較原位置接近頁首，此為已知限制）。

#### Scenario: 開啟不存在的網址
- **WHEN** 使用者開啟沒有對應路由的網址（例如 `/no-such-page/deep`）
- **THEN** 前端導向活動列表頁

#### Scenario: 換頁回到頁首
- **WHEN** 使用者在已捲動的頁面點選連結前往另一頁
- **THEN** 新頁面從頁首開始顯示；若為瀏覽器上一頁／下一頁，則交回瀏覽器記錄的捲動位置（只改變 `step` query 的導覽除外，見 BW-NAV-STEP-001）

#### Scenario: BW-NAV-STEP-001 切換確認步驟不捲回頁首
- **WHEN** 導覽只改變 `step` query（例如 `/events/{id}` 與 `/events/{id}?step=confirm` 之間，不論是否有瀏覽器記錄的捲動位置）
- **THEN** 路由不捲動頁面；路徑、其他 query 或 hash 不同的導覽維持原本的捲動規則
