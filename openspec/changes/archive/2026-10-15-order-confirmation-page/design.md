## Context

目前購票路徑：活動詳情頁選位 → 結帳列「送出訂單」→ 立即呼叫 `placeOrder`（後端建立 Pending 訂單、保留 10 分鐘，`CreateOrderHandler.HoldDuration` 常數）→ `router.push('/order-result/:id')` → 結果頁提供「確認付款／取消訂單」。

- 結果頁 `OrderResultPage.vue` 與訂單明細頁 `OrderDetailPage.vue` 共用 `usePendingOrderActions`，兩頁對 Pending 訂單的操作相同。
- 送出錯誤分流都在 `EventDetailPage.vue` 的 `handleSubmit()`：401、`403 QueueAdmissionRequired`、`403 RealNameRequired`、429、`409 SalesClosed`／`SalesNotOpen`、其他失敗。
- 排隊流程：熱門搶購活動要先排隊，`Admitted` 後才能選位；下單 API 為同步回應。入場資格有效 `AdmissionTtlSeconds`（`appsettings.json`，預設 300 秒），從放行起算，選位與確認步驟停留的時間都算在內。todo 文件寫的「排隊模式下建單是在結果頁等待」與程式不符，本 change 一併更正。
- 路由 `scrollBehavior` 目前為 `savedPosition ?? { top: 0 }`，任何導覽（含只改 query）都會捲回頁首。
- 前端已有 Pinia（`stores/auth.ts`）。

## Goals / Non-Goals

**Goals:**

- 建立訂單前讓買家看到完整的座位、計數票種、金額與注意事項，勾選同意後才建單。
- 建單成功後回到活動列表，提示 10 分鐘內付款並提供前往付款的連結。
- 移除結果頁，舊網址仍可用。
- 既有錯誤分流行為保留，只補上「錯誤後停在哪一步」。

**Non-Goals:**

- 不改後端、API、訂單狀態、保留時間、排隊與販售期間規則。
- 確認步驟不重新查詢座位可售狀態（後端建單時才是最終把關，與現行相同）。
- 不在活動列表顯示倒數計時或即時訂單狀態。
- 不做跨重新整理保存已選內容（現行選位也不保存）。

## Decisions

### 決策 1：確認步驟是同一頁的另一個步驟，以 `?step=confirm` 表示

「下一步」以 `router.push({ query: { step: 'confirm' } })` 進入；頁面 `watch(route.query.step)` 切換畫面。確認步驟取代購票欄內的選位內容（區域隨選、座位網格、計數購票、結帳列），購票欄上方既有的販售提示、實名引導、頁面頂端錯誤維持原位。左側活動資訊不變。

- 「返回改選」呼叫 `router.back()`，與瀏覽器上一頁同一路徑，已選內容在元件狀態中保留。確認步驟只能經由 push 進入（見下方正規化），上一筆紀錄一定是同一活動的選位步驟。
- **正規化**：網址帶 `step=confirm` 但目前不符合確認步驟條件時（沒有已選內容、未登入、`canPurchase` 為 false），以 `router.replace` 移除 `step`。涵蓋直接開啟或重新整理帶 `step=confirm` 的網址、瀏覽器下一頁回到確認步驟但內容已被清空，以及停留確認步驟期間條件失效（例如計時跨過停售時間、排隊資格被收回）。
- 錯誤導致的退回一律用 `router.replace` 移除 `step`，不依賴瀏覽器紀錄。

替代方案：
- 獨立路由 `/events/:id/confirm`：已選內容要跨元件傳遞（store 或 query），重新整理也要處理，比同頁切換多一層狀態。使用者已選同頁方案。
- 對話框（`el-dialog`）：瀏覽器上一頁無法關閉，手機版內容多時不好閱讀。

### 決策 2：「確認訂單」的啟用條件與防重複送出

- 注意事項勾選框每次進入確認步驟都重設為未勾選，避免返回改選後勾選狀態沿用到新內容。
- 「確認訂單」在未勾選、送出中時停用；確認步驟本身只在可購買時存在（決策 1 正規化）。
- 送出中「確認訂單」顯示 loading，「返回改選」停用，同一次確認只呼叫一次下單 API。
- 送出前沿用既有的限購重新加總檢查（防線不變）。「下一步」也做同一檢查，超過時錯誤顯示在結帳列、不進入確認步驟。
- 錯誤清除時機：既有「通過前置檢查後清除頁面頂端與結帳列兩處錯誤」改由「下一步」執行；「確認訂單」通過前置檢查後清除確認步驟的錯誤區與頁面頂端錯誤。

### 決策 3：下單錯誤後停在哪一步

原則：**照原樣重試就可能成功的錯誤停在確認步驟，其他退回選位步驟**。各錯誤原本的訊息、清空、刷新行為不變。

| 錯誤 | 步驟 | 訊息位置 | 已選內容 |
| --- | --- | --- | --- |
| 401 | 導向登入頁，`redirect` 為 `/events/:id`（不帶 `step`） | — | 不處理（離開頁面） |
| 429 | 停在確認步驟 | 確認步驟錯誤區 | 保留 |
| `409 SalesNotOpen` | 停在確認步驟 | 確認步驟錯誤區 | 保留 |
| `403 QueueAdmissionRequired` | 退回選位 | 頁面頂端（既有） | 保留，重新查詢排隊狀態 |
| `403 RealNameRequired` | 退回選位 | 實名引導（既有） | 保留 |
| `409 SalesClosed` | 退回選位 | 販售提示「本活動已停售」（既有） | 保留，操作停用 |
| 其他失敗 | 退回選位 | 結帳列（既有） | 清空並重新載入（既有） |

`403 QueueAdmissionRequired` 與 `409 SalesClosed` 即使不主動退回，也會因 `canPurchase` 變 false 被決策 1 的正規化退回；明列在表中是為了讓行為不依賴計時與輪詢的時序。

確認步驟的錯誤區放在「確認訂單」按鈕上方，`role="alert"`，比照結帳列錯誤區。兩個錯誤區共用既有的 `actionErrorMessage`，依當下步驟渲染在其中一處。這樣送出中按上一頁回到選位步驟時，429／SalesNotOpen 的訊息仍看得到，不需另外處理跨步驟搬移；清除時機只在「下一步」「確認訂單」「自動選位」通過前置檢查時。

### 決策 4：成功後回活動列表，以一次性 Pinia store 傳遞提示

新增 `stores/placedOrderNotice.ts`：`placedOrderId: string | null`、`setPlacedOrder(id)`、`consumePlacedOrder(): string | null`（取出並清空）、`clearPlacedOrder()`。

- 建單成功：`setPlacedOrder(id)`，接著 `router.replace({ name: 'events' })`（取代確認步驟這筆紀錄，按上一頁回到活動詳情頁的選位步驟，不會回到已送出的確認畫面）。
- 活動列表 `setup` 時呼叫 `consumePlacedOrder()`，有值就顯示頂端橫幅：`el-alert type="success"`、可關閉、`role="status"`，文字「訂單已建立，已為你保留 10 分鐘，請在期限內完成付款」，附 `router-link`「前往付款」指向 `/orders/{id}`。
- 橫幅只顯示一次：關閉、重新整理或再次進入列表都不再出現。重新整理會讓 store 清空，這是預期行為，訂單仍可在「我的訂單」找到。
- 送出中買家已離開活動詳情頁（離開導覽已開始，即 `onBeforeRouteLeave` 已觸發，或元件已卸載）時，成功回應不導頁，避免把買家從其他頁面拉走；也不 `setPlacedOrder`，因為延後到下次進入列表才顯示時「保留 10 分鐘」可能已過期，store 為全域也可能在換帳號後露出前一人的訂單連結。改用 `ElMessage.success`「訂單已建立，請到「我的訂單」完成付款」。同樣情形下的 401 也不導向登入頁。離開導覽失敗時（`router.afterEach` 帶 failure，或 `router.onError`，例如目標頁檔案載入失敗）買家仍在本頁，恢復為未離開，否則確認步驟仍可再按、計數票會重複下單。兩個 hook 是全域的，只在失敗的 `to` 與最近一次 `onBeforeRouteLeave` 收到的 `to` 為同一物件時才恢復（vue-router 傳給兩者的是同一物件）：連點連結時前一次導覽被後一次取代（cancelled），買家仍在離開途中。
- 導向活動列表失敗（`replace` reject，或 resolve 成 NavigationFailure）時，訂單已建立，不落入下單失敗處理：清除 store 中的提示、顯示上述成功訊息、清空已選內容、退回選位並重新載入，已下單的座位顯示為不可選，避免重複下單。若此時頁面已視為離開（買家另點連結取代了這次導頁），只清提示、顯示成功訊息並清空已選內容，不改步驟、不重新載入，避免取消買家的導覽或在卸載後重啟輪詢。
- 回應落在離開途中、之後離開導覽才失敗（恢復為未離開時）：離開途中被略過的「退回選位」此時補做（離開途中有錯誤分流要求退回、或確認步驟無法顯示而網址仍帶 `step` 時移除），離開途中訂單已成立者另重新載入；成功回應在離開途中即清空已選內容，所以恢復後不會停在可再按的確認步驟（BW-CONFIRM-020）。
- 卸載後才回來的下單錯誤（例如 403 QueueAdmissionRequired 查排隊狀態仍為 Waiting）不得再排程排隊輪詢：`startQueuePolling` 於卸載後不再建立 timer，避免已卸載頁面持續輪詢（此漏洞 master 上的輪詢回應晚於卸載時亦存在，一併修正）。
- 登出或換發失敗時（auth store `clearSession()`）呼叫 `clearPlacedOrder()`：成功後的 `replace` 被取消等情形留下的提示屬於前一個登入者，不得在換帳號後顯示。

替代方案：
- 用 query（`/events?placed=:id`）：重新整理或分享網址會重複顯示，還要驗證 query 內容。
- `ElMessage` toast：幾秒後消失，買家來不及點「前往付款」。

文字用「已為你保留」而不是 proposal 草稿的「座位為你保留」，因為只買計數票種的訂單沒有座位。

### 決策 5：橫幅寫死「10 分鐘」

保留時間是後端常數 `CreateOrderHandler.HoldDuration`，API 回應（201 `{ id }`）不含到期時間。為了顯示精確時間而在列表頁多查一次訂單明細，只為一行提示，不划算；橫幅出現時距建單只有一次導頁的時間差。精確到期時間由訂單明細頁顯示伺服器 `HeldUntilUtc`。

### 決策 6：只切換 `step` 時不捲動

`scrollBehavior` 判斷 `to.path === from.path`，且除了 `step` 以外 query 相同、`hash` 相同時，回傳 `false`（不捲動），捲動交給元件處理。瀏覽器上一頁／下一頁也適用，不還原 `savedPosition`：元件在返回時把焦點移到「下一步」，同時還原記錄位置會與焦點捲動互相競爭。其他情形維持 `savedPosition ?? { top: 0 }`。

### 決策 7：焦點與捲動

- 進入確認步驟：焦點移到確認步驟標題（`h2`，`tabindex="-1"`），瀏覽器 `focus()` 預設會把標題捲進可視範圍。
- 「返回改選」或瀏覽器上一頁回到選位步驟：焦點移到結帳列的「下一步」按鈕。
- 錯誤導致的退回不另外移焦點，錯誤訊息以 `role="alert"` 公告。

替代方案：`scrollIntoView` 再 `focus({ preventScroll: true })`。兩步驟在 jsdom 不好驗證，`focus()` 一步即可。

### 決策 8：注意事項內容

固定文字（`<ul>`，不用 `v-html`）：

- 確認訂單後，系統為你保留 10 分鐘；期限內未付款，訂單會自動取消並釋出座位與票券。
- 付款完成後才會出票，票券與 QR Code 可在「我的訂單」查看。
- `isRealNameRequired` 為 true 時加一行：本活動需實名，入場時須出示與登記資料相符的證件。

勾選框文字「我已閱讀並同意注意事項」。

### 決策 9：移除結果頁，舊網址導向明細頁

刪除 `OrderResultPage.vue` 與其測試。路由改為 `{ path: 'order-result/:id', redirect: (to) => ({ name: 'order-detail', params: { id: to.params.id } }) }`。導向後由 `order-detail` 的 `requiresAuth` 處理登入，權限與 404／403 由明細頁既有行為處理。`usePendingOrderActions` 保留，只剩明細頁使用，註解同步更新。

## Risks / Trade-offs

- [入場資格 300 秒包含確認步驟停留時間] → 確認步驟不增加後端時間；逾時收到 `403 QueueAdmissionRequired` 時依決策 3 退回選位、保留已選內容並重新查詢排隊狀態，行為與現行相同。注意事項不提入場時限，避免與保留 10 分鐘混淆。
- [確認步驟顯示的座位可能已被他人搶走] → 與現行相同，由後端建單時把關，失敗走「其他失敗」清空並刷新。
- [橫幅寫死 10 分鐘，後端常數改變時會不一致] → 決策 5；後端不動，前端集中成單一常數（橫幅與注意事項共用），常數旁註解寫明對應 `CreateOrderHandler.HoldDuration`。
- [多一步操作，搶票時多一次點擊] → 這是使用者要求的確認步驟，取捨已接受。
- [測試 mock 的 `useRoute` 是靜態物件] → 既有約 40 個測試（`submitButton(` 共 47 處）要改成可反應的 route mock 才能驗證 `step` 切換；tasks 1.x 先處理測試基礎。
- [守衛把離開導覽導回目前所在網址] → vue-router 判為重複導覽（不重跑離開守衛，afterEach 的 `to` 與離開守衛收到的不是同一物件），`hasLeftPage` 不會恢復，之後下單成功只顯示訊息、不導頁。現有 `router/index.ts` 的守衛只導向登入頁、活動列表、我的主辦方，碰不到；之後新增會導回活動詳情頁的守衛時須處理。
- [以瀏覽紀錄跳轉（popstate）離頁失敗後補做退回選位] → vue-router 先非同步走回原紀錄，才呼叫 afterEach／onError；此時補做的 `replace` 可能改到錯誤的那筆紀錄，只影響瀏覽紀錄，不會重複下單。需同時在確認步驟、一次跳多筆紀錄、離頁失敗、且離頁途中訂單已成立，記為已知限制，未在真實瀏覽器驗證。
- [瀏覽器上一頁在送出中回到選位步驟] → 請求繼續完成：成功依決策 4 導向活動列表；失敗依決策 3 的分流，退回選位對已在選位步驟的頁面不產生作用；停在確認步驟類的訊息因共用 `actionErrorMessage` 顯示在結帳列（BW-CONFIRM-016）。送出中「下一步」為 loading，焦點等送出結束、按鈕可用後才移過去；送出中又以下一頁回到確認步驟時取消這個延後動作，避免之後的錯誤退回搶走焦點。已知限制：此情形成功導向列表後，瀏覽紀錄的下一頁仍是 `?step=confirm`（瀏覽器無法刪除前進紀錄）；從列表按上一頁回到的是選位步驟那筆紀錄之前的位置，不影響訂單，不處理。

## 安全確認

- 外部輸入：只新增前端狀態（勾選框、`step` query）。`step` 只與字串 `'confirm'` 比對，其他值視為選位步驟；不會渲染進 DOM。
- 資料庫：無變更。
- 權限：下單仍需登入，401 依既有方式導向登入頁；`/orders/:id` 的 `requiresAuth` 與後端擁有者檢查不變，舊網址導向不繞過。
- 前端：注意事項與橫幅為固定文字與插值，不使用 `v-html`；API 呼叫沿用既有 `httpClient` 攔截器帶 Auth Header。

## AC 測試對應例外

核准狀態：**已核准**（2026-10-14）。

- **適用範圍**：只有 BW-FLOW-001「座位很多時結帳列固定在視窗底部」，其中的「按鈕完全位於視窗內」sticky 版面斷言。按鈕文字改為「下一步」的部分用 Vitest 驗證（tasks 2.1）。
- **偏離理由**：sticky 定位與視窗內位置需要真實版面計算，jsdom 沒有版面。沿用 purchase-flow-ux 已核准（2026-10-10）的同一例外。本 change 不改結帳列 CSS，只改按鈕文字與點擊行為。
- **替代驗證**：tasks 6.3。以瀏覽器量測重跑 purchase-flow-ux 的斷言 1，在 320、390、720、721、1280px 寬、700px 高逐一記錄：
  - 通過條件：「下一步」按鈕 `bottom <= 700` 且 `top >= 0`，且 `lastSeatTop > 700`。
  - 量測無效（不算通過）：`lastSeatTop <= 700`；找不到「下一步」按鈕或最後一個座位；座標不是有限數值；按鈕寬或高不大於 0。
  - 失敗條件：按鈕超出視窗。
- **解除條件**：專案導入可在 CI 跑的真實瀏覽器測試（例如 Playwright）後，改為自動化測試。
