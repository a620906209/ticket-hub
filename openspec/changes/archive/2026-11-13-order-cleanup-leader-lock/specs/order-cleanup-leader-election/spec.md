## ADDED Requirements

### Requirement: 逾時訂單清理的多實例互斥執行
系統 SHALL 在逾時訂單清理背景服務每一輪執行實際清理（掃描逾時仍為 Pending 的訂單並逐筆取消）之前，先嘗試取得以 Redis 為後端的分散式鎖（單一固定 key，涵蓋整輪清理）；取得成功時 MUST 執行本輪清理，且無論清理正常結束或拋出例外，MUST 在該輪結束時釋放該鎖；取得失敗（鎖已被其他實例持有）時 MUST 直接跳過本輪，不掃描、不取消任何訂單，等待下一輪再嘗試，並以 Debug 等級記錄跳過原因。分散式鎖的取得與釋放 MUST NOT 改變既有清理邏輯對外可觀察的結果（逾時 Pending 訂單最終被取消、座位與計數庫存被釋放，見 `ticket-ordering` 能力「取消訂單，統一處理主動取消與逾時清理」）。

#### Scenario: OCLE-001 單一實例取得鎖並執行清理
- **WHEN** 只有一個實例在跑清理背景服務，該輪嘗試取得分散式鎖，且資料庫中有逾時的 Pending 訂單
- **THEN** 系統成功取得鎖，取消該批訂單並釋放其座位與庫存，執行完畢後釋放鎖

#### Scenario: OCLE-002 多實例同時進入同一輪，僅一個實例處理該批訂單
- **WHEN** 兩個實例幾乎同時進入清理週期，各自嘗試取得同一把鎖，且資料庫中有同一批逾時的 Pending 訂單
- **THEN** 只有一個實例取得鎖並處理該批訂單，另一個實例本輪不執行任何掃描與取消；每筆訂單被取消的次數為 1，其座位被釋放的次數為 1，且日誌不出現因重複取消而產生的 Conflict Warning

#### Scenario: OCLE-003 未取得鎖的實例於下一輪重新競爭
- **WHEN** 某實例某一輪因鎖被其他實例持有而跳過
- **THEN** 該實例於下一輪仍會重新嘗試取得鎖，不因上一輪跳過而永久停止嘗試

#### Scenario: OCLE-004 清理拋出例外時仍釋放鎖
- **WHEN** 某實例取得鎖後，該輪清理在掃描階段拋出例外
- **THEN** 系統仍釋放該鎖，其他實例於下一輪可重新取得，且該例外沿用既有行為記錄為錯誤、不使背景服務停止

### Requirement: 清理鎖的租約與逾時自動釋放
清理鎖 SHALL 具備 TTL；持有者正常完成本輪後 MUST 主動釋放。若持有者在 TTL 到期前未能釋放（例如處理中途當掉），系統 SHALL 在 TTL 到期後視為鎖已釋放，允許其他實例於後續輪次重新取得，不需人工介入。鎖的釋放 MUST 只由目前實際持有者完成，MUST NOT 讓一個實例釋放另一個實例目前持有的鎖。本機制 MUST NOT 實作鎖的自動續租：若持有者因清理耗時超過 TTL 而仍在執行，另一實例 MAY 取得新鎖並開始清理，形成短暫重疊執行；系統 MUST NOT 阻止這種重疊，重疊期間的正確性由取消操作本身的資料庫鎖保證（見「逾時訂單的並發取消不重複釋放庫存」Requirement），分散式鎖只負責在正常情況下避免重複工作。

#### Scenario: OCLE-005 持有者未釋放，TTL 到期後鎖自動可用
- **WHEN** 持有鎖的實例在 TTL 到期前未釋放（模擬處理中途中斷）
- **THEN** TTL 到期後，其他實例於後續輪次可成功取得鎖並執行清理，不需人工介入

#### Scenario: OCLE-006 重疊執行期間不重複釋放庫存
- **WHEN** 實例 A 持有的鎖因 TTL 到期而失效但仍在清理中，實例 B 取得新鎖並開始清理同一批訂單
- **THEN** 每筆訂單最終只被取消一次，其座位與計數庫存只被釋放一次，不因兩個實例重疊而多釋放

### Requirement: Redis 不可用時清理照常執行
系統 SHALL 在嘗試取得清理鎖時明確區分「鎖已被其他實例持有」與「無法連線至 Redis」。當無法連線 Redis（含 Redis 回報唯讀、載入中等非連線類錯誤）時，系統 MUST 記錄 Warning 等級的結構化 log（指出本輪在未取得鎖的情況下執行），且 MUST 照常執行本輪清理（fail-open），不得跳過。理由：清理的正確性由資料庫層的取消操作保證，Redis 鎖只是效率優化，Redis 故障不應使逾時訂單的座位與庫存無法回收。Redis 恢復連線後的下一輪 MUST 恢復正常的鎖互斥行為，不需重新啟動應用程式。此行為與購票排隊入場推進的 fail-closed 是刻意不同的選擇（該機制的正確性依賴 Redis）。釋放鎖失敗 MUST NOT 遮蔽清理結果（清理的例外照常往外傳，清理成功的輪次不被記為失敗）。應用程式啟動階段 MUST NOT 因 Redis 不可用而被阻塞，沿用既有非阻塞連線設定。

#### Scenario: OCLE-007 Redis 不可用時照跑清理並記錄 Warning
- **WHEN** 清理背景服務嘗試取得鎖時無法連線至 Redis，且資料庫中有逾時的 Pending 訂單
- **THEN** 系統記錄 Warning 結構化 log（指出本輪未取得鎖），並照常取消該批訂單、釋放座位與庫存，背景服務不停止

#### Scenario: OCLE-007b 取鎖拋出非連線類 Redis 例外時照跑清理
- **WHEN** 清理背景服務嘗試取得鎖時，Redis 回報非連線類錯誤（例如唯讀、載入中），且資料庫中有逾時的 Pending 訂單
- **THEN** 系統記錄 Warning 結構化 log（指出本輪未取得鎖），並照常取消該批訂單，背景服務不停止

#### Scenario: OCLE-007c 釋放鎖失敗不遮蔽清理結果
- **WHEN** 清理已完成或清理拋出例外，而釋放鎖時 Redis 回報錯誤
- **THEN** 系統只記錄 Warning，清理拋出的原始例外照常往外傳，清理成功的輪次不被記為失敗

#### Scenario: OCLE-008 Redis 恢復後回復鎖互斥
- **WHEN** Redis 從無法連線恢復為可連線，清理服務下一輪再次嘗試取得鎖
- **THEN** 系統恢復分散式鎖互斥行為（取得者執行、未取得者跳過），不需重新啟動應用程式

### Requirement: 逾時訂單的並發取消不重複釋放庫存
系統 SHALL 保證同一筆逾時 Pending 訂單被多個清理執行緒（含不同實例）並發取消時，只有一個取消成功，其餘回報訂單已非 Pending 的衝突；該訂單的座位暫扣與計數庫存 MUST 只釋放一次，訂單最終狀態為 Cancelled。此保證 MUST NOT 依賴分散式鎖（鎖不可用或重疊執行時仍須成立）。

#### Scenario: OCLE-009 兩個並發的逾時清理取消同一筆座位訂單
- **WHEN** 兩個清理執行緒同時對同一筆已逾時、含座位項目的 Pending 訂單執行逾時取消
- **THEN** 恰有一個成功、另一個回報衝突，座位被釋放一次，訂單狀態為 Cancelled

#### Scenario: OCLE-010 兩個並發的逾時清理取消同一筆計數訂單
- **WHEN** 兩個清理執行緒同時對同一筆已逾時、僅含計數項目的 Pending 訂單執行逾時取消
- **THEN** 恰有一個成功、另一個回報衝突，該票種的可售數量只增加該訂單的數量一次，訂單狀態為 Cancelled
