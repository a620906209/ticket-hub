## ADDED Requirements

### Requirement: 同一活動的下單彼此不因活動層級鎖互斥
系統 SHALL 讓同一活動、互不重疊的選購項目（不同座位、不同計數票種）的建立訂單請求可以同時處理，不因活動本身的鎖定而逐筆通過。建立訂單在交易內 MUST 以共享鎖（PostgreSQL `FOR SHARE`）鎖定並重讀活動，以鎖定後讀到的 `IsQueueModeEnabled` 為唯一採信依據；共享鎖之間不互斥，但與切換熱門搶購模式時對活動列的寫入互斥，因此下單與切換排隊模式之間的線性化語意（TP-ORDER-015／016）不變：

- 建立訂單持有共享鎖期間，切換排隊模式的寫入 MUST 等到該筆建立訂單的交易結束才提交。
- 切換排隊模式提交之後才取得共享鎖的建立訂單，MUST 讀到切換後的值。

選購項目重疊時（同一座位、同一計數票種），仍由座位與票種各自的列鎖保證只有一筆成功、不超賣，不受本規則影響。

#### Scenario: TP-ORDER-034 同一活動不同座位的下單可同時進行
- **WHEN** 買家 A 對某活動座位 1 建立訂單，交易已鎖定活動但尚未提交；此時買家 B 對同一活動座位 2 建立訂單
- **THEN** 買家 B 的請求 MUST 不等待買家 A 的交易結束即完成，回傳 `201 Created`；買家 A 之後提交也成功，兩筆訂單各持有自己的座位

#### Scenario: TP-ORDER-035 進行中的下單會阻塞排隊模式切換
- **WHEN** 買家對一般活動（`IsQueueModeEnabled = false`）建立訂單，交易已鎖定活動但尚未提交；此時 Admin 將該活動切換為熱門搶購模式
- **THEN** 切換請求 MUST 等到該筆建立訂單的交易結束後才提交；該筆建立訂單依切換前的 `false` 正常完成（`201 Created`），不要求排隊資格

#### Scenario: TP-ORDER-036 同一座位的並發下單仍只有一筆成功
- **WHEN** 兩位買家同時對同一活動的同一個可售座位建立訂單
- **THEN** 只有一筆回傳 `201 Created`，另一筆回傳 `409 Conflict`；該座位只被一筆訂單持有

### Requirement: 建立訂單每筆只占用一條資料庫連線
系統 SHALL 讓每筆建立訂單請求從第一次資料庫查詢到交易結束都使用同一條資料庫連線，只向連線池取得一次；請求結束時（成功、業務錯誤、例外）MUST 歸還該連線。交易提交後的 Redis 呼叫（入場鏡像同步、票種快取失效）期間 MUST NOT 占用資料庫連線。請求格式驗證失敗時 MUST NOT 取得資料庫連線。

#### Scenario: TP-ORDER-037 各結果路徑都只取得一次連線並歸還
- **WHEN** 建立訂單請求分別以下列方式結束：成功；取得連線後、開交易前的業務拒絕（票種不存在 404、選購項目跨活動 400、不在販售期間、需實名但買家未完成實名、超過每筆訂單張數上限、交易外提早判斷為 409）；交易內業務拒絕（鎖定後判斷為 409、排隊模式下未取得入場資格）；交易內拋出例外
- **THEN** 每條路徑向連線池取得連線的次數 MUST 為 1，請求結束後該連線 MUST 已歸還（DbContext 連線狀態為 Closed）；請求格式驗證失敗時取得次數 MUST 為 0

#### Scenario: TP-ORDER-038 提交後的 Redis 呼叫不占用資料庫連線
- **WHEN** 建立訂單交易提交成功，接著執行入場鏡像同步（排隊模式下）與票種快取失效
- **THEN** 執行這兩項 Redis 呼叫時，該請求的資料庫連線 MUST 已歸還；Redis 呼叫拋出非取消例外時的處理維持既有規格：票種快取失效為 fail-open（`query-caching` QC-FAIL-002：記 Warning，訂單仍回 `201 Created`），入場鏡像同步為 best-effort（`purchase-queue` PQ-COMPLETE-003：名額由背景校正收斂）。請求取消（`OperationCanceledException`）時的行為不在本 Scenario 驗收範圍內
