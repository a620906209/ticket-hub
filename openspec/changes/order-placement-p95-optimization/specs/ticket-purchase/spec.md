## ADDED Requirements

### Requirement: 建立訂單在開啟交易前提早拒絕已確定失敗的請求
為避免已確定失敗的請求排隊等待活動層級的鎖，系統 SHALL 在開啟資料庫交易、取得任何鎖之前，依交易外讀取的資料提早拒絕下列請求；交易內鎖定後的判斷仍是唯一權威，提早判斷通過 MUST NOT 被視為建立成功的保證。

- **座位分區比對**：所選活動專屬座位對應的座位樣板查無資料時，MUST 在開啟交易前回報找不到對應資源。座位項目所選座位實際所屬分區與所選票種分區不一致時，交易外讀到活動者 MUST 在開啟交易前回報驗證錯誤；交易外讀不到活動者改在交易內鎖定活動後、排隊資格檢查與鎖定任何座位或票種之前回報。比對順序 MUST 為座位樣板存在 → 座位圖成員 → 分區，因此異常資料一律回報找不到對應資源而非驗證錯誤。此比對不論活動是否為排隊模式皆執行，因此排隊模式下未入場的會員選定分區不一致的座位時，回應驗證錯誤而非 403 `QueueAdmissionRequired`（與既有「所有項目須屬於同一場活動」等請求驗證在取得任何鎖之前完成的優先順序一致）。所選座位樣板所屬座位圖 MUST 與該活動的座位圖相同，不同時視為座位不在該活動座位圖中，回報找不到對應資源；此比對以交易外讀到的活動執行，交易外讀不到活動時改以交易內鎖定後讀到的活動執行（位置同上述分區比對，先於分區比對），不得以「活動專屬座位只由該活動座位圖產生」的建立期規則取代比對。此提前依賴下列不變量：座位樣板的所屬座位圖與分區、活動專屬座位對應的座位樣板與活動、活動對應的座位圖，建立後皆 MUST NOT 被變更（Domain 型別不提供修改這些值的方法或 setter）；若日後提供修改這些資料的功能，比對 MUST 移回交易內鎖定之後。
- **提早衝突判斷**：僅在交易外讀到的活動存在且 `IsQueueModeEnabled = false` 時執行，位置在交易外的販售期間、實名、限購檢查與分區比對之後。以交易外讀取的資料與當下時間判斷：任一座位項目所選座位經 `IsAvailableForHold(now)` 判定不可鎖定，或任一計數項目的購買數量超過該票種交易外讀到的 `AvailableQuantity`，MUST 回應 `409 Conflict`，不開啟交易、不鎖定或扣減任何項目。座位狀態 MUST 透過 `seat-reservation` 能力規定的狀態方法判斷，不得讀取內部欄位。
- 交易外讀到活動為排隊模式，或交易外讀不到活動時，MUST NOT 執行提早衝突判斷，一律交由交易內判斷，維持排隊資格檢查（403 `QueueAdmissionRequired`）優先於座位／庫存衝突（409）。
- 唯一例外：交易外讀到未開啟排隊模式、交易內鎖定重讀時已開啟（Admin 於兩次讀取之間切換），且提早衝突判斷已判定項目不可鎖定或庫存不足時，回應 409 而非 403；請求在提早判斷時即結束，不進入交易內的排隊資格檢查。

#### Scenario: TP-ORDER-017 座位已售出時不開啟交易即回 409
- **WHEN** 已登入會員對未開啟排隊模式、販售中的活動，選定一個已售出（Sold）的座位建立訂單
- **THEN** 系統回應 `409 Conflict`，不建立訂單，且不開啟資料庫交易、不鎖定任何資料列

#### Scenario: TP-ORDER-018 座位被其他訂單暫扣中時不開啟交易即回 409
- **WHEN** 已登入會員對未開啟排隊模式、販售中的活動，選定一個由其他訂單暫扣且尚未逾時的座位建立訂單
- **THEN** 系統回應 `409 Conflict`，不建立訂單，且不開啟資料庫交易

#### Scenario: TP-ORDER-019 暫扣已逾時的座位不被提早拒絕
- **WHEN** 已登入會員選定的座位處於 Held 狀態但暫扣已逾時
- **THEN** 系統不提早拒絕，依既有規則在交易內鎖定並建立訂單

#### Scenario: TP-ORDER-020 計數票種庫存不足時不開啟交易即回 409
- **WHEN** 已登入會員對未開啟排隊模式、販售中的活動，指定的購買數量超過該計數票種目前的可售總量
- **THEN** 系統回應 `409 Conflict`，不建立訂單，不扣減任何庫存，且不開啟資料庫交易

#### Scenario: TP-ORDER-021 座位分區不一致時不開啟交易即回驗證錯誤
- **WHEN** 交易外讀到活動，已登入會員選定的座位實際所屬分區與配對票種分區不同
- **THEN** 系統回報驗證錯誤，不建立訂單，且不開啟資料庫交易（補充 TP-ORDER-004：該情境的拒絕時點提前到交易前，TP-ORDER-004 所述查詢過程中短暫的 row lock 不再發生）

#### Scenario: TP-ORDER-022 排隊模式活動不做提早衝突判斷
- **WHEN** 交易外讀到活動 `IsQueueModeEnabled = true`，未入場的會員選定已售出的座位建立訂單
- **THEN** 系統回應 `403 Forbidden`（`title = "QueueAdmissionRequired"`），而非 409

#### Scenario: TP-ORDER-023 提早判斷通過但交易內競爭失敗
- **WHEN** 交易外讀取時座位仍可鎖定，但在本請求取得鎖之前已被另一筆訂單暫扣
- **THEN** 系統以交易內鎖定後的判斷為準回應 `409 Conflict`，不建立訂單，不超賣

#### Scenario: TP-ORDER-024 交易外讀不到活動時不做提早衝突判斷
- **WHEN** 交易外讀不到活動、交易內鎖定重讀時讀得到（未開啟排隊模式），會員選定已售出的座位建立訂單
- **THEN** 系統不提早拒絕，開啟交易並由交易內判斷回應 `409 Conflict`，不建立訂單

#### Scenario: TP-ORDER-025 排隊模式在兩次讀取之間開啟且項目已不可售
- **WHEN** 交易外讀到活動 `IsQueueModeEnabled = false`，之後 Admin 將其切換為 `true`，未入場的會員選定的座位在交易外讀取時已售出
- **THEN** 系統回應 `409 Conflict`，不建立訂單，且不開啟資料庫交易

#### Scenario: TP-ORDER-026 排隊模式下分區不一致優先回驗證錯誤
- **WHEN** 未入場的會員對 `IsQueueModeEnabled = true` 的活動選定分區與票種不一致的座位建立訂單
- **THEN** 系統回報驗證錯誤（而非 403 `QueueAdmissionRequired`），不建立訂單，且不開啟資料庫交易

#### Scenario: TP-ORDER-027 多座位訂單其中一席不可鎖定
- **WHEN** 已登入會員對未開啟排隊模式的活動選定 3 個座位，其中 1 個已售出、其餘 2 個可售
- **THEN** 系統回應 `409 Conflict`，不建立訂單，不開啟資料庫交易，3 個座位狀態皆不變

#### Scenario: TP-ORDER-028 混合訂單中計數項目庫存不足
- **WHEN** 已登入會員對未開啟排隊模式的活動，同時選定一個可售座位與一個購買數量超過可售總量的計數票種
- **THEN** 系統回應 `409 Conflict`，不建立訂單，不開啟資料庫交易，座位維持可售、票種庫存不變

#### Scenario: TP-ORDER-029 座位樣板查無資料時不開啟交易即回找不到資源
- **WHEN** 已登入會員選定的活動專屬座位存在，但其對應的座位樣板查無資料
- **THEN** 系統回報找不到對應資源（404），不建立訂單，且不開啟資料庫交易

#### Scenario: TP-ORDER-030 座位樣板不屬於該活動座位圖
- **WHEN** 活動專屬座位對應的座位樣板屬於另一張座位圖（違反建立期規則的異常資料），會員選定該座位建立訂單
- **THEN** 系統回報找不到對應資源（404）而非驗證錯誤（即使票種分區也不一致），不建立訂單，不鎖定任何座位或票種；交易外讀到活動時不開啟資料庫交易，交易外讀不到活動時在交易內排隊資格檢查之前回報

#### Scenario: TP-ORDER-033 交易外讀不到活動時分區不一致於鎖內回驗證錯誤
- **WHEN** 交易外讀不到活動、交易內鎖定重讀時讀得到，已登入會員選定的座位屬於該活動座位圖，但分區與配對票種分區不同
- **THEN** 系統回報驗證錯誤，不建立訂單；此時已開啟交易，但在排隊資格檢查與鎖定任何座位或票種之前回報

#### Scenario: TP-ORDER-032 同時違反限購與分區時回限購錯誤
- **WHEN** 已登入會員的請求同時超過限購數量，且所選座位分區與票種分區不一致
- **THEN** 系統回報限購錯誤（交易外檢查順序：販售期間 > 實名 > 限購 > 座位樣板存在 > 座位圖成員 > 分區），不建立訂單，且不開啟資料庫交易

#### Scenario: TP-ORDER-031 分區比對前提的屬性不可變
- **WHEN** 檢查座位樣板的所屬座位圖與分區、活動專屬座位的座位樣板與活動、活動的座位圖這些屬性
- **THEN** 這些屬性皆沒有 setter（含 `init`），外部無法在建立後變更

## MODIFIED Requirements

### Requirement: 透過 API 建立訂單並鎖定座位或扣減票種庫存
系統 SHALL 提供已登入會員建立訂單的端點，可在同一次請求中混合兩種選購項目：座位項目（指定 `EventSeatId` 與對應 `TicketTypeId`，票種須為 `RequiresSeat = true`）、計數項目（指定 `TicketTypeId` 與購買數量，票種須為 `RequiresSeat = false`，不指定 `EventSeatId`）。鎖定/扣減與驗證規則遵循既有 `ticket-ordering` 能力的規範（原子性鎖定或扣減、票價快照、跨活動與重複選位驗證等），並將發起建立的會員身份記錄為訂單的買家身份。選定的座位或票種若不存在，MUST 拒絕建立並回報找不到對應資源。座位項目所選座位實際所屬的分區 MUST 與所選票種的分區一致，不一致 MUST 拒絕建立。項目所指定的票種與其 `RequiresSeat` 屬性不一致時（例如對 `RequiresSeat = false` 的票種指定 `EventSeatId`，或對 `RequiresSeat = true` 的票種只指定數量、不指定座位，或對 `RequiresSeat = true` 的票種指定 `EventSeatId` 卻同時指定非 1 的購買數量）MUST 拒絕建立並回報驗證錯誤。同一次請求中，`EventSeatId` 為空的計數項目之間 `TicketTypeId` MUST 互不重複——買家想購買多張同一計數票種，MUST 將數量加總為單一選購項目的購買數量送出，不接受拆成多筆重複的計數項目。選購項目未提供購買數量時，系統 MUST 視為 1，維持本次變更前既有客戶端（未帶此欄位)的既有座位選購行為不受影響。若訂單所屬活動的 `IsQueueModeEnabled = true`（熱門搶購模式），系統 MUST 以「建立訂單當下」重新查得的排隊資格為準，確認發起建立的會員在該活動有狀態為 `Admitted` 且未逾時的排隊紀錄，沒有則 MUST 拒絕建立訂單、不執行任何座位鎖定或庫存扣減，並以 `403 Forbidden`（`ProblemDetails`，`title` 為穩定字串 `"QueueAdmissionRequired"`，與座位/庫存競爭失敗使用的 `409 Conflict`、以及既有其他業務語意也可能回傳的 403（例如非本人操作）明確區隔，前端 MUST 同時檢查 `status === 403` 且 `title === "QueueAdmissionRequired"` 兩者，不得只依 HTTP 狀態碼分流，據以導向排隊等待畫面）回報需先加入排隊；即使該會員在送出請求當下確實持有有效資格，只要在系統實際檢查的當下該資格已變為逾時或不存在，仍 MUST 視為不合格並拒絕——不得沿用請求開始前、或前端輪詢當下查到的舊有資格結果。`IsQueueModeEnabled = false` 的活動不受此限制，行為與本次變更前一致。同理，「活動是否處於熱門搶購模式」本身也 MUST 以系統實際執行建立邏輯當下重新讀取到的值為準，不得沿用建立訂單流程開始前（尚未進入實際處理）查詢到的舊值——若 Admin 在買家的建立訂單請求處理過程中變更了該活動的熱門搶購模式，系統 MUST 依實際處理當下的設定值決定是否套用排隊資格檢查，不得因為讀到變更前的舊值而錯誤地略過或誤套用排隊檢查；唯一例外見「建立訂單在開啟交易前提早拒絕已確定失敗的請求」（交易外讀到未開啟排隊模式且項目已不可售時提早回 409，見 TP-ORDER-015、TP-ORDER-025）。此請求另受 `api-rate-limiting` 能力定義的請求頻率限制規範，超過限制時依該能力規則拒絕，不進入本需求的建立邏輯。

#### Scenario: TP-ORDER-001 成功建立訂單
- **WHEN** 已登入會員選定多個皆可售的座位與對應票種建立訂單
- **THEN** 系統成功建立 Pending 訂單，所選座位轉為 Held，訂單的買家身份為該會員

#### Scenario: TP-ORDER-002 座位已被鎖定時建立訂單失敗

- **THEN** 系統回傳衝突錯誤，不建立訂單，本次已鎖定成功的其餘座位復原為 Available

#### Scenario: TP-ORDER-003 選定不存在的座位或票種
- **WHEN** 已登入會員選定的座位或票種當中，有一個實際不存在
- **THEN** 系統 MUST 拒絕建立訂單並回報找不到對應資源，不對任何座位執行鎖定（不建立業務上的 Held 狀態、不落地寫入；查詢過程中可能對座位短暫取得資料庫層級的 row lock，交易結束即釋放）

#### Scenario: TP-ORDER-004 座位分區與票種分區不一致
- **WHEN** 已登入會員選定的座位當中，有一個實際所屬分區與配對的票種分區不同（例如座位屬於 A 區，卻配了 B 區票種）
- **THEN** 系統 MUST 拒絕建立訂單並回報驗證錯誤，不建立訂單也不對任何座位執行鎖定（不建立業務上的 Held 狀態、不落地寫入；查詢過程中可能對座位短暫取得資料庫層級的 row lock，交易結束即釋放）

#### Scenario: TP-ORDER-005 成功建立純計數選購的訂單
- **WHEN** 已登入會員對 `RequiresSeat = false` 的票種指定購買數量（不指定 `EventSeatId`）建立訂單，且指定數量不超過當下可售總量
- **THEN** 系統成功建立 Pending 訂單，該票種的可售總量相應扣減，訂單的買家身份為該會員

#### Scenario: TP-ORDER-006 純計數票種指定了座位
- **WHEN** 已登入會員對 `RequiresSeat = false` 的票種在請求中指定了 `EventSeatId`
- **THEN** 系統 MUST 拒絕建立訂單並回報驗證錯誤，不對任何座位或庫存執行變更

#### Scenario: TP-ORDER-007 綁座位票種未指定座位
- **WHEN** 已登入會員對 `RequiresSeat = true` 的票種在請求中只指定數量、未指定 `EventSeatId`
- **THEN** 系統 MUST 拒絕建立訂單並回報驗證錯誤，不對任何座位或庫存執行變更

#### Scenario: TP-ORDER-008 座位項目指定非 1 的購買數量
- **WHEN** 已登入會員對 `RequiresSeat = true` 的票種在請求中指定了 `EventSeatId`，同時指定購買數量不等於 1
- **THEN** 系統 MUST 拒絕建立訂單並回報驗證錯誤，不對任何座位或庫存執行變更

#### Scenario: TP-ORDER-009 同一計數票種在同一次請求中重複出現
- **WHEN** 已登入會員在同一次建立訂單請求中，對同一個 `RequiresSeat = false` 的票種送出兩筆以上不指定 `EventSeatId` 的選購項目（例如分開指定購買數量 2 與 3）
- **THEN** 系統 MUST 拒絕建立訂單並回報驗證錯誤，不對任何座位或庫存執行變更；買家應改為送出單一選購項目、購買數量為加總後的值

#### Scenario: TP-ORDER-010 座位選購項目未提供購買數量（既有客戶端相容）
- **WHEN** 已登入會員呼叫建立訂單端點，選購項目比照本次變更前的既有格式，只提供 `EventSeatId` 與 `TicketTypeId`、未包含購買數量欄位
- **THEN** 系統 MUST 視為購買數量 1，依既有座位選購規則處理，行為與本次變更前完全一致

#### Scenario: TP-ORDER-011 熱門搶購模式下已入場的會員成功建立訂單
- **WHEN** 已登入會員在 `IsQueueModeEnabled = true` 的活動中，擁有狀態為 `Admitted` 且未逾時的排隊紀錄，送出建立訂單請求
- **THEN** 系統依既有規則正常處理建立訂單，成功後將該筆排隊紀錄標記為 `Completed`

#### Scenario: TP-ORDER-012 熱門搶購模式下未入場即嘗試建立訂單
- **WHEN** 已登入會員在 `IsQueueModeEnabled = true` 的活動中，沒有狀態為 `Admitted` 且未逾時的排隊紀錄，送出建立訂單請求
- **THEN** 系統 MUST 拒絕建立訂單，回傳 `403 Forbidden`（`title = "QueueAdmissionRequired"`），不執行任何座位鎖定或庫存扣減，回報需先加入排隊

#### Scenario: TP-ORDER-013 一般活動不受熱門搶購模式影響
- **WHEN** 已登入會員對 `IsQueueModeEnabled = false` 的活動建立訂單
- **THEN** 系統依既有規則正常處理，不檢查排隊紀錄

#### Scenario: TP-ORDER-014 排隊資格於建立訂單處理過程中才變為逾時
- **WHEN** 已登入會員送出建立訂單請求時排隊資格仍為 `Admitted` 且未逾時，但系統實際執行資格確認的當下，該資格已超過 `AdmissionExpiresAtUtc`
- **THEN** 系統 MUST 拒絕建立訂單，回傳 `403 Forbidden`（`title = "QueueAdmissionRequired"`），不執行任何座位鎖定或庫存扣減——即使請求送出當下資格仍有效，仍以系統檢查當下的最新狀態為準

#### Scenario: TP-ORDER-015 建立訂單處理過程中熱門搶購模式才被開啟
- **WHEN** 買家送出建立訂單請求時活動的 `IsQueueModeEnabled` 仍為 `false`，但在系統實際執行建立邏輯之前，Admin 已將該活動切換為 `true`，且買家不具備已入場的排隊資格
- **THEN** 系統 MUST 以切換後的最新設定值為準，拒絕建立訂單並回傳 `403 Forbidden`（`title = "QueueAdmissionRequired"`），不得因請求送出當下讀到的是切換前的 `false` 而略過排隊檢查、繼續完成建立
- **AND** 例外：若交易外讀到 `false` 時所選座位已不可鎖定或計數票種庫存已不足，系統依「建立訂單在開啟交易前提早拒絕已確定失敗的請求」回應 `409 Conflict`（同樣不建立訂單，見 TP-ORDER-025）；此情況只發生在 Admin 切換排隊模式的時間差內，且回應如實反映項目已不可售

#### Scenario: TP-ORDER-016 建立訂單處理過程中熱門搶購模式才被關閉
- **WHEN** 買家送出建立訂單請求時活動的 `IsQueueModeEnabled` 仍為 `true` 且買家不具備已入場的排隊資格，但在系統實際執行建立邏輯之前，Admin 已將該活動切換為 `false`
- **THEN** 系統 MUST 以切換後的最新設定值為準，不再檢查排隊資格，依一般活動的既有規則正常處理建立訂單
