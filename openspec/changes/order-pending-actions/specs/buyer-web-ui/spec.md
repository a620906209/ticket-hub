## MODIFIED Requirements

### Requirement: 買家可在下單結果頁確認或取消剛下的訂單
系統 SHALL 在下單成功導向的訂單結果頁，以下單當下取得的訂單 Id 呼叫 `buyer-order-query` 能力的訂單明細 API，取得訂單目前狀態與伺服器端持有到期時間（`HeldUntilUtc`）後，顯示訂單 Id 與訂單狀態的中文標籤；MUST NOT 以前端本地狀態或前端自行推算的時間代替伺服器值（原「不透過查詢 API」與「以下單當下時間加 10 分鐘推算」的規定，是在買家訂單查詢 API 尚不存在時的權宜做法，本次廢止）。訂單目前狀態為 Pending 時，頁面 SHALL 提供「確認付款」「取消訂單」操作入口，呼叫既有確認／取消訂單 API，並顯示「保留至 {時間}」；狀態非 Pending 時 MUST NOT 顯示這兩個操作與持有到期時間。按鈕文字由既有「確認訂單」改為「確認付款」、成功後狀態文字由「已確認」改為「已付款」，與統一的訂單狀態中文標籤（Paid「已付款」）一致。確認或取消操作不論成功或失敗，系統 SHALL 重新查詢訂單明細並依伺服器回傳的狀態更新畫面；操作失敗時 SHALL 在重新查詢完成後顯示失敗訊息，不得被重新查詢流程清除。明細 API 回應 404 或 403 時，比照訂單明細頁顯示對應提示，不提供任何操作。

#### Scenario: 在訂單結果頁確認訂單
- **WHEN** 買家在下單成功後導向的訂單結果頁，訂單目前狀態為 Pending，點選「確認付款」
- **THEN** 系統呼叫確認訂單 API，成功後重新查詢訂單明細，畫面顯示狀態「已付款」，不再顯示確認付款與取消操作

#### Scenario: 在訂單結果頁取消訂單
- **WHEN** 買家在下單成功後導向的訂單結果頁，訂單目前狀態為 Pending，點選「取消訂單」
- **THEN** 系統呼叫取消訂單 API，成功後重新查詢訂單明細，畫面顯示狀態「已取消」，不再顯示確認付款與取消操作

#### Scenario: BW-RESULT-001 重新整理已付款訂單的結果頁
- **WHEN** 買家在結果頁確認付款成功後重新整理頁面
- **THEN** 系統查詢訂單明細 API，顯示狀態「已付款」，不顯示確認付款與取消操作

#### Scenario: BW-RESULT-002 結果頁顯示伺服器端持有到期時間
- **WHEN** 買家進入一筆 Pending 訂單的結果頁
- **THEN** 系統顯示訂單 Id、狀態「待付款」，且「保留至 {時間}」為明細 API 回傳的 `HeldUntilUtc`，不是前端自行推算的時間

#### Scenario: BW-RESULT-003 確認付款失敗
- **WHEN** 買家在結果頁點選「確認付款」，確認訂單 API 回傳錯誤（例如付款失敗或訂單已逾時）
- **THEN** 系統重新查詢訂單明細、依伺服器狀態更新畫面，並在重新查詢完成後顯示失敗訊息

### Requirement: 「我的訂單」列表與明細頁串接查詢 API，顯示訂單、票券狀態與 QR Code
系統 SHALL 提供「我的訂單」列表頁與訂單明細頁，呼叫 `buyer-order-query` 能力查詢自己的訂單列表與明細。列表頁與明細頁 SHALL 顯示每筆訂單的狀態。訂單狀態與票券狀態 SHALL 以中文標籤顯示（訂單：Pending「待付款」、Paid「已付款」、Cancelled「已取消」、Expired「已逾時」；票券：Issued「已出票」、Redeemed「已核銷」），MUST NOT 直接顯示英文列舉值；收到上述以外的未知狀態值時 SHALL 原樣顯示該值，不得顯示空白或造成頁面錯誤。持有到期時間（`HeldUntilUtc`）僅在訂單狀態為 Pending 時 SHALL 顯示為「保留至 {時間}」提示，訂單狀態為 Paid、Cancelled 或 Expired（終態或已逾時）時 MUST NOT 顯示此欄位——`HeldUntilUtc` 是建立訂單當下設定的原始值，不因訂單轉為終態而清空或重新賦值（比照既有 `buyer-order-query` 能力對此欄位的定義），對終態訂單顯示原值會誤導買家以為訂單仍在保留中。明細頁 SHALL 顯示訂單狀態、每筆項目對應的票券清單與各自狀態（`Issued`／`Redeemed`）。狀態為 `Issued` 或 `Redeemed` 的票券，明細頁 SHALL 提供「查看 QR Code」操作，點選後顯示該票券的 QR Code 圖檔；圖檔 MUST 透過既有 API 攔截器（帶 Authorization Header）取得後以 Blob／Object URL 顯示，MUST NOT 直接將 `<img src>` 指向需要驗證的端點網址。訂單內項目尚未出票（例如訂單仍為 Pending）時，該項目 SHALL 顯示「尚未出票」，不顯示 QR Code 操作。`Ticket.Voided` 狀態依既有 `ticket-issuance` 能力規格現況無任何觸發路徑，本次前端 MUST NOT 為 `Voided` 實作任何顯示邏輯（不在本次 UI 行為範圍內）；待未來新增 `Voided` 觸發路徑的提案時，須一併規劃對應的前端顯示行為。

#### Scenario: 開啟我的訂單列表頁
- **WHEN** 已登入買家開啟「我的訂單」頁面
- **THEN** 系統呼叫訂單列表 API，顯示自己所有訂單的中文狀態標籤；狀態為 Pending 的訂單額外顯示「保留至 {時間}」，其他狀態不顯示持有到期時間；尚無任何訂單時顯示空清單提示，不視為錯誤

#### Scenario: 開啟訂單明細頁查看已出票訂單
- **WHEN** 已登入買家從列表點入一筆已確認付款、已出票的訂單明細
- **THEN** 系統呼叫訂單明細 API，顯示訂單狀態「已付款」（不顯示持有到期時間，因訂單已為 Paid 終態）與每筆項目對應的票券清單，狀態為 `Issued` 的票券顯示「已出票」與「查看 QR Code」操作

#### Scenario: 點選查看 QR Code
- **WHEN** 買家在訂單明細頁對一張 `Issued` 或 `Redeemed` 狀態的票券點選「查看 QR Code」
- **THEN** 系統透過帶 Authorization Header 的請求取得 QR Code 圖檔，以 Blob／Object URL 顯示在畫面上

#### Scenario: 開啟尚未出票訂單的明細頁
- **WHEN** 已登入買家開啟一筆狀態為 Pending、尚未出票的訂單明細頁
- **THEN** 系統顯示訂單狀態「待付款」與「保留至 {時間}」，訂單內每筆項目顯示「尚未出票」，不提供「查看 QR Code」操作

#### Scenario: 直接以網址開啟不存在的訂單明細頁
- **WHEN** 使用者直接開啟一個不存在的訂單 Id 的明細頁網址
- **THEN** 訂單明細 API 回應 404，系統顯示「找不到這筆訂單」提示與返回「我的訂單」列表的操作，不顯示任何訂單資料

#### Scenario: 直接以網址開啟非本人的訂單明細頁
- **WHEN** 已登入買家直接開啟非自己所屬訂單的明細頁網址
- **THEN** 訂單明細 API 回應 403，系統顯示「你沒有權限查看這筆訂單」提示與返回「我的訂單」列表的操作，不顯示任何訂單資料

#### Scenario: BW-MYORDER-DISPLAY-002 收到未知的訂單狀態值
- **WHEN** 訂單列表 API 回傳的某筆訂單狀態為前端對照表未定義的值
- **THEN** 該筆訂單的狀態欄位原樣顯示該值，頁面其餘內容正常顯示

## ADDED Requirements

### Requirement: 買家可在訂單明細頁對 Pending 訂單確認付款或取消
系統 SHALL 在「我的訂單」明細頁，當訂單目前狀態為 Pending 時提供「確認付款」「取消訂單」操作，呼叫既有確認／取消訂單 API；狀態非 Pending 時 MUST NOT 顯示這兩個操作。操作不論成功或失敗，系統 SHALL 重新查詢訂單明細並依伺服器回傳的狀態更新畫面（確認付款成功後，已出票的票券與「查看 QR Code」操作隨之顯示）；操作失敗時 SHALL 在重新查詢完成後顯示失敗訊息，不得被重新查詢流程清除。操作進行中 SHALL 停用兩個操作按鈕，避免重複送出。「我的訂單」列表頁不提供確認付款或取消操作，買家由「查看明細」進入明細頁操作。

#### Scenario: BW-PENDING-001 在訂單明細頁確認付款
- **WHEN** 已登入買家開啟一筆 Pending 訂單的明細頁並點選「確認付款」
- **THEN** 系統呼叫確認訂單 API，成功後重新查詢明細，畫面顯示狀態「已付款」、票券清單與「查看 QR Code」操作，不再顯示確認付款與取消操作

#### Scenario: BW-PENDING-002 在訂單明細頁取消訂單
- **WHEN** 已登入買家開啟一筆 Pending 訂單的明細頁並點選「取消訂單」
- **THEN** 系統呼叫取消訂單 API，成功後重新查詢明細，畫面顯示狀態「已取消」，不顯示持有到期時間，不再顯示確認付款與取消操作

#### Scenario: BW-PENDING-003 確認付款失敗後以伺服器狀態為準
- **WHEN** 已登入買家在 Pending 訂單明細頁點選「確認付款」，確認訂單 API 回傳錯誤，且重新查詢後伺服器狀態為 Expired
- **THEN** 畫面顯示狀態「已逾時」與失敗訊息，不再顯示確認付款與取消操作

#### Scenario: BW-PENDING-004 非 Pending 訂單不顯示操作
- **WHEN** 已登入買家開啟狀態為 Paid、Cancelled 或 Expired 的訂單明細頁
- **THEN** 頁面不顯示「確認付款」與「取消訂單」操作

#### Scenario: BW-PENDING-005 操作進行中停用按鈕
- **WHEN** 已登入買家點選「確認付款」後、確認訂單 API 尚未回應
- **THEN** 「確認付款」與「取消訂單」按鈕皆為停用狀態

### Requirement: 角色為 Admin 的使用者可從買家端版面進入主辦方審核頁
買家端版面的會員下拉選單 SHALL 在登入者角色為 `Admin` 時顯示「主辦方審核」入口，點選後導向 `/admin/organizers`；此入口不要求已切換 Organizer（與該頁面路由守衛規則一致）。角色非 `Admin` 的使用者 MUST NOT 看到此入口。

#### Scenario: BW-ADMIN-ENTRY-001 尚未切換 Organizer 的 Admin 從買家端進入審核頁
- **WHEN** 角色為 `Admin`、尚未切換至任何 Organizer 的使用者在買家端開啟會員下拉選單並點選「主辦方審核」
- **THEN** 系統導向 `/admin/organizers` 並顯示審核頁內容

#### Scenario: BW-ADMIN-ENTRY-002 非 Admin 使用者看不到審核入口
- **WHEN** 角色非 `Admin` 的已登入使用者開啟買家端會員下拉選單
- **THEN** 選單中不顯示「主辦方審核」
