## MODIFIED Requirements

### Requirement: 買家可在下單結果頁確認或取消剛下的訂單
系統 SHALL 在下單成功導向的訂單結果頁，以下單當下取得的訂單 Id 呼叫 `buyer-order-query` 能力的訂單明細 API，取得訂單目前狀態與伺服器端持有到期時間（`HeldUntilUtc`）後，顯示訂單 Id 與訂單狀態的中文標籤；MUST NOT 以前端本地狀態或前端自行推算的時間代替伺服器值（原「不透過查詢 API」與「以下單當下時間加 10 分鐘推算」的規定，是在買家訂單查詢 API 尚不存在時的權宜做法，本次廢止）。訂單目前狀態為 Pending 時，頁面 SHALL 提供「確認付款」「取消訂單」操作入口，呼叫既有確認／取消訂單 API，並顯示「保留至 {時間}」；狀態非 Pending 時 MUST NOT 顯示這兩個操作與持有到期時間。按鈕文字由既有「確認訂單」改為「確認付款」、成功後狀態文字由「已確認」改為「已付款」，與統一的訂單狀態中文標籤（Paid「已付款」）一致。「取消訂單」操作 SHALL 先顯示確認對話框（按鈕文字為「取消訂單」與「保留訂單」，MUST NOT 使用「確定」／「取消」），使用者選「保留訂單」或關閉對話框時 MUST NOT 呼叫取消訂單 API；「確認付款」不需確認對話框。操作成功時 SHALL 顯示簡短成功提示（「付款成功，票券已出票」／「訂單已取消」）。重新查詢期間 SHALL 保留目前畫面內容，不得先清空再重新顯示。確認或取消操作不論成功或失敗，系統 SHALL 重新查詢訂單明細並依伺服器回傳的狀態更新畫面；操作失敗時 SHALL 在重新查詢完成後顯示失敗訊息，不得被重新查詢流程清除。操作後的重新查詢本身失敗（網路錯誤、5xx、404、403）時，系統 SHALL 顯示錯誤訊息並提供「重新整理」操作，且 MUST NOT 再顯示「確認付款」「取消訂單」按鈕與「保留至 {時間}」——此時畫面內容可能已過時，不得讓使用者依過時狀態再次操作。確認或取消操作失敗、重新查詢後伺服器狀態仍為 Pending 時（例如付款被拒，確認訂單 API 回應 409，訂單不會因此轉為終態），SHALL 同時顯示失敗訊息、「保留至 {時間}」與「確認付款」「取消訂單」操作，允許買家再次嘗試。明細 API 回應 404 或 403 時，比照訂單明細頁顯示對應提示與返回「我的訂單」列表的操作，不顯示任何訂單資料、不提供確認付款或取消操作；網址中的訂單 Id 非 GUID 格式時，前端不另做格式檢查，由後端路由約束 `{id:guid}` 回應 404，依 404 處理。同一頁面切換至另一筆訂單時（例如瀏覽器上一頁／下一頁），系統 SHALL 以新訂單重新查詢，且較早送出的明細請求晚於較新請求回應時 MUST NOT 覆蓋畫面。

- **THEN** 畫面顯示錯誤訊息與「重新整理」操作，不顯示「確認付款」與「取消訂單」按鈕，也不顯示「保留至」

### Requirement: 「我的訂單」列表與明細頁串接查詢 API，顯示訂單、票券狀態與 QR Code
系統 SHALL 提供「我的訂單」列表頁與訂單明細頁，呼叫 `buyer-order-query` 能力查詢自己的訂單列表與明細。列表頁與明細頁 SHALL 顯示每筆訂單的狀態。訂單狀態與票券狀態 SHALL 以中文標籤顯示（訂單：Pending「待付款」、Paid「已付款」、Cancelled「已取消」、Expired「已逾時」；票券：Issued「已出票」、Redeemed「已核銷」），MUST NOT 直接顯示英文列舉值；狀態 SHALL 以標籤元件呈現並依狀態區分顏色（訂單 Pending 為警示色、Paid 為成功色、Cancelled／Expired 為中性色；票券 Issued 為成功色、Redeemed 為中性色；未知值為中性色），標籤內 MUST 顯示文字，顏色不得為唯一辨識方式；收到上述以外的未知狀態值時 SHALL 原樣顯示該值，不得顯示空白或造成頁面錯誤。持有到期時間（`HeldUntilUtc`）僅在訂單狀態為 Pending 時 SHALL 顯示為「保留至 {時間}」提示，訂單狀態為 Paid、Cancelled 或 Expired（終態或已逾時）時 MUST NOT 顯示此欄位——`HeldUntilUtc` 是建立訂單當下設定的原始值，不因訂單轉為終態而清空或重新賦值（比照既有 `buyer-order-query` 能力對此欄位的定義），對終態訂單顯示原值會誤導買家以為訂單仍在保留中。明細頁 SHALL 顯示訂單狀態、每筆項目對應的票券清單與各自狀態（`Issued`／`Redeemed`）。狀態為 `Issued` 或 `Redeemed` 的票券，明細頁 SHALL 提供「查看 QR Code」操作，點選後顯示該票券的 QR Code 圖檔；圖檔 MUST 透過既有 API 攔截器（帶 Authorization Header）取得後以 Blob／Object URL 顯示，MUST NOT 直接將 `<img src>` 指向需要驗證的端點網址。訂單內項目尚未出票（例如訂單仍為 Pending）時，該項目 SHALL 顯示「尚未出票」，不顯示 QR Code 操作。明細頁網址中的訂單 Id 非 GUID 格式時，前端不另做格式檢查，由後端路由約束 `{id:guid}` 回應 404，依「找不到這筆訂單」處理。`Ticket.Voided` 狀態依既有 `ticket-issuance` 能力規格現況無任何觸發路徑，本次前端 MUST NOT 為 `Voided` 實作任何顯示邏輯（不在本次 UI 行為範圍內）；待未來新增 `Voided` 觸發路徑的提案時，須一併規劃對應的前端顯示行為。

## ADDED Requirements

### Requirement: 買家可在訂單明細頁對 Pending 訂單確認付款或取消
系統 SHALL 在「我的訂單」明細頁，當訂單目前狀態為 Pending 時提供「確認付款」「取消訂單」操作，呼叫既有確認／取消訂單 API；狀態非 Pending 時 MUST NOT 顯示這兩個操作。操作不論成功或失敗，系統 SHALL 重新查詢訂單明細並依伺服器回傳的狀態更新畫面（確認付款成功後，已出票的票券與「查看 QR Code」操作隨之顯示）；操作失敗時 SHALL 在重新查詢完成後顯示失敗訊息，不得被重新查詢流程清除。操作進行中 SHALL 停用兩個操作按鈕，避免重複送出。「取消訂單」操作 SHALL 先顯示確認對話框（按鈕文字為「取消訂單」與「保留訂單」，MUST NOT 使用「確定」／「取消」），使用者選「保留訂單」或關閉對話框時 MUST NOT 呼叫取消訂單 API；「確認付款」不需確認對話框。操作成功時 SHALL 顯示簡短成功提示（「付款成功，票券已出票」／「訂單已取消」）。重新查詢期間 SHALL 保留目前畫面內容，不得先清空再重新顯示。操作後的重新查詢本身失敗（網路錯誤、5xx、404、403）時，系統 SHALL 顯示錯誤訊息並提供「重新整理」操作，且 MUST NOT 再顯示「確認付款」「取消訂單」按鈕與「保留至 {時間}」——此時畫面內容可能已過時，不得讓使用者依過時狀態再次操作；「重新整理」查詢進行中 SHALL 停用該按鈕。確認或取消訂單 API 回應 429 時，失敗訊息 SHALL 為「請求過於頻繁，請稍後再試」。操作失敗、重新查詢後伺服器狀態仍為 Pending 時（例如付款被拒，確認訂單 API 回應 409，訂單不會因此轉為終態），SHALL 同時顯示失敗訊息、「保留至 {時間}」與「確認付款」「取消訂單」操作，允許買家再次嘗試。同一頁面切換至另一筆訂單時（例如瀏覽器上一頁／下一頁），系統 SHALL 以新訂單重新查詢，且較早送出的明細請求晚於較新請求回應時 MUST NOT 覆蓋畫面；切換前舊訂單仍在進行中的確認／取消操作，其回應 MUST NOT 在新訂單畫面顯示成功提示或失敗訊息，也不得觸發重新查詢而覆蓋新訂單畫面。「我的訂單」列表頁不提供確認付款或取消操作，買家由「查看明細」進入明細頁操作。

- **THEN** 系統不呼叫取消訂單 API，訂單維持「待付款」，不顯示錯誤訊息

#### Scenario: BW-PENDING-007 重新查詢期間保留畫面內容
- **WHEN** 已登入買家在 Pending 訂單明細頁確認付款成功，重新查詢明細的請求尚未回應
- **THEN** 頁面仍顯示原本的訂單內容，不清空、不顯示整頁載入狀態

#### Scenario: BW-PENDING-008 取消訂單失敗後以伺服器狀態為準
- **WHEN** 已登入買家在 Pending 訂單明細頁確認取消，取消訂單 API 回傳錯誤（例如 409），重新查詢後伺服器狀態為 Paid
- **THEN** 畫面顯示狀態「已付款」與失敗訊息，不再顯示確認付款與取消操作

#### Scenario: BW-PENDING-009 操作後重新查詢失敗
- **WHEN** 已登入買家在 Pending 訂單明細頁確認付款後，重新查詢訂單明細的請求失敗（例如網路錯誤）
- **THEN** 畫面顯示錯誤訊息與「重新整理」操作，不顯示「確認付款」與「取消訂單」按鈕，也不顯示「保留至」；點選「重新整理」後、查詢回應前「重新整理」為停用狀態，回應後依結果顯示

#### Scenario: BW-PENDING-010 切換訂單時舊回應不覆蓋畫面
- **WHEN** 已登入買家在訂單 A 的明細頁（Pending）尚未載入完成時，切換至訂單 B 的明細頁（Paid），且訂單 A 的明細回應晚於訂單 B 回來
- **THEN** 畫面顯示訂單 B 的內容與「已付款」，不顯示訂單 A 的資料，也不顯示「確認付款」「取消訂單」

#### Scenario: BW-PENDING-011 確認付款或取消訂單遭頻率限制
- **WHEN** 已登入買家在 Pending 訂單明細頁點選「確認付款」（或確認取消訂單），確認訂單（或取消訂單）API 回應 429
- **THEN** 系統重新查詢明細並依伺服器狀態顯示，失敗訊息為「請求過於頻繁，請稍後再試」

#### Scenario: BW-PENDING-012 確認付款失敗但訂單仍為待付款
- **WHEN** 已登入買家在 Pending 訂單明細頁點選「確認付款」，確認訂單 API 回傳錯誤（例如付款被拒回應 409），且重新查詢後伺服器狀態仍為 Pending
- **THEN** 畫面顯示狀態「待付款」、「保留至 {時間}」與失敗訊息，並重新顯示可操作的「確認付款」與「取消訂單」，買家可再次嘗試

#### Scenario: BW-PENDING-013 切換訂單時舊訂單的操作結果不顯示
- **WHEN** 已登入買家在訂單 A 的明細頁（Pending）點選「確認付款」，確認訂單 API 尚未回應時切換至訂單 B 的明細頁（Paid），之後訂單 A 的確認回應才回來
- **THEN** 畫面維持顯示訂單 B 的內容與「已付款」，不顯示訂單 A 的成功提示或失敗訊息，也不以訂單 A 的重新查詢結果覆蓋畫面

#### Scenario: BW-STATUS-TAG-001 狀態標籤依狀態區分顏色且含文字
- **WHEN** 已登入買家開啟「我的訂單」列表，列表中有 Pending、Paid、Cancelled 訂單
- **THEN** 三者狀態分別以警示色、成功色、中性色的標籤呈現，且標籤內分別顯示「待付款」「已付款」「已取消」

### Requirement: 角色為 Admin 的使用者可從買家端版面進入主辦方審核頁
買家端版面的會員下拉選單 SHALL 在登入者角色為 `Admin` 時顯示「主辦方審核」入口，點選後導向 `/admin/organizers`；此入口不要求已切換 Organizer（與該頁面路由守衛規則一致）。角色非 `Admin` 的使用者 MUST NOT 看到此入口。

#### Scenario: BW-ADMIN-ENTRY-001 尚未切換 Organizer 的 Admin 從買家端進入審核頁
- **WHEN** 角色為 `Admin`、尚未切換至任何 Organizer 的使用者在買家端開啟會員下拉選單並點選「主辦方審核」
- **THEN** 系統導向 `/admin/organizers` 並顯示審核頁內容

#### Scenario: BW-ADMIN-ENTRY-002 非 Admin 使用者看不到審核入口
- **WHEN** 角色非 `Admin` 的已登入使用者開啟買家端會員下拉選單
- **THEN** 選單中不顯示「主辦方審核」
