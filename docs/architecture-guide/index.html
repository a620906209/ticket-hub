前置知識：讀之前要懂的概念

這一節是給還不熟悉後端與資料庫的人。懂的可以跳過，遇到不懂的術語再回來查。

1. 介面（Interface）與依賴注入（DI）

介面只規定「能做什麼」，不管「怎麼做」，例如 IEventSeatRepository 說「能找座位、能鎖座位」。DI 是在程式啟動時決定「要用的那個實作」（例如 Program.cs 註冊哪個類別），程式其他地方只認介面，不認實作。這樣換實作或換成假的（mock）測試都不用改呼叫端。

2. 交易（Transaction）

一組資料庫操作要「全部成功或全部不做」。例如扣庫存和建立訂單必須一起成功，中間任一步失敗就整組回滾（rollback）。交易 commit 之前的修改，其他人看不到。

3. 列鎖（Row Lock）與超賣

兩個請求同時讀到「剩 1 張票」，各自判斷「還有票」，然後都賣出去，這就是超賣（race condition）。解法是讓第一個交易鎖住那一列：
  • SELECT ... FOR UPDATE：鎖住，其他交易要等它結束才能讀寫這一列。
  • SELECT ... FOR SHARE：共享鎖，多個交易可以同時讀，但會擋住別人改寫。
這個專案的座位、票種用 FOR UPDATE，因為要改它們。

4. EF Core 與 Tracking

EF Core 是 C# 的 ORM，把資料表轉成物件。Tracking 指 EF 記住「這個物件從資料庫讀出來、之後改了什麼」，儲存時自動寫回。No-tracking 讀出來的是純資料，改它不會被存。所以在交易裡扣庫存，必須用被追蹤、已鎖定的那個實例。

5. Redis 與快取

Redis 是放在記憶體裡的鍵值資料庫，速度快，但不保證資料不遺失。常見用途：
  • 快取：把常查的結果存起來，設定 TTL（存活時間）到期自動清除。
  • 分散式鎖：多台機器共用同一把鎖，通常附帶過期時間，避免持有者當機後鎖永遠釋放不了。
重點是：Redis 的資料丟了應該能重建，所以不能當成唯一的真相來源。

6. HTTP 狀態碼：4xx 與 500

4xx 表示客戶端的問題（例如「已售完」「不在販售期間」，參數錯誤），是可預期的失敗。500 表示伺服器發生未預期的錯誤（程式 bug、例外）。本專案用 Result 表達前者、用例外表達後者，所以使用者看到的錯誤碼才有意義。

7. 分層架構與依賴方向

程式分成幾層，內層不能引用外層。最內層是「業務規則」，不依賴資料庫或框架。下方「程式碼為什麼分四層」有詳細說明。

8. 其他名詞速查

  • Rate limit：限制單位時間內同一來源的請求次數，用來減壓。
  • CancellationToken：請求被取消（例如使用者關掉網頁）時，通知後端停止還在做的工作。
  • 冪等（idempotent）：同一個請求做一次或做多次，結果一樣。重試時很重要。
  • Mock：測試用的假實作，用來取代真的資料庫或外部服務。

00 架構：為什麼這樣設計

一句話：把「售票規則」和「技術細節」分開放，讓最重要、最不該壞的規則（例如一個座位不能賣兩次）不會因為換資料庫、換框架、加快取而被改到。

後面所有設計，幾乎都是從這句話推出來的。

為什麼 db 和 redis 都要？
PostgreSQL 有交易和列鎖，資料不會錯，但比較慢；Redis 很快，但不保證資料不丟。所以會影響錢和座位的資料只放 PostgreSQL，Redis 只放「丟了也能重建」的東西（快取、排隊鏡像）。
為什麼要 seq？
出問題時要能用 TraceId 把一個請求的所有 log 串起來查（Logging/TraceIdLoggingMiddleware.cs），而不是去容器裡翻文字檔。
為什麼全部放容器？
每個人、每台機器、CI 都用同一個版本的 .NET、PostgreSQL、Redis，避免「我電腦上可以跑」。

程式碼為什麼分四層

用餐廳來比喻：

WebApi ＝ 外場服務生
接單、確認你是誰、把結果端回去。不決定菜怎麼做。Controllers/、Program.cs
Infrastructure ＝ 廚房設備與供應商
真的去 PostgreSQL 存取、去 Redis 排隊、寄信。可以換品牌。Persistence/、Caching/
Application ＝ 店長排的流程
「先檢查庫存、再鎖座位、再成立訂單」這種要協調多樣東西的步驟。Orders/OrderService.cs
Domain ＝ 店規
「座位被別人保留就不能再保留」「庫存不夠就不能賣」。最核心、最少變動。Events/EventSeat.cs、Tickets/TicketType.cs

規則只有一條：外層可以認識內層，內層不能認識外層

Domain 的 .csproj 沒有引用任何其他專案，所以店規裡寫不出「去查 PostgreSQL」這種程式碼，編譯就會失敗。這不是靠大家自律，是靠編譯器擋。

好處 1：規則好測
Domain 不碰資料庫，測試「座位不能重複保留」只要 new 一個物件就能測，幾毫秒跑完。見 tests/ProjectC.Domain.Tests。
好處 2：換技術不動規則
這個專案中途加了 Redis 快取、排隊、分散式鎖，Domain 的售票規則幾乎沒改（4 個相關的 merge 裡只有 1 個動到 Domain，1 個檔案），因為那些都是 Infrastructure 的事。
好處 3：知道東西放哪
看到一段程式碼，問「它是店規、流程、設備、還是服務生的事？」就知道該放哪一層，也知道 bug 該去哪找。

為什麼 Entity 的欄位都是 private set？

如果任何地方都能寫 seat.Status = Sold，店規就形同虛設。改成只能呼叫 seat.Hold(...)，規則檢查就一定會跑到，沒辦法繞過。

介面：插座與插頭

問題來了：Application 要「讀座位」，但它不能認識 Infrastructure，怎麼辦？

內層定義插座IEventSeatRepository
「我需要有人能幫我找座位、鎖座位」
外層提供插頭EventSeatRepository
「我用 EF Core + PostgreSQL 做到」
啟動時插上Program.cs 的 DI 註冊
「要 IEventSeatRepository 時，給它 EventSeatRepository」

這就是「依賴反轉」：內層只依賴自己定義的介面，外層去配合內層。測試時插上假的實作（mock）就能測流程，不用真的資料庫。

介面放 Domain 還是 Application？

問一句：換掉實作時，業務規則的描述要不要跟著改？

  • 要 → 放 Domain，例如 IEventSeatRepository、IEmailNotificationService（「成交要通知買家」是業務規則）
  • 不用 → 放 Application/Common/Interfaces，例如 IDateTimeProvider、IQueryCache、IUnitOfWork（純技術，跟售票無關）

為什麼特別適合售票

售票系統最怕的只有兩件事，架構都是為它們服務：

怕 1：超賣
同一個座位賣給兩個人，是最嚴重的 bug。所以「能不能賣」由 Domain 規則判斷，再由 PostgreSQL 列鎖（FOR UPDATE）保證同一時間只有一個交易能改它。不靠 Redis、不靠前端。
怕 2：開賣瞬間被擠爆
熱門場次一開賣就是大量請求同時湧入。所以前面有 Rate limit、排隊（Redis）、快取（Redis）、驗證碼擋流量；這些都只是「減壓」，擋不住也不會造成超賣，因為最後關卡還是 DB 鎖。
可預期的失敗
「已售完」「不在販售期間」不是程式錯誤，是正常結果。所以用 Result 回傳、轉成 4xx，而不是拋例外變成 500。

代價（誠實版）

  • 檔案多、跳來跳去：做一個功能要碰 4 個專案。小專案這樣做是過度設計；這個專案 Entity 已經很多，才划算。
  • 有既有例外：會員、主辦方相關的程式碼直接用 IApplicationDbContext 查 EF，沒走 Repository。這是早期簡化留下的，2026-10-16 審視後決定不重構，新功能則一律走 Repository（見 docs/archive/2026-10-16-project-review.md 3.1）。讀程式碼時看到兩種寫法不要困惑。
  • 少數 Raw SQL：EF Core 沒有 FOR UPDATE 的寫法，所以鎖定查詢用參數化的 Raw SQL，是有寫明理由的例外。

4 個設計概念

1. 交易外快速檢查、交易內權威判斷

同一條規則（例如販售期間）會檢查兩次。第一次為了效能，不讓注定失敗的請求去排鎖；第二次為了正確性，因為等鎖的期間資料可能已經變了。

2. 防止超賣靠的是 DB 列鎖，不是 Redis

座位和票種用 FOR UPDATE 鎖住。Redis 只負責排隊鏡像和快取，所以放在 commit 之後、以 best-effort 執行；Redis 失敗不會造成超賣。

3. 分層的判斷標準

需要查 DB 或協調多個 Entity 的規則放 OrderService。只看自己狀態就能判斷的規則放 Domain Entity（Hold、Reserve）。CreateOrderHandler 介於兩者之間：它是跨 Entity 的純邏輯，所以放 Application，但不做 I/O。

4. 用 Result 而不是例外表達業務失敗

每個 return Result.Failure(...) 都是可預期的失敗，最後由 ToActionResult 統一轉成 4xx。真正的例外交給全域的 IExceptionHandler，回 500。

自我檢查（先想再展開）

為什麼 Redis 鏡像同步放在 commit 之後，而不是交易內？
Redis 不參與 PostgreSQL 交易。放在交易內的話，交易後來回滾時 Redis 已經改了，兩邊會不一致；而且 Redis 的網路延遲會拉長持鎖和占用連線的時間。DB 才是權威，Redis 只是鏡像，所以 commit 後以 best-effort 同步。
為什麼鎖 Event 用共享鎖（FOR SHARE）就夠，不需要 FOR UPDATE？
下單只讀 Event、不修改它。共享鎖彼此相容，同一活動的多筆下單可以並行，不必逐筆排隊。切換排隊模式要拿 FOR UPDATE，和共享鎖互斥，所以下單期間不會讀到切換一半的狀態。超賣是靠座位、票種各自的 FOR UPDATE 防止，不依賴 Event 鎖。
如果販售期間只在交易外檢查一次，會出什麼問題？
請求可能在開賣前一刻通過檢查，然後等鎖等到停售時間之後才真正下單。所以鎖拿到之後要重新取「現在時間」再檢查一次，交易內那次才算數。
為什麼 TicketType.Reserve() 必須對 GetForUpdateAsync 拿到的實例呼叫？
交易外查到的是 no-tracking、沒加鎖的舊資料。對它扣庫存，會以過期的 AvailableQuantity 為基準（可能超賣），而且 EF 沒有追蹤它，變更也不會被存回去。只有鎖住後重新讀的實例才是正確基準。

02 會員與登入

一句話：用「短命的 Access Token ＋ 長命但會輪替的 Refresh Token」，兼顧不必每次查 DB 的效能，和 token 被偷時能止血。

為什麼要兩種 token？
JWT 驗簽章就能用，不查 DB，但發出去就收不回來，所以只給 30 分鐘。Refresh Token 存在 DB，可以撤銷（登出、偵測到被偷），用來換新的 JWT。
為什麼要輪替？
每次換發都換新的 Refresh Token，舊的作廢。如果作廢的 token 又出現，代表有兩個人拿著同一個 token，系統就撤銷該會員全部 token。
為什麼 DB 只存雜湊？
密碼用 BCrypt、Refresh Token 用雜湊。資料庫就算外洩，也拿不到能直接登入的東西。

03 主辦方權限（多租戶）

一句話：一個人可以屬於多個主辦方；先「切換」選定一家，之後所有後台操作只能碰那一家的資料。

主辦方 Id 從哪來？
從 JWT 的 OrganizerId claim 來，不從網址或 body 來。前端傳什麼都不算數，這樣才無法偽造成別家。
為什麼有兩道檢查？
第一道在 Authorization Policy：沒選主辦方就進不來。第二道在 Handler：資源（活動、訂單、票券）的 OrganizerId 必須等於 JWT 裡的。只有第一道的話，A 主辦方可以改 B 主辦方的活動。
為什麼回 404 不回 403？
回 403 等於告訴對方「這個活動存在，只是不是你的」。回 404 就不洩漏存在與否。

04 排隊購票（熱門搶購模式）

一句話：熱門場次開賣時，不讓所有人同時擠進下單，而是先排隊、一批一批放行；放行的決策交給 Redis 算，紀錄留在 PostgreSQL。

為什麼要排隊？
10 萬人同時下單，DB 鎖會塞爆、大家都超時。排隊讓同時下單的人數有上限，系統穩定，先來的人也比較公平。
為什麼放行用 Redis？
「數目前放行多少人、從隊伍頭取幾個人」要非常快又不能算錯。Redis 的 sorted set 加 Lua Script 可以一次原子完成，不會兩邊同時放行超額。
為什麼還要 leader 鎖？
api 可能開多台，每台都有背景服務。用 Redis 分散式鎖選出一台當這一輪的 leader，其他台跳過。
Redis 掛了會怎樣？
排隊暫停推進（fail-closed），寧可慢也不超額放行。這和快取的策略（Redis 掛了照常服務）相反，見 07。

05 付款、取消、逾時

一句話：下單只是「保留」10 分鐘；付款確認才真正售出並出票，沒付款就由背景服務自動取消、把座位還回去。

訂單狀態
Pending（保留中）→ Paid（已付款、已出票）或 Cancelled（買家取消或逾時被清理）。另有 Expired：只是查詢時依時間推導出來顯示用，不會寫進 DB。狀態轉換寫在 Order.Confirm() / Order.Cancel()，不合法的轉換由 Domain 擋。
為什麼三種動作共用一個骨架？
確認、取消、逾時取消都要「開交易 → 依固定順序鎖訂單、座位、票種 → 改狀態 → commit」，只有中間那步不同。共用骨架才能保證三者的鎖順序一致、不會互相死鎖。
為什麼寄信失敗不算失敗？
錢已經收、票已經出，不能因為信寄不出去就退回。所以寄信放在 commit 之後，失敗只記 log。

06 出票與驗票

一句話：QR Code 裡放「票券 Id ＋ 伺服器簽章」，掃碼時先驗簽章再鎖票改狀態，一張票只能進場一次。

為什麼要簽章？
票券 Id 是 GUID，雖然難猜但不是秘密（例如出現在網址）。加上只有伺服器知道密鑰的 HMAC 簽章，別人就算知道 Id 也做不出有效 QR。
為什麼 QR 不存檔？
QR 可以從 Id 和密鑰隨時算出來，存檔只是多一份要保護、要同步的資料。
為什麼核銷要加鎖？
兩個入口同時掃同一張截圖，沒有鎖的話兩邊都會看到「未使用」而都放行。

排隊放行：fail-closed
Redis 掛了就暫停放行。繼續放行會失去「不超額」的保證。
快取何時清？
改到庫存的動作（下單扣計數票、取消還庫存、新增票種）會在 commit 後刪掉對應快取；純座位訂單不動 AvailableQuantity，不清。

08 前端架構（web/）

一句話：Vue 3 ＋ Element Plus；頁面只管畫面，API 呼叫集中在 api/，登入狀態集中在 Pinia store。

資料夾放什麼為什麼這樣分
pages/依角色分 buyer/、admin/、organizers/三種使用者的畫面互不干擾
layouts/BuyerLayout、AdminLayout、PlatformLayout導覽列、權限區塊依區域共用
api/每個資源一個檔案；httpClient.ts 統一帶 Auth header、處理 401 換發元件不寫 fetch 細節，換發邏輯只寫一次
stores/auth.ts（登入狀態、token）只有跨頁共享的狀態才進 store
composables/useCaptcha、usePendingOrderActions、useRedemptionScanner多個頁面共用的邏輯（含相機掃碼）
router/路由與 beforeEach 守衛（requiresAuth、requiresAdmin、requiresOrganizerContext）沒登入就導去登入頁；頁面都 lazy import，首屏小
前端守衛算安全嗎？
不算。前端守衛只是讓使用者不會看到進不去的頁面；真正的權限檢查在後端（02、03）。前端可以被任意修改，不能信任。
Token 放哪？
Access Token 只在記憶體（重新整理就沒了），Refresh Token 在 localStorage；App 啟動時用 Refresh Token 換一次新的 Access Token 恢復登入。stores/auth.ts:22

09 可觀測性與測試

一句話：出事時查得到（log），改程式時不怕壞（測試），上線前知道撐得住多少（壓測）。

可觀測性

結構化 log
Serilog 輸出到 Console 和 Seq；每個請求和每輪背景工作都有 TraceId，在 Seq 用 TraceId 就能串起一次請求的所有 log。
全域例外處理
Controller 不寫 try-catch。未預期的例外由 ExceptionHandling/GlobalExceptionHandler.cs 統一轉成 ProblemDetails（500），並記錄 log。
敏感資料遮蔽
log 不記密碼、token；Email 以 EmailMasker 遮蔽後才寫入。

測試金字塔

專案測什麼碰真實 DB？
ProjectC.Domain.TestsEntity 規則（座位不能重複保留、庫存不足）否，最快
ProjectC.Application.TestsHandler 流程，Repository 用 Moq 假造否
ProjectC.Infrastructure.TestsRepository、鎖、並發下單（例如 OrderServiceConcurrencyTests）是，Testcontainers 啟動獨立的 PostgreSQL / Redis
ProjectC.WebApi.Tests從 HTTP 打進來：路由、授權、狀態碼是，WebApplicationFactory ＋ Testcontainers
web/ 的 *.test.ts前端元件、store、router否（Vitest）
loadtest/k6 壓測：熱門開賣時的 P95 延遲、是否超賣是，獨立的 compose 設定

為什麼「防超賣」一定要有 Infrastructure 層的並發測試？因為它靠的是 PostgreSQL 的列鎖，用 mock 測不出來，只有真資料庫加上多條並行交易才驗證得到。
