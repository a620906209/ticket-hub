## Instructions

1. 確認目前 git 狀態（`git status`）。若有未提交的變更，先詢問使用者要如何處理；處理完成並重新確認工作樹乾淨前，不可切換分支或覆蓋變更。
2. 在任何分支切換、同步或建立，以及建立 OpenSpec artifacts 之前，先對使用者提出的功能進行 Grill 訪談：
   - 先讀取相關專案文件與程式碼，查明可由環境確認的事實；不要詢問使用者可自行查證的資訊。
   - 將待決策事項整理成設計樹。每一輪同時詢問所有前置條件已確定的決策；依賴本輪未決答案的問題留待後續輪次。
   - 每題編號並附上建議答案，措辭須讓「是」代表接受建議。使用以下格式：
     ```
     ❓ **Q1** - **<問題標題>**：<問題與選項>

     ➡️ <建議答案>

     ---
     ```
   - 等待使用者回答後，依回答更新設計樹，再提出下一輪問題；直到所有分支都已釐清，沒有未決事項。
   - 以摘要列出問題、方案、範圍、關鍵需求、驗收／驗證方向、排除項目，以及英文 kebab-case 功能名稱與 `feature/<功能名稱>` 分支名稱，並請使用者確認雙方理解一致。
   - 使用者確認前，不得切換、同步或建立分支，不得建立或修改 OpenSpec artifacts，也不得開始實作。若使用者不同意摘要，繼續 Grill；若訪談中出現新的重要決策，先釐清並重新確認摘要。
3. 使用者確認共識後，執行以下指令同步 master：
   ```
   git checkout master
   git pull origin master
   ```
4. 建立並切換新分支：
   ```
   git checkout -b feature/<功能名稱>
   ```
5. 分支建立完成後，向使用者確認分支已就緒，接著**必須**執行 `/opsx:propose <功能名稱>`（`<功能名稱>` 沿用 Grill 摘要中確認的名稱）建立本次功能的 spec 提案草稿，不要自行用其他方式產生 proposal。將 Grill 已確認的決策摘要提供給提案流程，避免重複訪談；若提案過程發現新的重要決策，暫停受影響的 artifact 產生，回到 Grill 釐清並取得確認。
6. spec 草稿完成後，依照 CLAUDE.md 的「OpenSpec 工作流規則 → Task 執行前」清單，確認 Acceptance Criteria 是否已定義且對應測試任務，未對應者提醒使用者補上，不進入實作階段。

## Notes

- 這個 skill 負責「Grill 釐清需求 → 開分支 → 交接給 OpenSpec」；負責規劃前訪談，不負責產生 spec artifacts，避免與 OpenSpec 流程重複維護。
- 若專案的預設分支不是 `master`（例如 `main`），使用前請調整步驟 3、4 中的分支名稱。
